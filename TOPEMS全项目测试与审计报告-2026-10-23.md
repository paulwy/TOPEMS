## 六、架构级问题专项分析



1. **依赖方向健康**：svc→lib 单向依赖成立，无 svc 互依赖、无 lib→svc 反向依赖（仅 server 聚合入口）。这是 monorepo 分域演进的前提，**保持现状，禁止新增跨 svc 依赖**。

2. **权限门控体系未收口（P1-1 + P2 系列）**：master-data 全量 `:admin` 精确门控（业务角色全 403 且迁移承诺未落地）、portal REST 休眠门控、srm 全量 `:admin` 粗粒度、analytics `:admin` 覆盖只读路由过严 ——`require_module_access`/`require_permission` 两层体系并存且各服务口径不一（精确 vs 前缀），**建议统一为模块访问 + 写操作细分权限的两层模型**，并以 permission-matrix-guard 测试（已存在，前端测试已抓到 R2 偏差）为门禁。

3. **嵌入 /standalone 双形态契约漂移（P2 系列）**：字段加密（嵌入恒 None vs 单例真初始化）、permissions 写路由（standalone 入 public\_routes 无 auth vs 嵌入整体丢弃）、MCP resources 注册（仅 stdio 二进制）—— 同一服务两种部署形态行为不一致，需以 feature 门禁测试锁住差异。

4. **桩 / 虚构数据仍在上线路径（P1 系列）**：hrm 发薪编造、monitor 阈值 / 快照虚构、finance report\_center 掺假报表、analytics 30 个 KPI 硬编码、mes 能耗合成、mobile 条码假物品 ——"桩已去硬编码" 专项只覆盖了部分模块，**建议全仓桩清点按 "落库实现 / 明确下线 / 带 degraded 标记" 三选一收口**。

5. **租户隔离纵深不足**：多数服务读路径依赖 GUC-RLS 单层（WMS 硬编码租户、qms body tenant\_id、PM/SEARCH/GIS 无显式条件、analytics GUC 名错配）。RLS 静态覆盖良好（463 SQL validate 0 error、817 表 RLS ON），但**应用层显式 tenant 条件应作为纵深补上**，且 GUC 名（app.tenant\_id vs app.current\_tenant）必须与迁移策略统一。

6. **工程基建门禁存在 "本地绿 CI 红" 风险**：clippy 本地 `-D correctness` vs CI `-D warnings`；gitleaks 规则生成顺序错误；e2e 无后端启动；迁移版本号重复已实际阻断 CI；cargo deny licenses 红 ——**本轮发现的 4 项门禁不一致需先于业务修复处理**。

7. **配置管理**：.env 已被 git 忽略（无泄漏）；但 30+ 环境变量未进 .env.example、双配置层并存、enhanced.rs 硬编码开发 DSN 兜底、守卫脚本明文回显连接串（P3）—— 建议收敛为单一配置源并脱敏日志。
