### 渲染层（`GlobalLayoutV3.tsx`）

## 五、DB 种子同步与对账归零

### 迁移 `20261107000025_seed_menus_batch29.sql`

平台级（tenant `00000000-0000-0000-0000-000000000000`）种子：

| 动作 | 数量 |
|---|---|
| 补齐菜单组（`ON CONFLICT DO NOTHING`） | 77 新增（共 94 组，17 已存在） |
| 补种菜单项（`ON CONFLICT (tenant_id, code) DO UPDATE`） | 267 |
| path 对齐（`mes-work-stations`） | 1 |
| 历史清理（软删重复登记 `mes-work-orders`、失效路由 `scm-contracts`） | 2 |

平台级 core_menus：**184 → 449**（与前端 navItems 449 完全一致）。

**permission 口径**：补种植入的是前端 navItems 的**真实 `permission` 字段值**（如 `admin:audit:read`），不是占位。仅 1 项（`hrm-setup`）前端本身无 permission 字段，回退 `hrm:read`，与前端实际守卫行为一致。

**幂等验证**：连续执行两遍，第二遍 `INSERT 0 267`（全部走 DO UPDATE，零新增）、`UPDATE 0`，行数不变 449。

### 为什么补种不会让已下沉项重新出现

`GlobalLayoutV3` 在 `dbMenus` 存在时按 `Boolean(dbItem) && dbItem?.visible !== false` 过滤，但该过滤作用于 `navigationRegistryV2.getSidebarNavItems()` 的返回值，而后者已在注册表层执行 `.filter(item => item.showInSidebar !== false)`（`NavigationRegistryV2.ts:152`）。**下沉发生在注册表层，早于 DB 过滤，DB 补种无法绕开。**

`core_menus` 无 `visible` 列，侧栏可见性的唯一真源是 `navItems.showInSidebar`。
