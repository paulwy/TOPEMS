## 二、根因链（完整取证）

### 2.1 RLS 策略形态

`public` schema 下 590 张表启用 RLS，policy 形态为：

```sql
tenant_id::text = NULLIF(current_setting('app.tenant_id'),'')::text
  OR tenant_id IS NULL
  OR NULLIF(current_setting('app.tenant_id'),'') = '00000000-0000-0000-0000-000000000000'
```

`app.tenant_id` 为空时三个分支**全部不成立** → 恒 0 行。业务 SQL 里写得多正确的 `WHERE tenant_id = $1` 都无法挽回——RLS 在 SQL 层之外独立过滤。

### 2.2 为什么是裸池

`DocumentService` 持 `state.pool.clone()`，五个方法全部 `.fetch_all(&self.pool)` / `.fetch_one(&self.pool)` / `.execute(&self.pool)`。裸池每次查询从池里**随机借一条连接**。

### 2.3 为什么中间件救不了

`svc/unified-core/src/middleware/tenant_rls.rs:237` 的 `tenant_rls_middleware`（挂在 `routes/mod.rs:268`）做的是：

- `state.pool.acquire()` **独占一条连接**
- 在该连接上做**会话级** `set_config('app.tenant_id', $1, false)`
- 只把 `TenantId` 塞进 extensions，**不注入连接本身**
- 请求结束在同一连接 `RESET` 后 drop 归还

业务代码后续再 `&self.pool` 会借到**另一条**连接 → 会话级 GUC 不会被继承。

### 2.4 为什么不能改 after_connect（用户明令禁止）

`lib/shared-db/src/database/mod.rs:96-137` 的 `after_connect` 仅当 `default_tenant` 为 `Some` 且非多租户时才 `set_config('app.tenant_id', …, false)`。当前 `.env`（`MULTI_TENANT_ENABLED=true` + `DEFAULT_TENANT_ID=…0001`）下 `default_tenant = None` → 连接基线从不设 GUC。

在此处设 baseline 租户会让**所有**连接带上同一租户，破坏多租户隔离——属错误修法，已排除。

## 三、修复方案与范式

### 3.1 已确立范式（照抄既有，不新造）

参照 `svc/portal/src/modules/todos.rs` 的 `RequestTxn` + `Db::scope_with`，以及 `lib/shared-auth/src/middleware/tenant.rs` 普通用户分支的 `pool.begin()` + `set_config(..., true)`，采用**业务方法内部自开请求级事务**：

```rust
async fn tenant_txn(&self, tenant_id: Option<Uuid>) -> Result<Transaction<'static, Postgres>> {
    let mut tx = self.pool.begin().await?;
    let rls_tenant = tenant_id
        .map(|t| t.to_string())
        .unwrap_or_else(|| Uuid::nil().to_string());
    sqlx::query("SELECT set_config('app.tenant_id', $1, true)")   // true = SET LOCAL / 事务级
        .bind(rls_tenant)
        .execute(&mut *tx)
        .await?;
    Ok(tx)
}
```

- **普通用户**传真实 tenant_id → 命中 `tenant_id = current_setting('app.tenant_id')` 分支
- **superadmin / 无租户**传 `Uuid::nil()` → 命中全零旁路分支，可跨租户管理
- 每个方法：`let mut tx = self.tenant_txn(...).await?;` → 查询走 `&mut *tx` → `tx.commit().await?;`
- 事务级 GUC 随事务绑定连接，后续所有语句必然继承

### 3.2 修复清单（14 个方法 + 4 个 helper）

| # | 位置 | 方法 | 访问表 |
|---|---|---|---|
| 1-5 | `services/document.rs` | list / get / create / update / delete | `core_doc_documents` |
| 6-10 | `services/folder.rs` | list / get / create / update / delete | `core_doc_folders` |
| 11-16 | `services/template.rs` | list / get / create / update / delete / list_categories | `core_doc_templates` |
| 17 | `handlers.rs` `get_dashboard_handler` | 单事务内 9 个 count | documents / folders / templates |
| 18-20 | `handlers.rs` | list_document_versions / get_document_version / restore_document_version | `core_doc_document_versions`（读+写同事务） |

配套改造：4 个 count helper 签名由 `&PgPool` 改为 `&mut PgConnection`，返回 `Result<i64, sqlx::Error>`。

### 3.3 顺带修复的降级口径缺陷

原 helper 的错误处理是 `Err(_) => 0` —— 把数据库错误**静默伪装成"真实空结果"**。这属审计口径禁止的降级做法（"把降级态伪装成真实空结果"）。

改造后错误通过 `?` 向上传播，handler 侧 `tracing::error!` 记录并返回 `ApiResponse::server_error("仪表盘统计失败")`，不再伪装。

### 3.4 顺带修复的既有缺列缺陷

`FolderService` 的两处 SELECT 列与 `Folder` 模型不匹配（模型有 `sort_order` / `is_enabled`，SELECT 里没有；SELECT 里反而多了模型不存在的 `deleted_at`）。

这一缺陷**一直被 fail-closed 掩盖**——裸池下恒 0 行，没有行可以解析，`FromRow` 从不报错，列表永远"正常"返回空。修复后有了真实数据，`FromRow` 立即报缺列 → 500。已补全为模型全部 10 个字段（`deleted_at` 仅保留在 `WHERE` 条件里）。

**这条是本批最有价值的副产品**：fail-closed 不仅让功能不可用，还掩盖了下游的真实缺陷。

## 四、权威载体定案（批 41 悬案关闭）

批 41 遗留疑问："`public.core_doc_documents` 是否为权威载体"，已知 `flow` / `doc_service` 下有同名空表。

**本批判定性实验**：用 A 用户创建文档后立即查三张表——

| schema | 该文档行数 | RLS |
|---|---|---|
| `public` | 0 | 启用 |
| `flow` | **1** | 启用 |
| `doc_service` | 0 | **未启用** |

**结论**：doc 模块真实载体是 **`flow.core_doc_documents`**，`public` 与 `doc_service` 是影子空表。

**机制**：`svc/unified-core/src/embedded.rs:50`

```rust
std::env::set_var("SEARCH_PATH", "flow, public");
```

嵌入模式下 unified-core 的 search_path 被固化为 `flow, public`（注释原文："flow 业务表为权威……避免无前缀查询误命中 public 影子表（历史 500 根因）"）。无前缀的 `core_doc_documents` 因此解析到 `flow`。

**修正批 41 表述**：fail-closed 定性正确（`flow` 表确实启用 RLS），但"权威载体是 public"的假设错误。
