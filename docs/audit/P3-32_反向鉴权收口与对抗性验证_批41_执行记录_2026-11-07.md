## 一、问题定性（为什么批 40 的"已覆盖"仍留裸奔面）

批 40 把 702 条真实裸奔收敛到 328→0，但收口口径存在三类结构性漏洞，本批逐一闭合：

1. **分组兜底残留**：unified-core `doc/handlers.rs:626` 的 `create_routes()` 分 read/write/admin/dashboard
   四组挂码，剩余 `rest` 组保持 auth-only。`GET /templates`（`list_templates`）就在 `rest` 里，
   批 40 实测对无码用户返回 **200** —— 是"分组漏归"而非"判定漏判"。
2. **语义错位**：portal `monitoring.rs` 5 个 handler（`get_monitoring_services:43`、`get_monitoring_metrics:98`、
   `get_monitoring_alerts:168`、`acknowledge_alert:221`、`get_monitoring_logs:236`）**全部没有 Claims 参数**，
   纯转发 monitor 服务并在失败时降级返回空列表，语义是**系统运维面**，却被挂在 `personal_routes`
   （个人自服务面，仅 auth 兜底）。用户要求"4 条"，实际代码是 **5 条**（含 `POST /monitoring/alerts/{id}` 确认告警），
   本批按 5 条全部处置并在此登记差异。
3. **网关兜底误判**：finance 14 个小文件的判定依据是"依托网关层 `require_finance_write` 兜底"。
   **该门只拦非 GET** —— 对 GET 而言网关层直接放行，即"兜底"在 GET 上恒不成立。
   这是批 40 §6 第①项登记为"未逐条复核"的部分，本批机器化跨行解析后确认为**真裸奔**。

## 二、取证方法与口径

- **doc 侧**：`svc/unified-core/src/routes/doc.rs` 仅 14 行，`doc_routes(state)` → `Router::new().nest("/doc", modules::doc::create_routes(state))`；
  真实路由表在 `modules/doc/handlers.rs:626` 的 `create_routes()`。按 handler 职能与资源语义逐条归类，
  **不按路径前缀拍脑袋**（批 40 曾因把 `finance:report:read` 挂成 mod.rs 全局基线层导致 `/vouchers` 要求"报表"码，被返工）。
- **portal monitoring**：逐个 handler 读签名确认无 Claims、读实现确认是纯转发 + 降级空列表（运维面特征），
  再确认调用方（前端运维面板而非个人中心）。
- **finance 小文件**：单行 `grep get(` 计数会把 handler 内 DB `.get()` 也算进去，**不可作端点数依据**；
  改用跨行 route 声明解析（`route(` 到 `)` 的括号平衡配对）逐文件枚举，14 文件 `require_permission` 出现次数原为 **0**。
- **权限码唯一性**：`require_permission`（`lib/shared-auth/src/middleware/permission.rs:29`）是**精确串匹配、不做前缀/通配**，
  且只读 JWT `permissions` 字段、**不查 DB** —— 因此新挂的码必须已存在于 `core_permissions`，缺则走幂等迁移补建。

## 五、过程中发现并处置的两个既有缺陷

### 5.1 portal todos 类型错配（**本批已修复**）

- **现象**：`GET /api/portal/todos` 对任何用户都只返回「欢迎使用 TOPEMS 门户」「完善个人资料」两张卡片，
  真实待办一条都查不出来。
- **根因**：`portal.portal_todos.user_id` 是 **`varchar`**，而 `svc/portal/src/modules/todos.rs` 的 SQL 写成
  `user_id = $1::uuid`（:48 列表）、`user_id = $2::uuid`（:199 完成、:245 删除）。
  PostgreSQL 报 `operator does not exist: character varying = uuid` → 查询 `Err` → 走 `default_todos()` 硬编码兜底。
  DB 直连复现该错误确认。
- **修复**：3 处改为 `user_id = $1` / `user_id = $2`（varchar 直接比较，避免 `::uuid` 在脏数据上抛错）；
  `:147` 的 `VALUES ($1::uuid, …)` **保留**（那是 INSERT 的 `id`，列本就是 uuid，正确）。
- **复测**：A token 只见 `B41 A-user todo`、B token 只见 `B41 B-user todo`，跨租户隔离同时成立。
- **影响面**：portal 个人待办功能此前**整体不可用**（本次对抗性验证因需要可信载体才暴露）。

### 5.2 doc 模块 fail-closed（**本批只定性未修，登记为后续批次**）

- **根因链**：`lib/shared-db/src/database/mod.rs:96-137` 的 `after_connect` 仅在 `default_tenant` 为 `Some`
  且**非多租户**时才 `set_config('app.tenant_id', …, false)`；当前 `.env` 是 `MULTI_TENANT_ENABLED=true`
  \+ `DEFAULT_TENANT_ID=…0001` 组合 → `default_tenant = None` → 连接基线从不设租户 GUC。
  而 `DocumentService` 直接持 `state.pool.clone()` 的原生池、**不走 `Db::scope` 请求级事务** → GUC 恒空 →
  RLS 过滤掉全部非 nil 租户行。
- **表现**：任何身份（含 superadmin）`GET /api/core/doc/documents*` 恒 `data:null` / `data:[]`。
- **不修原因**：属既有缺陷、不在本批授权范围；修法涉及 `lib/shared-db` 与 unified-core 两侧改动面，
  需单独评估（让 `DocumentService` 改走 `Db::scope` 会影响所有 doc 数据路径）。**不隐瞒、不假修**。
