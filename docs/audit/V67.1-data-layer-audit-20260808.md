## 🔴 二、P0 关键问题（5 项 — 数据一致性/合规/运行时错误）

### P0-1 审计日志覆盖率仅 25%，合规关键服务全缺失
- **严重度**: 🔴 P0（合规 + 安全）
- **证据**: `audit_log.rs` 模型仅存在于 crm/erp/hrm/rd/scm/srm/wms = **7 个服务**；缺失 21 个：ai / analytics / billing / communication / ehs / feedback / **finance** / gis / integration / lims / lowcode / master-data / **mes** / mobile / pdm / **pm** / portal / qms / search / ticket / unified-core
- **风险**: finance（财务凭证篡改无迹）、mes（工单修改无迹）、pm（项目里程碑变更无迹）、qms/lims（质量/检测数据合规审计空白）、ehs（安全事件记录缺失）→ 财务/GDPR/ISO 合规不达标
- **修复建议**: 
  1. shared-bootstrap/audit.rs 通用审计模块直接复用（现有模板已写）
  2. 1 个批量 PR：为缺的 21 服务各加 `audit_log.rs` + 路由 + 3 标准触发器（C/U/D）

### P0-2 ApprovalStatus 枚举 5 处独立定义，变体 3~6 个互不兼容
- **严重度**: 🔴 P0（跨服务反序列化失败）
- **证据**（至少 5 个不同定义点）：
  | 位置 | 文件 | 变体数 | 变体 |
  |---|---|---|---|
  | shared-core | [common_types.rs](file:///Users/xingzhai/TOPEMS/lib/shared-core/src/common_types.rs#L19-L26) | 6 | Pending, Approved, Rejected, InProgress, Cancelled, Expired |
  | unified-core | [master/models.rs](file:///Users/xingzhai/TOPEMS/svc/unified-core/src/modules/master/models.rs#L351) | ? | 独立定义，未用 shared |
  | portal | [query_governance.rs](file:///Users/xingzhai/TOPEMS/svc/portal/src/modules/query_governance.rs#L207) | ? | 独立定义，未用 shared |
  | srm | `supplier_evaluation.rs` | 2 | Only Approved/Rejected（缺 Pending 等 4） |
  | rd | `modules/project.rs` | 3 | 与 shared 近似但类型不同 |
- **风险**: 跨服务事件（ERP 采购单→SRM 供应商准入→PM 项目立项）传递审批状态时：SRM `serde_json::from_str<ApprovalStatus>("pending")` → **Err: unknown variant**，导致审批流中断
- **修复建议**:
  1. 全网 grep 替换 `pub enum ApprovalStatus` → `pub use topems_shared_core::common_types::ApprovalStatus;`
  2. SRM 若确需子集，用 `#[serde(other)]` 或新类型包裹，不要重新定义 enum

### P0-3 迁移校验和与登记清单双失配
- **严重度**: 🔴 P0（生产/UAT 漂移）
- **证据**:
  - 实际迁移 SQL：`database/migrations (25) + svc/*/migrations (126) = 151 个`
  - `database/checksums.txt` 注册条目（非空/非注释行）：**142**
  - → **9 个迁移存在未注册 checksum**（生产迁移器校验失败将拒绝执行）
  - `docs/development/migration-inventory.md` 登记条目：**26 / 151 ≈ 17%**（83% 的迁移没有文档登记）
- **风险**: 新环境 `verify-migration.sh` 校验失败；开发新增迁移忘了补 checksum → UAT 过了生产挂
- **修复建议**:
  1. 跑一次 `topems-migrate rebuild-checksums`（若 CLI 支持）补 9 条记录
  2. CI 钩子：`git diff --name-only -- *migrations*.sql` 非空时强制更新 inventory

### P0-4 三元长度不匹配：SQL VARCHAR(n) vs Rust 无限制 vs 前端无校验
- **严重度**: 🔴 P0（用户体验/错误时序）
- **证据**（以 Employee 为代表，全局 >200 字段类似）：
  | 字段 | SQL ([hrm_schema.sql](file:///Users/xingzhai/TOPEMS/svc/hrm/migrations/20260608100000_create_hrm_schema.sql)) | Rust ([employee.rs](file:///Users/xingzhai/TOPEMS/svc/hrm/src/models/employee.rs)) | 前端 EntitySchema ([employee.ts](file:///Users/xingzhai/TOPEMS/apps/web/src/schemas/hrm/employee.ts)) |
  |---|---|---|---|
  | employee_number | `VARCHAR(50)` | `String` | `{type:'text'}` — **无 maxLength** |
  | name | `VARCHAR(255)` | `String` | **无 maxLength** |
  | gender | `VARCHAR(20)` | `Option<String>` | **无 maxLength** |
  | id_card_number | `VARCHAR(50)` | — | **无 maxLength** |
  | email | `VARCHAR(100)` | — | **无 maxLength** |
  | phone | `VARCHAR(50)` | — | **无 maxLength** |
- **风险**: 用户在表单里输入 200 字符的 employee_number，前端通过、Rust 通过，入库时报 `value too long for type character varying(50)` → **500 Internal Error**，用户无法判断哪里出问题
- **修复建议**: EntitySchema 的 `SchemaField.validation` 加 `{ type: 'maxLength', value: <SQL值> }`；或从 migration SQL 反向生成字段约束

### P0-5 种子时序依赖 012-menu.sql，执行顺序脆弱
- **严重度**: 🔴 P0（首次部署失败）
- **证据**:
  - [000004_seed_module_permissions.sql](file:///Users/xingzhai/TOPEMS/database/migrations/20260724000004_seed_module_permissions.sql) 引用表 `core_roles` → 定义在 001-iam.sql（序号 1 ✅）
  - [000005_seed_module_menus.sql](file:///Users/xingzhai/TOPEMS/database/migrations/20260724000005_seed_module_menus.sql) 引用表 `core_menus` / `core_menu_groups` → **定义在 012-menu.sql（序号 12）**
  - `database/migrations` 命名规则混用：`012-menu.sql`（编号前缀） vs `20260724000005_...sql`（日期前缀）
- **风险**: 如果迁移执行器按"日期段 first vs 编号段 first"分阶段执行，或者按时间戳数字位排序而非字典序，就会出现 `20260724000005 > 012` → 种子在菜单表之前运行 → `relation "core_menus" does not exist` 安装失败
- **修复建议**: 25 个全局迁移统一改为 YYYYMMDD 时间戳；把 001~013 重命名为 `20260601000001_iam.sql` … `20260601000013_login_log.sql`，保证全局字典序 = 时序序

## 🟠 三、P1 重要问题（6 项）

### P1-1 add_tenant_id 27 个独立迁移文件重复逻辑
- **证据**: `add_tenant_id` 类迁移 27 份，分布 21 服务；ehs/qms/pm/gis 各有 2 次（6 月 29 日旧版 + 7 月 10 日新版重复）
- **问题**: 每一份 copy-paste 都要重复写 `ALTER TABLE x ADD COLUMN tenant_id UUID NOT NULL` + `CREATE INDEX` + `RLS POLICY`；一份写错全局不一致
- **建议**: 用 migration-generator 的模板批量生成，并在 shared-db/migration.rs 内提供 `apply_tenant_id(&mut conn, schema, tables)` 函数

### P1-2 全局迁移两套命名体系混用
- **证据**: database/migrations = 13 个"编号式"（001-iam~013-login-log）+ 12 个"日期式"（202607xxxx...）
- **建议**: 按 P0-5 统一重命名

### P1-3 MES 单日 8 个"补漏式"碎片 DDL
- **证据**: svc/mes/migrations 20260709 000002~000012 时间戳 8 个文件：add_missing_tables × 2 / add_missing_columns × 2 / fix_missing_columns / add_more_tables / add_effective_date / add_result_column / add_quality_columns
- **问题**: 说明开发阶段 schema 未经评审迭代式 commit 到 main，一天改 8 次；迁移数量膨胀，CI 迁移测试时间长
- **建议**: 开发期用 WIP 临时 migration（带 `_wip` 后缀，合 main 前合并）+ PR template 里 checklist 要求"迁移合并 + checksum 更新 + inventory 登记"

### P1-4 软删除三模式混用（deleted_at / is_deleted / status）
- **证据**: 统计表有 deleted_at 22 处；is_deleted 2 处；status 字段 91 处（常被用作 status = -1 / archived 表示删除）
- **问题**: 前端 `useCrudQueries` 默认过滤必须同时兼容三种，否则偶尔"列表里还看得到已删记录"
- **建议**: shared-core 新增 `SoftDeleteMode` 枚举 + 宏统一生成 WHERE 条件；短期统一采用 `deleted_at TIMESTAMPTZ`（业界通用）

### P1-5 EntitySchema 缺 maxLength 导致 P0-4 大规模发生
- **证据**: P0-4 是 Employee 抽样，其余 ~20 模块同样如此；EntitySchema 的 SchemaField 数组支持 `validation.maxLength` 但几乎无人填写
- **建议**: 写一个 30 行脚本扫描最新 migration CREATE TABLE，与 EntitySchema fields 比较，自动生成 PR 添加缺失的 maxLength

### P1-6 add_tenant_id 时序错位（6 月 29 日 / 7 月 6 日 / 7 月 9 日 / 7 月 10 日 / 7 月 14 日 / 7 月 17 日 6 批）
- **证据**: hrm/ehs/qms 先在 0629 打补丁，大部分在 0710 打补丁，unified-core 等到 0717 才修。同一租户隔离能力跨越 3 周补齐
- **建议**: 以后这种全局特性必须在"所有服务同一日迁移 + 全局 PR 一起合并"，避免新老服务混合运行时出现跨服务查询 RLS 不等价

## 📐 六、架构改进建议（中期路线）

1. **建立 Schema 单一真相源（SOT）**：用 `sqlx` 或 migration-generator CLI 先定义 `.proto`/`.yaml`，同时生成 ① SQL 迁移 ② Rust Model derive ③ 前端 Zod Schema → 从源头消除三元不一致
2. **建立 Enums 单一真相源**：shared-core/ `common_types.rs` 扩展所有服务使用的枚举（Priority / OrderStatus / TicketStatus ...），全网禁止 `pub enum` 重名；CI 跑 grep `pub enum` 做门禁
3. **审计日志内建 shared-bootstrap**：新服务默认含 audit_log 表 + 路由 + C/U/D 自动打点；老服务 21 个按 P0-1 安排一个批量 PR
4. **迁移命名统一 + 门禁**：统一 YYYYMMDDNNNNNN_xxx.sql 格式；CI 对比 `wc -l checksums.txt` vs `find . -name '*.sql' | wc -l` 防止新增迁移漏改 checksum
5. **软删除策略 RFC**：投票定统一方式（建议 deleted_at + RLS）；迁移脚本把 is_deleted/status=-1 老表迁移过去
