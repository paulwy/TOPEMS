## 一、`erp:vouchers`：确认打 finance → 改 `api.module` + 接入 `finance:voucher`

批 18 因"改 module 可能动请求路径"而停手。本批把调用链完整取证，结论是**可以安全改**。

### 1.1 取证链（A→B→C 三层闭合）

| 层 | 证据（文件:行号） | 结论 |
|---|---|---|
| ① schema 的 api 声明 | `apps/web/src/schemas/erp/voucher.ts:142-145` `api: { module: 'erp', resource: 'vouchers' }` | 声明写着 erp |
| ② schema 实际调用的 API 模块 | `apps/web/src/schemas/erp/voucher.ts:14` `import { voucherApi } from '@/api/finance/voucher'` | 数据走 **finance** 模块 |
| ③ API 实现的真实 baseURL | `apps/web/src/api/finance/voucher.ts:25,51,57,74,88,94,108,123` 全部 `apiClient.finance.get/post('/vouchers' …)` | 实际请求 **`/api/finance/vouchers`** |
| ④ 后端 erp 侧路由 | `grep -rn "vouchers" svc/erp/src` 仅命中 `main.rs:35`（prometheus gauge `topems_erp_voucher_count`）、`main.rs:283`（`SELECT COUNT(*) FROM financial_vouchers`）、`schema_defense.rs:339`（表名） | **不存在 `/api/erp/vouchers` 路由** |
| ⑤ `api.module` 的运行时用途 | `grep -rn "api\.module" apps/web/src --include=*.ts --include=*.tsx`（排除测试）**返回空** | 该字段**无任何运行时引用** |
| ⑥ CrudPage 的数据通道 | `CrudPage.tsx:504/521/545/569` 全部走 `apiAdapter.list/create/update/delete` | 请求路径由页面传入的 adapter 决定，`api.module` 不参与拼装 |
| ⑦ 对账脚本口径 | `scripts/audit_permission_codes.py:30` 为 `SKIP_MARKERS` + 正则扫字面权限码；`grep -n "api"` 无字段读取 | 改 `api.module` **不影响 fe/be/db 对账基线** |

**结论**：`api.module: 'erp'` 是纯声明错配（历史遗留：schema 放在 `schemas/erp/` 目录但数据走 finance），改它既不改请求路径，也不改任何权限判定，只是让声明与事实一致。

### 1.2 改动

```ts
// apps/web/src/schemas/erp/voucher.ts:142
api: {
  // 批 19 订正：本页面数据全部经 @/api/finance/voucher（apiClient.finance.get('/vouchers')），
  // 实际请求打 finance 服务，原 module: 'erp' 是错误声明（api.module 在 FE 无运行时引用，仅声明）。
  module: 'finance',
  resource: 'vouchers',
},

// 批 19：写权限资源前缀（凭证主数据归 finance 域，复用既有 finance:voucher 四码）
permissionResource: 'finance:voucher',
```

**文件位置未移动**：`schemas/erp/voucher.ts` 仍在 erp 目录（移动会破坏 5 处 import），只订正声明；目录错位登记为后续整理项。

**为何不复用 erp 侧码**：`erp` 模块的 DB 资源名清单中无 `voucher`（见批 17 盘点），补 `erp:voucher:*` 会与既有 `finance:voucher:{create,update,delete,write}` 形成同义双码，违反批 2 的收敛方向。

**不回归验证**：改后 `pnpm --filter topems-portal typecheck` 0 error、eslint 0 error、全量 vitest 624/6669 全通过；请求路径由 `@/api/finance/voucher` 硬编码，与 `api.module` 无耦合（证据⑥）。

### 2.1 建码依据（`tenant:member:{update,delete}`）

- 前端：`apps/web/src/api/tenant/index.ts:20` `const API_BASE = '/tenant'`，经 `apiClient.core` 调用（打 unified-core 的 tenant 模块）
- 后端 handler 真实存在：`svc/unified-core/src/modules/tenant/handlers.rs:1030` `remove_member`、`:1057` `update_member_role`
- **不建 `tenant:member:create`**：UI 的 `create` 适配器为空实现（新建成员走页面自有 Button + 另一接口），CrudPage 侧无真实 create 写路径 → 不造无依据码。副作用：接入后 CrudPage 不显示"新建成员"按钮，正好消除一个点击无效的僵尸入口。

### 2.2 迁移 `20261107000009_tenant_member_resource_codes.sql`

- 2 码：`tenant:member:update`、`tenant:member:delete`，`[batch19]` 标记 + ROLLBACK 段
- 授权：admin / superadmin 各 2（tenant 域无 manager 角色，租户成员管理属平台运营操作）
- 幂等：首次 `INSERT 0 2` + `INSERT 0 4`，二次 `INSERT 0 0` / `INSERT 0 0`
- DB `core_permissions`：1229 → **1231**

### 2.3 接入

`schemas/admin/tenantUser.ts` 加 `permissionResource: 'tenant:member'`（页面零改动）。
CrudPage 解析结果：`update`/`delete` 有码 → 按钮按权限显示；`create` 无码 → 隐藏（符合实际）。

## 三、`admin:auditLogs`：维持只读不接入

- `schemas/admin/auditLog.ts` 对应审计日志查询页，**无 create/update/delete 操作**（只读列表 + 导出）。
- CrudPage 不传 `permissionResource` 时不过滤（存量行为不变），读权限由路由/菜单层控制。
- 结论：**维持只读，不做写权限接入**。理由：接入会要求三个写码，而该页面不存在任何写路径，强行建码即"无依据造码"。
