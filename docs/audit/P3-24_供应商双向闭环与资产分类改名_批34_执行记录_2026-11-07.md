**但两列实际值全为 `false`——管道建成后从未跑过。** 本批不启用那条，只在 mdm 侧新增，理由见 §9.3。

### 2.2 设计

| 方向 | 实现 |
|---|---|
| mdm → scm/srm | `create_supplier` / `update_supplier` / `delete_supplier` **主写入提交后**，`tokio::spawn` 后台按 `(supplier_no, tenant_id)` `ON CONFLICT` upsert；软删对应 `UPDATE deleted_at = now()` |
| scm/srm → mdm | 下游对应 CRUD 写完后 `tokio::spawn`，读本行 upsert 到 `mdm_suppliers`，`source_system='scm'/'srm'`、`source_id`=下游行 id |

**四项硬性要求逐项落实：**

| 要求 | 实现 |
|---|---|
| **不阻塞主写入** | 同步全在 `tokio::spawn`，主请求先落库并返回；同步失败只 `tracing::warn!` + 写死信表，**绝不改主请求状态码** |
| **幂等** | `(supplier_no, tenant_id)` 作 upsert 键，`ON CONFLICT DO UPDATE`；`supplier_no` 为 NULL 的行跳过（mdm 有 NOT NULL 约束） |
| **失败可追踪** | 新建 `master_data.mdm_sync_dead_letter`（迁移 `20261107000033`），字段 `entity_type` / `entity_key` / `direction` / `operation` / `error_message` / `payload` jsonb / `retry_count` / `tenant_id` / `resolved_at`，RLS 照抄 `mdm_suppliers` 策略 |
| **防环** | ① 所有同步**直接写库、不调对方 HTTP API** → 不会触发对方写端点回写；② `ON CONFLICT DO UPDATE` 用 `CASE WHEN source_system='mdm' THEN 'mdm' ELSE EXCLUDED END` 保护 mdm 自建行；③ 软删同步加 `source_system IS DISTINCT FROM 'mdm'` 条件 |

### 2.3 `scripts/schema_boundary.json`

mdm 服务跨 schema 写 `scm`/`srm` 表会触发边界门禁，因此：

- `master-data` allow 增加 `["scm","srm"]`
- `scm` 增加 `["master_data"]`、`srm` 增加 `["master_data"]`
- `python3 scripts/check_schema_boundary.py` → **全 PASS exit 0**

## 三、`category` 三表语义分裂（本批最关键的隐蔽缺陷）

### 3.1 问题定性

这是**前端切 mdm 时才暴露出来的**，但根因在后端同步管道：

| 表 | `category` 语义 | 约束 |
|---|---|---|
| `scm.suppliers` | **标准码**（`raw_material`） | nullable=YES |
| `srm.suppliers` | **中文名**（`原材料`） | **NOT NULL，无 default** |
| `master_data.mdm_suppliers` | 自由文本（历史遗留） | 可为 NULL |

**故障链**：mdm 新建供应商时若只传 `category_code='raw_material'` 而不传 `category` →
- 同步到 scm **成功**（可 NULL）
- 同步到 **srm 失败**（NOT NULL 违反）→ 写死信表 → **该供应商在 srm 缺失**

这直接破坏「双向闭环可用」。

### 3.2 为什么不能靠前端补丁

前端 agent 曾加过一层临时补丁（api 层从字典补 `category` 中文），但它**只覆盖前端新建路径**——直接调 API、任何非前端写入路径仍会失败。所以必须在同步管道修根因。

### 3.3 修法：用 `source_values` 做双向翻译

`master_data.mdm_supplier_categories.source_values` 本来就存着这个映射：

```json
{"scm": "raw_material", "srm": "原材料"}
```

实现：

| 方向 | 表达式 |
|---|---|
| mdm → scm | `COALESCE(source_values->>'scm' WHERE code=category_code, mdm.category, NULL)` |
| mdm → srm | `COALESCE(source_values->>'srm' WHERE code=category_code, mdm.category, '')` ← **空串兜住 NOT NULL** |
| scm → mdm | `code WHERE source_values->>'scm' = scm.category`；查不到 → `category_code=NULL` |
| srm → mdm | `code WHERE source_values->>'srm' = srm.category`；查不到 → `category_code=NULL` |

**不猜、不硬编码**：查不到映射就把 `category_code` 留 `NULL`，把源表 `category` 原值写入 `mdm.category` 供追溯。

**性能**：字典只有 1 行，`load_category_dict()` 一次性加载进 `HashMap<code,(scm_val,srm_val)>`，不每条查库。

### 5.2 5 页切换明细

| 页面 | 原数据源 | 切换后 | 机制 |
|---|---|---|---|
| `pages/scm/ScmSupplierPage.tsx` | `scmApi.suppliers` | `masterDataApi.suppliers` | `createCrudPageAdapter` |
| `pages/srm/SrmSupplierPage.tsx` | `srmApi.list/create/update/deleteSupplier` | `masterDataApi.suppliers` | 4 方法显式替换 |
| `pages/srm/SrmSupplierDetailPage.tsx` | `srmApi.getSupplier(id)` | `masterDataApi.suppliers.get(id)` | `useQuery` queryFn |
| `pages/erp/SupplierManagementPage.tsx` | `erpApi.suppliers`（`itemsField:'suppliers'`） | `masterDataApi.suppliers` | `createCrudPageAdapter`，**去掉 itemsField 覆盖** |
| `pages/wms/SupplierManagementPage.tsx` | `scmApi.suppliers` | `masterDataApi.suppliers` | `createCrudPageAdapter` |

### 5.3 三处必须处理的技术点

1. **信封差异**：mdm list 返回 `{items, total, page, page_size}`，与 scm/srm/erp 老信封都不同 → 统一吃 `data.items`（原 erp 页的 `itemsField='suppliers'` 必须去掉，否则恒空）
2. **软删语义**：mdm `DELETE` 是软删 → 删后 list 不再出现、`GET :id` 返回 404 「未找到: 供应商不存在」。页面删除后刷新行为与此对齐
3. **权限模型不动**：`permissionResource` / 路由 / 菜单保持原样——**切数据源不改变权限**，沿用 `master-data` 模块门

### 5.4 空列清理（一步到位）

切权威源后，原 schema 里有些字段 mdm **根本不返回**，会在列表里显示一整排空列。判据是「**这一列的数据来自哪里？答不出来就删**」：

- `schemas/erp/supplier.ts`：删 `short_name` / `country` / `province` / `city` / `zip_code`
- `schemas/wms/supplier.ts`：删 `short_name`

### 5.5 字段名对齐 mdm（原先会静默丢弃）

| schema | 原字段名 | 改为 |
|---|---|---|
| `scm` / `wms` | `contact_name` / `contact_phone` / `tax_number` | `contact_person` / `phone` / `tax_id` |
| `srm` | `risklevel` / `category` | `risk_level` / `category_code` |
| `erp` | `supplier_code` / `supplier_name` / `contact_email` / `remark` | `supplier_no` / `name` / `email` / `remarks` |

这些字段名与 mdm 端点不匹配时**会被后端静默忽略**——用户以为改了，实际没生效。
