## 二、供应商主数据权威源建设（迁移 `0029` 建表 + `0030` 导入）

### 背景

批 31 把全局搜索的供应商段改为 `scm.suppliers ∪ srm.suppliers` 的 `UNION ALL` + `ROW_NUMBER` 去重（scm 优先），属于**临时兜底方案**——数据分散在两个源表、每次查询都要跨 schema 拼接去重。本批建立统一权威源。

### 命名与位置

`master_data` schema 已有 0 张 supplier 表；同 schema 的 `mdm_*` 表全部 `relrowsecurity=t` + `relforcerowsecurity=t`。新表定名 **`master_data.mdm_suppliers`**，与既有命名惯例一致。

### 表结构（25 列，两源并集业务必要字段）

核心业务列：`id` uuid PK default `gen_random_uuid()`、`supplier_no` varchar NOT NULL、`name` varchar NOT NULL、`legal_name`、`category`、`status` varchar NOT NULL、`tax_id`、`address`、`contact_person`、`phone` text、`email` text、`website`、`credit_rating`、`risk_level` varchar NOT NULL、`bank_name`、`bank_account`、`remarks` text、`name_en`、`lead_time_days` int、`tenant_id` uuid、`created_at`/`updated_at` timestamptz default `now()`、`deleted_at` timestamptz。

**溯源列（为后续双写专项预留）**：`source_system` varchar（`scm` / `srm`）、`source_id` uuid（原表 id）。

### 约束与安全

| 项 | 落地 |
|---|---|
| 唯一约束 | `mdm_suppliers_supplier_no_tenant_key UNIQUE (supplier_no, tenant_id)` |
| RLS | `relrowsecurity=t` + `relforcerowsecurity=t`（**ENABLE + FORCE**） |
| 策略 | `tenant_isolation_mdm_suppliers`，表达式**与同 schema `mdm_assets_tenant_policy` 逐字一致**（含 `app.tenant_id` 为空放行、全零超管放行、`tenant_id IS NULL` 放行、正常租户匹配四个分支） |
| 授权 | `topems_app` 具备 SELECT / INSERT / UPDATE / DELETE（`role_table_grants` 共 7 项，另 3 项为 owner 自带） |
| 索引 | `supplier_no`、`lower(name)`、`tenant_id`、`deleted_at` 共 4 个 |
| 幂等 | 建表全 `IF NOT EXISTS`、策略用 `DO $$ ... IF NOT EXISTS (SELECT 1 FROM pg_policies ...)` |

### 数据导入

两源实测：`scm.suppliers` 196 行（tenant `...0001` 195 + `...0000` 1）、`srm.suppliers` 92 行（全 `...0001`），**两源零重叠**。

写法：`ROW_NUMBER() OVER (PARTITION BY supplier_no ORDER BY (src='scm') DESC)` 去重（scm 优先）+ `ON CONFLICT (supplier_no, tenant_id) DO NOTHING`；srm 无 `remarks` / `lead_time_days` 列，用 `NULL::text` / `NULL::int` 占位。

**导入结果：287 行**（`scm` 195 + `srm` 92），与批 31 搜索实测的 287 数对齐。

| 验证项 | 结果 |
|---|---|
| `count(*)` | **287** |
| 来源分布 | scm 195 / srm 92 |
| 重复（按 `supplier_no`+`tenant_id`） | **0** |
| 目标表 `supplier_no IS NULL` | **0** |
| 二次执行幂等 | `INSERT 0 0`，行数保持 287 |
| 源表只读核对 | `scm.suppliers` 仍 196、`srm.suppliers` 仍 92，未改动 |

**备份**：`database/backup/batch32_scm_suppliers_20261107_072206.csv`（197 行含表头）、`database/backup/batch32_srm_suppliers_20261107_072206.csv`（93 行含表头）。

### 两处如实登记的偏差

**① 被排除 1 行（实得 287 而非 288）**

`scm.suppliers` id `fafba72d-7bef-41ab-8231-64ed0b8ae0bd`，name `双语验证供应商`，tenant `...0000`，**`supplier_no IS NULL`**。因 `mdm_suppliers.supplier_no` 为 NOT NULL 业务唯一键，导入 SQL 显式 `AND supplier_no IS NOT NULL` 过滤。该行已登记在迁移文件头注释与报告 `excluded_source_rows`，**留待源表治理专项**（补 `supplier_no` 或删除该测试行）。

**② RLS 实测 `app.tenant_id = ...0000` 可见 287 行而非 1 行**

因策略照抄 `mdm_assets_tenant_policy`，其中含「全零 UUID 超管旁路」分支。**真正的隔离证据是随机租户**：`app.tenant_id = aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee` → **0 行**。

本批选择**照抄同 schema 表达式而非擅自去掉超管分支**，理由是保持同 schema 策略一致性；是否保留该旁路与既有口径（"无激活记录租户兜底放行"）相关，留待口径专项决策。

**③ 枚举跨源分裂（登记不映射）**

`category`：scm 英文 `raw_material`（195 行）vs srm 中文 `原材料`（92 行）。本批**原样保留不做映射**，以保真两源事实；需 `supplier_category` 字典 + 映射专项。`status` 两源均 `active`，暂无分裂。

### 回滚

- 建表：`DROP TABLE IF EXISTS master_data.mdm_suppliers;`
- 数据：`DELETE FROM master_data.mdm_suppliers WHERE source_system IN ('scm','srm');`

（两条均写在迁移文件头注释）

## 四、`mdm_asset_categories` 改名评估：**不改名，只登记方案**

### 取证

`grep -rn "mdm_asset_categories"` 覆盖 `svc/ lib/ apps/web/ database/ docs/`（`.rs`/`.ts`/`.tsx`/`.sql`/`.md`）→ **19 处引用**。表内数据 4 行。

### 判定

用户设定的阈值是「引用 ≤ 3 处且可一次性改 → 改名；引用多则登记方案不动」。**19 处远超阈值 → 本批不执行改名**。

### 登记方案（供后续专项）

改名目标 `mdm_data_asset_categories`（明确"数据资产"语义，避免与 `erp.asset_categories` 固定资产分类混淆）。执行需一次性同步 19 处，含：
- Rust：`svc/master-data/` 内相关模块的 SQL 字面量与 `schema_defense` 表定义
- 前端：`apps/web/src` 内相关 API 层与类型
- 迁移：历史迁移文件**不改**（保留历史真实性），新增一条 `ALTER TABLE master_data.mdm_asset_categories RENAME TO mdm_data_asset_categories`（幂等需 `DO $$ ... IF EXISTS`）
- 文档：`docs/` 内引用

风险点：改名会破坏历史迁移的可重放性（旧迁移仍写旧名）→ 必须新增强制改写迁移而非改历史文件。
