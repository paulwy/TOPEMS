# P3-2 三组权限码统一：方案与执行（2026-11-06）

> 批 6。对应整改计划 P3 遗留第一项。本文件包含命名决策、影响面实测、迁移与回滚、执行结果，以及本次盘点发现的数据库结构风险。

## 一、命名决策

### 1.1 决策

统一为 **DB 种子 / 前端现行拼写（带下划线）**：

| 组 | 统一码 | 旧拼写（待清理） |
|---|---|---|
| BI 数据源 | `bi:data_source:read` / `bi:data_source:write` | `bi:datasource:read` / `bi:datasource:write`（仅 BE plugin 声明） |
| MES 工单 | `mes:work_order:read` / `mes:work_order:write` | `mes:workorder:*`（仅 BE security 声明） |
| WMS 盘点 | `wms:stocktake:read` / `wms:stocktake:write` | `wms:stock_take:*`（仅 BE plugin 声明） |

### 1.2 理由

1. **授权数据迁移量为零**：DB 与 FE 已使用目标拼写，唯一偏离的是 BE 的 4 处声明字符串。改 BE 即可收敛，不存在"角色授权需要重建"的场景。
2. **与历史迁移意图一致**：`20260908000014_sync_frontend_permission_codes.sql`（插入 `bi:data_source:read`）、`20261102000001_sync_frontend_permission_codes_batch4.sql`（插入 `wms:stocktake:read`）声明的就是这一拼写，改 BE 是让实现对齐既定设计。
3. **前端零改动**：`apps/web/src/config/permissions.ts`（`bi:data_source:read`:431、`mes:work_order:read`:633、`wms:stocktake:read`:823）、`menuPermissions.ts`、`modules/{bi,mes,wms}/config.ts` 全部已是目标拼写，风险面最小。
4. **反向方案（统一为无下划线）需改 FE 多处 + DB 授权迁移**，成本高、回滚难，不采用。

## 二、影响面统计（本地库实测，非估算）

查询来源：`postgres://topems_app@127.0.0.1:5432/topems`，`core_permissions` / `core_role_permissions` / `core_user_roles` / `core_users`。

| 码 | 迁移前 DB 记录 | 授权角色 | 角色下用户数 |
|---|---|---|---|
| `mes:work_order:read` | 1（mes 副本） | `mes_manager` 1 个角色 | **0** |
| `mes:work_order:create/update/delete` | 各 1 | 未授权 | 0 |
| `mes:work_order:write` | 0（本批补种） | 无 | 0 |
| `bi:data_source:read` | public 副本 1 条（含 2 条历史授权） | 历史角色 | 0 |
| `bi:data_source:write` | 0（本批补种） | 无 | 0 |
| `wms:stocktake:read/write` | 0（本批补种） | 无 | 0 |
| 旧拼写 `mes:workorder:*` / `bi:datasource:*` / `wms:stock_take:*` | **0** | — | — |

**结论**：本地库 `core_users` 总数为 0（干净库），全部改动 **不影响任何实际用户**。生产环境需按同一 SQL 复核（报告已给出 SQL 口径）。

> 风险提示：`mes:work_order:write` 目前无角色授权，BE 写接口 `security(("BearerAuth" = ["mes:work_order:write"]))` 对非超管用户仍会拒绝。这是既有授权缺口（原错误码 `mes:workorder:write` 同样无人持有），本批只统一命名、**不擅自授权**，授权分配交由业务方。

## 三、三端同改方案

### 3.1 改动清单

| 端 | 文件 | 改动 |
|---|---|---|
| BE | `svc/mes/src/modules/work_order.rs` | `mes:workorder:read` → `mes:work_order:read`（2 处，:266/:492）；`mes:workorder:write` → `mes:work_order:write`（8 处，:557/:700/:813/:874/:941 等） |
| BE | `svc/analytics/src/modules/bi/plugin.rs` | `bi:datasource:read/write` → `bi:data_source:read/write`（code 2 处 + `resource_type: "datasource"` → `"data_source"`） |
| BE | `svc/wms/src/modules/wms_plugin.rs` | `wms:stock_take:read/write` → `wms:stocktake:read/write`（code 2 处 + `resource_type: "stock_take"` → `"stocktake"`） |
| DB | `database/migrations/20261106000001_permission_code_unify_bi_mes_wms.sql` | 幂等改名（仅目标不存在）+ 幂等补种 5 条缺失码 |
| FE | — | **无改动**（已全部使用目标拼写） |

### 3.2 迁移幂等性设计

- 改名：`UPDATE ... WHERE code='旧码' AND NOT EXISTS (目标码)` → 重复执行第二次 `UPDATE 0`。
- 补种：`INSERT ... SELECT ... WHERE NOT EXISTS (码)` → 重复执行第二次 `INSERT 0 0`。
- 不 `DELETE` 既有码、不触碰 `core_role_permissions`（改名保留 permission id，授权关系自动跟随）。
- 实测：第一次 `INSERT 0 5`（mes 副本 642 → 647），第二次 `INSERT 0 0`。

### 3.3 回滚

迁移文件末尾附 ROLLBACK 段（人工执行）：删除本批新增且**无授权关联**的码，改名项按"目标码改回旧码"反向处理（同样带 `NOT EXISTS` 保护）。BE 回滚即 revert 提交。

### 3.4 兼容过渡

无需过渡期：FE 与 DB 一直是目标拼写，BE 改后三方一致，不存在"旧码继续工作"的需求。已上线的 `:view → :read` 兼容层（批 5）与本批无冲突。

## 五、重大发现（需评审，登记 P5）

**`core_permissions` 在 3 个 schema 各有一份副本，且严重漂移**：

| schema | 行数 | 说明 |
|---|---|---|
| `mes` | 647（迁移后；迁移前 642） | 运行时 `search_path = mes, public` 优先命中 → **事实权威副本** |
| `public` | 1033 | 历史迁移 `20260908000014` 显式写 `public.core_permissions` 造成；含 `bi:data_source:read` 及 2 条历史授权 |
| `iam` | 0 | 空副本 |

**风险**：
1. 同一权限码可能在 mes / public 两副本各自被授权，应用只读 mes → public 的授权不生效（`bi:data_source:read` 的 2 条授权即属此类）。
2. 任何"只写 public"的迁移都不会在运行时生效——本批首版迁移曾因此落到 public（已回滚并改为不带 schema 前缀）。
3. `iam` 空副本会随租户初始化流程被填充吗？需在 P4 tier / P5 数据层专项确认。

**建议**：P5 收敛为单一权威副本（应用读的 mes），public 副本降级为历史归档或在迁移中显式清理；租户初始化模板必须与权威副本对齐。
