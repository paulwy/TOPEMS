# P3-8 模块级 → 资源级 权限码细化（批 18 执行记录）

> 执行日期：2026-11-06　批次：批 18（承接批 17 遗留的结构性缺口）
> 目标：把只有模块级 `read/write` 的 5 个模块细化到资源级，让 10 个页面能接入写权限；同时核实 3 项跨域语义。

## 1. 缺口本质

批 17 的 ③ 类里，有 8 项页面卡在同一个结构性问题上：**模块只有模块级码，没有资源级码**。

| 模块 | 批 18 前 DB 现有码 | 缺口 |
|---|---|---|
| notification | `notification:read` / `:write` / `:admin` / `:dashboard` / `:delete`（全模块级） | 无任何 `模块:资源:动作` |
| ticket | `ticket:admin` / `:dashboard` | 无 `ticket:ticket:*` |
| plugin | `plugin:dashboard` / `:marketplace` | 无 `plugin:plugin:*` |
| migration | **无任何三段码** | 无 `migration:*:*` |
| integration | 有 `connection` / `event` / `mapping` / `lims` / `mes` / `erp` / `wms` | 无同步任务资源（`*_sync`） |

前端有 8 个页面（notification 2 + integration 3 + ticket 1 + plugin 1 + migration 1）实际带 CRUD，
但 DB 侧无对应资源码 → 接入就会"传了不存在的码"，按钮全消失。

## 2. 建码依据（逐条核实实体，不造无依据的码）

每条码都先确认了**实体存在**（DB 表 或 后端路由），依据如下：

| 模块 | 资源 | 建码数 | 实体依据 |
|---|---|---|---|
| notification | notification | 3 | `core_notifications` 表 + `/api/core/notification` 路由 |
| notification | archived_notification | 3 | `archived_notifications` 表 |
| integration | lims_qms_sync | 3 | `/api/integration/lims-qms` 路由（含 `/{id}/sync`） |
| integration | mes_erp_sync | 3 | `svc/integration/src/mes_erp_sync.rs` + `/api/integration/mes-erp` 路由（含 `/sync`、`/retry`、`/logs`） |
| integration | wms_scm_sync | 3 | `svc/integration` 的 wms-scm 同步模块 |
| ticket | ticket | 3 | `core_tickets` 表 + `/api/ticket/*` 路由（feedbacks / workflows） |
| plugin | plugin | 3 | `core_plugins` 表 + `/api/plugins/*` 路由 + `svc/plugin-registry` |
| migration | service | 3 | `core_migration_history` 表 + `svc/unified-core/src/modules/migration` |
| finance | account | 3 | `core_finance_accounts` 表 + `/api/finance/accounts` 路由 |
| **合计** | **9 资源** | **27** | — |

> `finance:account` 原本只有 `finance:accounts` 页面的写需求，DB 侧 `admin:account` 只有 `read`，
> 而实体表是 `core_finance_accounts`、路由是 `/api/finance/accounts` → 权限应归 **finance 域**，
> 故建 `finance:account:*` 而不是补 `admin:account:*`（后者是系统账号，语义不同）。

## 3. 跨域 3 项核实结论

批 17 把 `erp:fixedAssets` / `erp:vouchers` / `finance:accounts` 归为"跨域"并登记。批 18 逐项核实调用链后分化处理：

| 页面 schema | `api.module` | entity | 后端归属证据 | 结论 |
|---|---|---|---|---|
| `finance/fixedAsset.ts` | `erp` | `finance_fixed_asset` | `svc/erp/src/modules/fixed_asset.rs` 存在 | **接入 `erp:asset`**（同域、四码齐全；"资产"覆盖固定资产），不改 module |
| `admin/account.ts` | `finance` | `admin_account` | 路由 `/api/finance/accounts` 存在 + `core_finance_accounts` 表 | **补 `finance:account:*` 后接入**，不改 module |
| `erp/voucher.ts` | `erp` | `voucher` | 路由 `/api/finance/vouchers` 存在；DB 有 `finance:voucher` 四码 | **停并登记**（见下） |

### 为何 `erp:vouchers` 停手

两个解法都有问题：
- 接 `finance:voucher`：跨域（erp 页面用 finance 码），日后拆分模块权限即失配；
- 补 `erp:voucher:*`：与 `finance:voucher:*` 形成**同义双码**，与批 2 的收敛方向相反，违反"不造无依据的码"。

正确解法应是**改 schema 的 `api.module` 为 finance**（与路由 `/api/finance/vouchers` 一致），
但这会改变 CrudPage 的请求路径拼装（`/api/erp/vouchers` → `/api/finance/vouchers`），
属于会触及 API 请求路径的改动，**按纪律先停、登记，待确认该页面当前实际请求路径后再动**。
