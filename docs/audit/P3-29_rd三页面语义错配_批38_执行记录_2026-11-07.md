## 一、结论

审计 **B 项（rd 三页面业务语义与数据源不一致）关闭**。

| 页面 | 处置 | 落点 |
|---|---|---|
| 配方评审 `/rd/review` | 数据源 `rd.builds` → **`rs.formulas`** | `rs.formulas` 自带 `approval_status`/`approved_by`/`approved_at`，是评审语义的天然落点，不新建表 |

三条链路自评审到发布贯通：配方（`rs.formulas`）→ 评审状态 → 发布记录（`rd.deploys.formula_id`）→ 展示关联配方名称与编码。

## 三、后端（`svc/rd/`）

### 1. 评审端点改造（`modules/formula.rs` + `models/formula.rs` + `modules/openapi.rs:50`）

- 路由 `POST /formulas/{id}/approve` → **`POST /formulas/{id}/review`**
- `ApproveFormulaRequest {}`（空结构体）→ **`ReviewFormulaRequest { action, reviewer: Option<String>, comment: Option<String> }`**
- `approve_formula` → **`review_formula`**，三态语义：

| action | approval_status | status | approved_by | approved_at |
|---|---|---|---|---|
| `submit` | `pending` | `draft` | 清空 | 清空 |
| `approve` | `approved` | `released` | 写入 reviewer | 写入 now |
| `reject` | `rejected` | `draft` | 写入 reviewer | 写入 now |

非法 action → `ApiResponse::error(400, ...)`；`reviewer` 空则回退 `"system"`。

**修复原有 2 个实质缺陷**（批 32 材料已记录）：
- `approved_by` **从不写入** → 现已正确落库（实测 `approved_by=审计验证员`）
- 请求体被完全忽略（`Json(_req)`）→ 现已按 `action/reviewer/comment` 生效

### 2. 列表过滤（`ListParams`）

- 新增 `approval_status: Option<String>`（alias `approvalStatus`），约定 **`"none"` 表示筛 `approval_status IS NULL`**
- `list_formulas` 的 SELECT 与 COUNT 同步加过滤条件
- **顺带修复不一致**：主查询缺 `deleted_at IS NULL`（原来只有 COUNT 有）

### 3. 发布关联（`modules/rd_ci_cd.rs`）

- `CreateDeployRequest` 加 `formula_id: Option<Uuid>`
- `deploy_to_json` 加 `formula_id`/`formula_name`/`formula_code`，用 `try_get` 容错（`create_deploy` 的 `RETURNING *` 不含后两者，缺列返回 `null` 而非 panic）
- `list_deploys` / `get_deploy` 由 `SELECT * FROM rd.deploys` 改为手写 SQL + **`LEFT JOIN rs.formulas f ON f.id = d.formula_id`**；COUNT 同步改
- `create_deploy` INSERT 加 `formula_id` 列与 `$9` 绑定

> 合规性：`scripts/schema_boundary.json` 中 `rd` 的主 schema 即 `rs`（`search_path: "rs, public"`），LEFT JOIN 为同 schema 访问，无需 boundary 例外。

## 五、本批查出并修复的缺陷（4 项）

1. **`rs.formulas.created_by` 类型错配（重大）**：DB 为 `uuid`，Rust 侧 `Formula`/`FormulaVersion` 声明 `String`，`create_formula` 直接 `bind(claims.sub)`。后果：**创建永远 500**；且一旦表有数据，`list_formulas` 的 `query_as` 会把 `uuid` 列解码成 `String` 而失败。**这才是 `rs.formulas` 长期 0 行、从未被使用的真因**。迁移 0036 第 5 步改 `text` 后，创建即刻恢复 200。
2. **`list_formulas` 主查询缺 `deleted_at IS NULL`**（与 COUNT 不一致，会把软删行计入 items 但 total 不算），已补。
3. **`RsDeployPage.tsx:28` 信封错位**：后端返 `items`、前端读 `deploys` → 该页恒空数据，已修。
4. **`approve_formula` 不写 `approved_by` + 忽略请求体**，已在 `review_formula` 重写中消除。

## 六、92 项 SQL-only 声明处理（顺带，独立复核）

### 结论：`database/init` 侧实际可删 **0 项**，92 项全部保留

独立复核（主 Agent 实跑，不采信 Subagent 单方判断）：把 92 项码逐个在 `database/init/` 做固定串匹配，**仅 `finance:budget:write` 命中 1 处**，其余 91 项 init 零命中。

|---|---|---|---|

### 根因与建议（**未擅自修改，需另行决策**）

`scripts/audit_permission_codes.py::scan_sql_declared`（`:144-148`）的 SQL 声明集是 **`database/init` ∪ `database/migrations`** 的并集。migrations 里批 25 `DELETE ... code IN ('...', ...)` 多行列表中的码仍被计入「SQL 声明」，而 live DB 已删除 → **永远计入 SQL-only，无法收敛**。

这是**统计口径缺陷**（脚本未区分「声明」与「删除语句里的字面量」），不是 init 里有冗余声明。修正路径有两条：① 让 `scan_sql_declared` 只扫 `init`（migrations 仅用于回溯取证）；② 识别并排除 `DELETE`/`DROP` 语句上下文。**两者均属改审计口径、超出本批授权**，故本批不改，登记待决策。**不采用「先删再说」或「放宽判定」的做法**——与批 35/36 反复强调的「不得靠豁免掩盖」一致。

对账结果（init 未动，改前=改后）：`FE 445 | BE 577 | DB 995 | FE∩BE 127`；`SQL 声明 1087 | live DB 995 | 交集 995 | SQL-only 92 | DB-only 0`；`be_only 450 / fe_only 318 / fe_orphan 32 / db_only 570`——**未变差**。
