## 二、语义契约（本批确立，后续沿用）

### 2.1 读操作：优雅降级为 200 空态

上游服务未接入时：

| 端点形态 | 返回 |
|---|---|
| 列表 | `HTTP 200` + `{items: [], total: 0}` |
| 概览 / 统计 | `HTTP 200` + 零值 JSON（保留字段结构，值置 0 / false / 默认字符串） |
| 详情 | `HTTP 200` + `data: null` |

`message` 统一标注**「XX 成功（上游服务未接入，返回空态）」**——明确标识降级态，**不把"上游未接入"伪装成"真实查到 0 条"**。

**结构化降级标记 `data.degraded === true`（本批由提交门禁倒逼出的关键改进）**：

初版前端是**靠 message 文案判定**降级态的（`msg.includes('未接入')`）。这带来两个问题：

1. `hardcoded-precise` 门禁拦下了这 2 处中文字面量（pre-commit `❌ Strict mode FAILED: 2 hardcoded CJK UI strings detected`），提交被阻断；
2. 更本质的是——**用文案做协议判定是脆弱的**：文案可以随时改，改了就静默失效。

正确解法不是把中文挪个位置绕过检测，而是让后端给出**机器可判别的标记**。于是：

- 后端 `inventory.rs` / `production.rs` 的 **10 处读降级返回**统一加上 `"degraded": true`：
  `json!({ "items": [], "total": 0, "degraded": true })`
- 前端 `detectNotConnected` 改为判 `data.degraded === true`，**彻底删除中文匹配**。

实测 4 个读端点均返回 `degraded=True, items=0`。契约从此稳定、可被任何客户端（含非中文环境）可靠判读。

（写操作的判定此前已用 `body.code === 503`，不受影响。）

### 2.2 写操作：明确 503，绝不假成功

上游服务未接入时：

```
HTTP 503
body.code = 503
message = "上游服务未接入：<服务名>，<操作名>未执行"
```

用 `lib/shared-core/src/response.rs:101` 已有的 `ApiResponse::unavailable`（本批未新增方法）。

**关键细节：4xx 业务校验失败要透传，不能被 503 吞掉。** `check_in` / `check_out` / `create_customer` 等写端点保留了原逻辑——如果下游返回 4xx（参数非法、业务规则拒绝），照原样映射 4xx 给调用方；只有"服务不可达"才降 503。这两类失败语义完全不同，混为一谈会让前端无法区分"我填错了"和"服务挂了"。

### 2.3 为什么用 503 而不用 200 假成功 / 501

- **不用 200 假成功**：这是用户反复强调的底线。用户点"提交报工"，界面提示成功，但记录根本没落库——这比直接报错危害大得多，因为用户不会重试。
- **不用 501**：501（Not Implemented）语义是"这个端点本身没实现"，而这里的端点**是实现的**，只是上游依赖不可用。语义不对。

## 三、smoke 的 503 语义豁免（本批最关键的机制设计）

### 3.1 冲突

smoke 的判定口径是 `http >= 500` 即 FAIL。写操作按要求返回 503 后，这些端点会在 smoke 里 FAIL。

### 3.2 解法：沿用仓内已有的 501 豁免先例

这不是我新造的口径。`scripts/web_contract_smoke.py` 里**早就有一条 501 的语义豁免**：

```python
elif status == 501 or body_code == 501:
    # S25 语义：501 Not Implemented 是明确的"模块未实现"业务降级语义
    # （如 mes/energy 的告警/报表端点），非错误响应，计 PASS。
    reason = None
```

即仓内已经把「明确标注的业务降级」与「处理异常」区分开了。503 属同一类，按同一逻辑豁免。

### 3.3 豁免条件必须严格，不能变成"5xx 一律放过"

新增的判定（`:717-726`，重试段 `:746-752` 同步）：

```python
elif status == 503 and body_code == 503:
    msg503 = body.get("message") if body else None
    if msg503 and "未接入" in msg503:
        reason = None          # 设计好的降级契约
    else:
        reason = "handler_error"   # 真实故障，仍判 FAIL
```

**三个必要条件同时满足才豁免**：`HTTP == 503` **且** `body.code == 503` **且** `message` 含「未接入」。

因此：

| 场景 | 判定 |
|---|---|
| 我们设计的降级（503 + code 503 + "上游服务未接入：CRM"） | **PASS** |
| 真实网关 503（无我们的 envelope） | **FAIL** |
| 真实 DB 故障 500 | **FAIL** |
| 缺字段 422（WARN） | 不判 FAIL，但也不算覆盖（见第四节） |

这样"降级语义"不会被用来掩盖真实故障——这正是用户强调"不得用『返回 500 但 smoke 预期 500』糊弄"的合规落地方式：**501/503 的豁免依据是响应体自证语义，不是靠预期清单开脱**。

## 四、smoke 补覆盖 Err 路径（此前是"没测到"而非"测过且通过"）

### 4.1 根因

`scripts/web_contract_smoke.py:644`：

```python
body = POST_BODIES.get(tmpl, {})
```

对 POST 端点，从 `POST_BODIES` 按模板取载荷，**取不到就给空体 `{}`**。

而 `POST_BODIES`（`:263`）原先只有 6 条 CRM / HRM / MES / 工单的载荷，**没有任何 mobile 条目**。于是 mobile 的所有 POST 端点都发空体：

- `MobileCheckInRequest` 要求 `lat` + `lng` → 空体反序列化失败 → **422**
- `MobileCreateLeaveRequest` 要求 `leave_type` + `start_date` + `end_date` → **422**
- `CreateWorkReportRequest` 要求 8 个字段 → **422**

422 在 smoke 里走 WARN 分支，**请求根本没进 handler**，自然也没碰到服务调用的 Err 分支。这就是"0 FAIL 但真实会 500"的成因。

### 4.2 处置：补最小合法载荷

按各 handler 的 `Json<T>` 结构补 4 条：

| 模板 | 载荷字段 | 来源结构 |
|---|---|---|
| `/attendance/check-in` | `lat`, `lng`, `address?` | `MobileCheckInRequest`（`attendance.rs:71`） |
| `/attendance/check-out` | `lat`, `lng`, `address?` | `MobileCheckOutRequest`（`:78`） |
| `/attendance/leaves` | `leave_type`, `start_date`, `end_date`, `reason?` | `MobileCreateLeaveRequest`（`:85`） |
| `/production/work-reports` | `order_id`, `workstation`, `operator`, `quantity`, `good_quantity`, `bad_quantity`, `start_time`, `end_time` | `CreateWorkReportRequest`（`production.rs:9`） |

### 4.3 覆盖有效性实测（关键证明）

补载荷后逐条 curl，确认**真的打进了降级分支**而不是又换个方式 422：

| 端点 | HTTP | body.code | message |
|---|---|---|---|
| `POST /attendance/check-in` | **503** | 503 | 上游服务未接入：HRM，打卡未执行 |
| `POST /attendance/check-out` | **503** | 503 | 上游服务未接入：HRM，下班打卡未执行 |
| `POST /attendance/leaves` | **503** | 503 | 上游服务未接入：HRM，请假申请未执行 |
| `POST /production/work-reports` | **503** | 503 | 上游服务未接入：MES，提交报工记录未执行 |

**这才是"smoke 断言对齐真实语义"**：0 FAIL 不是因为没测，而是测到了正确的降级契约。

## 六、额外发现并修复：`/customers` 写操作假成功（超出原定范围，但违反底线）

### 6.1 问题

A 组取证时发现：`customer.rs` 的真实 handler 挂在 **`/customer`（单数）**（`shared/mod.rs:757-766`），而前端 `apps/web/src/api/mobile/customer.ts` 调的是 **`/customers`（复数）**：

```ts
apiClient.mobile.get('customers', { params })        // :124
apiClient.mobile.post('customers', data)             // :132
apiClient.mobile.put(`customers/${id}`, data)        // :139
apiClient.mobile.delete(`customers/${id}`)           // :143
```

复数路径被 `contract_fallback.rs:87-90` 占位路由接管：

```python
.route("/customers", get(list_empty).post(mutate_ok))
.route("/customers/{p1}", delete(mutate_ok).get(detail_missing).put(mutate_ok))
```

而 `mutate_ok` 是：

```rust
async fn mutate_ok() -> ApiResponse<Value> {
    ApiResponse::success(json!(null), "操作成功（轻量兜底，待上游支持）")
}
```

**后果**：前端新建 / 更新 / 删除客户，界面提示**操作成功**，实际数据一条都没落库。用户不会重试，因为界面说成功了。这比报错危害大得多，也直接违反用户「写操作绝不假成功」的底线。

### 6.2 为什么不扩大成全量改造

`contract_fallback.rs` 有约 165 个占位端点，`mutate_ok` 被其中所有写端点共用。把 `mutate_ok` 全局改为 503 会一次性改变 160+ 个端点行为，影响面不可控，可能打断其他前端流程。本批只精准修**已确认前端真实在用、且已确认假成功**的 `/customers` 系。

### 6.3 处置

| 改动 | 内容 |
|---|---|
| `shared/mod.rs:757-767` | `/customer` → **`/customers`**，`/customer/{id}` → **`/customers/{id}`**，由真实 handler 接管 |
| `contract_fallback.rs` | 删掉 `/customers` 与 `/customers/{p1}` 两条（避免 axum 重复路由 panic），改为注释说明已被真实 handler 接管 |
| `contract_fallback.rs` | 新增 `mutate_unavailable` handler（503 + 「上游服务未接入，该操作未执行」）；`/customers/{p1}/assign`、`/contacts`、`/follow-ups` 的 POST 从 `mutate_ok` 改为它（这三条后端无真实实现，读保持空态、写改为 503） |

**前端调用契约未变**（仍调 `/customers`），无需改前端。

### 6.4 实测验证

```
GET  /api/mobile/customers  → HTTP 200, code=200, data={"items":[],"total":0},
                              message="获取客户列表成功（CRM 服务未接入，返回空态）"
POST /api/mobile/customers  → HTTP 503, code=503,
                              message="上游服务未接入：CRM，创建客户未执行"
```

**修复前 POST 返回的是「操作成功（轻量兜底）」**。现在用户点"保存"，看到的是明确的"服务未接入，操作未执行"。

1. **`contract_fallback.rs` 其余约 160 个占位端点的写操作仍走 `mutate_ok` 假成功**。本批只修了已确认前端真实在用的 `/customers` 系。其余端点若无真实前端流量，暂不扩大改动面；建议后续按"前端实际调用量"排序逐个收口，或在下一批统一评估把 `mutate_ok` 改为 503 的影响面。
2. **`/leads` 系仍为 fallback**（`/leads` GET 空列表 + POST `mutate_ok`；`/leads/{id}/convert` PUT `mutate_ok`）。前端 `customer.ts:187-198` 有封装，但需先取证是否有页面在用，未在本批判定。
3. **`mdm_suppliers.category` 暂不 DROP**（用户本批拍板），保留为观察项。
4. **`create/update/delete_production_order` 前端无封装**——这三个 handler 后端有、前端从未调用，smoke 因此覆盖不到。本批已把它们降级到 503，但**是否应该删除这三个死端点**需后续取证（当前保留，因不确定是否有非 web 客户端在用）。
5. **`get_equipment`（`production.rs`）未挂路由**，是死代码。本批顺手把它从 500 改为 200 null，但端点本身仍未注册——删除与否留待后续。
