## 一、为什么这次不能重复"起服务就好"

`TODO.md` 的 v1.15x 段（原 `:2069-2075`）记载过同一批 500 的处置结论：

> 「实测 21 个端点 FAIL（handler_error 500），根因 = 下游独立服务未运行（非代码缺陷）；启动 4 个下游服务后 4667/4667 PASS」

这个结论在**当时**成立，但它只治标：

- `web-contract-smoke` 是 **pre-commit 门禁**，每次提交都会跑。
- 它不可能要求每个开发者、每台 CI 机器在跑门禁前先拉起 IAM/HRM/MES/WMS 五个微服务。
- 结果就是门禁长期红、`--no-verify` 长期有借口——批 34 正是因此破了一次例。

本批把处置口径改为**契约层**：不依赖下游也能成立的端点改优雅降级，确认已经死掉的端点删掉。**smoke 门禁从此与运行环境解耦。**

## 二、取证方法（15 项逐项，不做推测）

三项证据必须同时到位，缺一项就不算定案：

1. **真实响应**：用 smoke 脚本自身的 `issue_token("local")` 自签 `test_admin` token，直接打 `127.0.0.1:8099`，取回每个端点的真实状态码与响应体。
2. **handler 源码**：定位到具体文件:行号，读失败分支写法，确认失败是"客户端调用失败"还是"SQL/序列化/缺路由"。
3. **全仓消费面**：后端引用面 + 前端页面 import 面 + 测试引用面 + 文档提及面，四路 grep。

### 一个容易踩的取证陷阱（本批实际踩到了）

初判时用 `grep -rn "from '@/api/mobile/attendance'" apps/web/src/pages/` 得到 **0 命中**，一度以为 mobile 的 12 项全是死封装、可以直接删。

**这是错的**：`MobileAttendancePage.tsx` 是通过 `@/api/mobile` **barrel 出口**间接引用的（`import { mobileApi } from '@/api/mobile'`），grep 子模块路径自然扫不到。实际 `MobileAttendancePage.tsx:74,83,92` 确实在调用 `getAttendanceStats` / `listAttendanceRecords` / `listLeaveApplications`。

如果按初判直接删，会**删掉移动端正在用的能力**。这也是本批坚持"每个端点都要四路取证"的原因。

### 3.2 组 B：`[mobile] attendance/statistics` 与 `attendance/shifts` 2 项 —— 真根因是「缺路由」

这两项的 smoke message 都是「**获取考勤记录详情失败**」，而不是「获取考勤统计失败」「获取班次失败」——**message 对不上端点语义，本身就是线索**。

**根因**：后端路由表里有 `GET /attendance/{id}`，axum 会把 `statistics`、`shifts` 这两个**字面量当成路径参数 `id`** 匹配进来，命中 `get_attendance_record_by_id`，于是去 HRM 查一个叫 "statistics" 的考勤记录 → 失败 → 返回「获取考勤记录详情失败」。

**这两个端点后端从来没实现过**：`git log -S` 对这两个路由无任何命中。前端声明来自 commit `b02cb3297`「expand PM statistics subdomain and multi-module API bindings」的批量扩展——**声明先行、实现从未跟上**。

**处置**：新增两条精确路由。axum 的路由匹配中更具体的静态路径优先于 `{id}` 通配，因此声明在 `/attendance/{id}` 之前即可正确分流。

| 改动 | 位置 |
|---|---|
| 新增 `get_attendance_statistics` handler | `svc/mobile/src/modules/attendance.rs` |
| 新增 `list_attendance_shifts` handler | `svc/mobile/src/modules/attendance.rs` |
| import + 路由注册 | `svc/mobile/src/shared/mod.rs`（`/attendance/leaves` 之后） |

| 端点 | 依赖服务 |

失败分支形如（`attendance.rs:117-129`）：

```rust
match client.get_attendance_overview(&user_id).await {
    Ok(data) => (StatusCode::OK, ApiResponse::success(unwrap_data(data), "获取考勤概览成功")),
    Err(e) => {
        tracing::error!("调用HRM服务获取考勤概览失败: {}", e);
        (StatusCode::INTERNAL_SERVER_ERROR, ApiResponse::server_error("获取考勤概览失败"))

```

**为什么不能删**：6 个 attendance 端点被 `MobileAttendancePage.tsx:74,83,92` 真实调用（见第二节的 barrel 陷阱）。

**为什么不改直连 DB**：HRM/WMS/MES 的数据在各自的独立 schema（`hrm.*` / `wms.*` / `mes.*`），而 mobile 服务的 DB pool 只授权 `mobile, public, shared`。跨 schema 直查会被 RLS 与 schema 边界保护拦下——这是架构约束，不是可以绕过的实现细节。

**处置：优雅降级**，沿用仓内已有的成熟范式：

- `svc/mobile/src/modules/workbench.rs` —— 上游失败时 `warn` + 返回默认值（`0` / `"not_checked_in"`），永不 500
- 同文件 `stocktake` / `inbound` / `outbound` / `work-reports` / `equipment` —— 上游失败返回空列表
- `contract_fallback.rs` —— 165 个未实现端点统一返回 200 空态

具体返回：

| 端点类型 | 降级返回 |
|---|---|
| 概览 / 统计类 | 零值 JSON（`today_status: "not_checked_in"` 等） |
| 列表类 | `{ items: [], total: 0 }` |
| 详情类 | `data: null` |
| 写操作类（start/complete） | 200 受理（与 `contract_fallback` 的 `mutate_ok` 一致） |

**诚实性要求（守「宁缺勿假」底线）**：所有降级返回的 message 统一为「XX 成功（HRM/WMS/MES 服务未接入，返回空态）」，**明确标识这是降级态，不把"上游未接入"伪装成"真实查到 0 条数据"**。字段值（零值/空数组/null）与 message 语义保持一致。

**未选 501 的原因**：smoke 脚本的判定口径是把 `http >= 500` 判为 FAIL。返回 501 仍然 FAIL，等于没修。

## 五、`category` 自由文本收敛

### 5.1 数据实测（`psql`，`deleted_at IS NULL`，287 行）

| 维度 | 行数 |
|---|---|
| `category` 与 `category_code` 都非 NULL | **287** |
| 仅自由文本有值、无 code | **0** |
| 仅 code 有值、无自由文本 | **0** |
| 两者都 NULL | **0** |

按 `(category, category_code)` 分组：

| category | category_code | 行数 | 来源推断 |
|---|---|---|---|
| `raw_material` | `raw_material` | 195 | scm 反向同步写入 |
| `原材料` | `raw_material` | 92 | srm 反向同步写入 |

**结论：同一个 `category_code` 对应两种自由文本值** —— `category` 实际是"反向同步把下游原值镜像回来"的产物，**不是权威源**。

### 5.2 消费面取证

| 面 | 结果 |
|---|---|
| 数据库索引 | 仅 `mdm_suppliers_category_code_idx`，**无** `category` 索引 |
| 视图 / 触发器 | **0** |
| RLS policy | 只依赖 `tenant_id`，与 `category` 无关 |
| 前端展示 fallback | `SrmSupplierDetailPage.tsx:162-164`、`schemas/srm/supplier.ts:72-78`、`schemas/erp/supplier.ts:72` —— 因所有行 code 非 NULL，**fallback 永不触发** |
| 后端 list filter | `supplier_master.rs:94` —— **按自由文本过滤（真 bug，见 5.3）** |
| 后端 create/update | `supplier_master.rs:376-393` / `:479-507` —— 仍写 `category` |
| 同步翻译兜底 | `supplier_sync.rs:106-130` —— 用 `mdm.category` 兜 `srm.category NOT NULL` |

### 5.3 查出并修复的真 bug

前端 srm 供应商列表的「分类」筛选（`schemas/srm/supplier.ts:232-246`）传的是 **`category_code`（英文码）**，而后端 `supplier_master.rs:94` 用 **`WHERE category = $2`** 按自由文本过滤。

后果：**筛选 `raw_material` 时，那 92 行 `category='原材料'` 的数据全部被漏掉**——用户看到的结果集少了 32%。

修复：filter 从 `WHERE category = $2` 改为 `WHERE category_code = $2`。

### 5.4 处置结论：走向 B（仍有消费 → 统一走 `category_code`）

- **不直接删列**：`category` 仍被同步管道用作 `srm.category NOT NULL` 的兜底来源，直接删会破坏批 34 建成的闭环。
- **标废弃**：迁移 `20261107000035_mark_mdm_suppliers_category_deprecated.sql` 加 `COMMENT ON COLUMN`，注明"仅作 srm NOT NULL 兼容与展示兜底保留，读取/过滤一律走 category_code"。
- **模块头写清边界**：`supplier_master.rs` 头部加批 35 取证段，把上表数据与处置理由固化在代码里，防止后人误以为 `category` 是权威字段。
- **未动 `scm`/`srm` 的 `category` 列**（用户明确边界：那是同步目标语义）。

**待拍板**：是否在下一批彻底 `DROP COLUMN`。前置条件是零读零写（当前仍有 list SELECT 展示与同步翻译两处引用），且要把 `srm.category NOT NULL` 兜底改由同步管道内部生成（需独立迁移 `0036+`，风险较高）。**建议再观察 1-2 个批次再动。**
