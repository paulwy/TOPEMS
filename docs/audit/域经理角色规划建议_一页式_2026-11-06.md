## 三、建议授权的三级模型

按 tier（`basic/standard/enterprise`，用户已定"平台级统一映射，不做租户级自定义"）与现有 `hasPermission` 三段码规则：

| 档位 | 授权范围 | 适用角色 |
|---|---|---|
**域全量** | 本域全部 `<域>:<资源>:read|create|update|delete` + `<域>:dashboard:read` | 各域 manager |
**域只读 + 跨域读** | 本域 `read` + 明确需要的跨域 `read`（如 rd_manager 需 `rd:dashboard:read` + `rd:build:read`） | 协作者角色 |
**域写（父域下发）** | 父域 manager 全量 + 子域 `read` | 上级管理者（如 `project_manager` 覆盖 `pm:*` + `rd:project:read`） |

三条硬规则（沿用既有约定）：

1. **只补 read 不补 write 的跨域授权**（如 erp_manager 对 `finance:voucher:read`，批 22 先例）。
2. **不给 employee 类角色补三段码**（批 23 已核 employee 三段码 0/188）。
3. **`X:write` 单向聚合**：持有 `X:write` 即拥有 create/update/delete，反向不成立（批 15 规则）。

## 四、若全部采纳的预期结果

| 项 | 现在 | 采纳 P1+P2+P3（10 个新角色）后 |
|---|---|---|
有 manager 的域 | 14 | 24 |
无 manager 的前缀 | 45 | 5（mobile / migration / plugin / iam / tenant，均为平台能力） |
业务用户可写覆盖率 | 14 域 | 24 域（剩余 5 个平台域保持 admin-only） |

建议分两次落地：

- **第一次（P1）**：`rd_manager`、`integration_manager`、`aps_manager` — 覆盖 22 个前缀，是业务量最大的三域。
- **第二次（P2+P3）**：`tms_manager`、`workflow_manager`、`monitor_manager`、`notification_manager`、`bi_manager`、`ticket_manager`、`doc_manager` — 覆盖 18 个前缀。

每次落地均需：幂等迁移（`[batchN]` + ROLLBACK）+ 全量授权 + 角色可见性核对 + 全量 vitest。

## 五、需要产品确认的四个点

1. **是否采纳 P1 三域**（rd / integration / aps）先行？
2. **`report_manager` 是否需拆出 `bi_manager`**？当前 `report` 域仅 1 前缀由 report_manager 覆盖，而 `bi` 域 2 前缀无人覆盖，二者业务相邻（数据分析与报表），可合并也可拆。
3. **`mobile` / `migration` / `plugin` / `iam` / `tenant` 五域是否确认维持 admin-only**？
4. **`project_manager` 与 `pm_manager` 是否重复**？现两者并存，`pm` 域 3 前缀，需明确是继承关系还是同义。
