## 一句话结论

研发（RD）域菜单上的三个页面——**「配方评审」「配方发布」「代码库」**——它们背后实际读取的数据库表，和页面标题承诺的业务语义对不上：评审页读的是 CI 构建记录，发布页读的是部署记录，代码库页读的是研发项目立项数据（而且分支数/提交数是前端随机数生成的假数据）。这不是命名歧义，是历史上"先把页面摆上去、数据源借现成的顶上"留下的债，需要产品确认这三个页面**到底想给用户看什么**，再决定怎么改。

### 2.2 逐页证据链

#### 页面 1：配方评审（`/rd/review`）

| 项 | 值 |
|---|---|
| 页面组件 | `apps/web/src/pages/rd/RsReviewPage.tsx` |
| 组件里调的 API | `buildApi.listBuilds`（`RsReviewPage.tsx:10,18`） |
| 前端 API 层 | `apps/web/src/api/rd/build.ts:27` → `GET /builds` |
| baseURL | `apps/web/src/config/runtime.ts:101` → `/api/rd` |
| 后端路由注册 | `svc/rd/src/modules/rd_ci_cd.rs:27` → `.route("/builds", get(list_builds)…)` |
| 后端 handler | `svc/rd/src/modules/rd_ci_cd.rs:399` `list_builds` |
| 实际 SQL | `svc/rd/src/modules/rd_ci_cd.rs:118` `SELECT * FROM rd.{table}`（table="builds"） |
| 真实表 | `rd.builds` |
| 表行数 | **139 行**（全部 status='active'，project_name/branch/commit_hash 字段均为空——种子数据） |
| 表关键列 | `build_no, project_id, branch, commit_hash, build_type, trigger_type, status, duration, build_time, logs` |

**为什么说是错配：**
- 页面标题 i18n 原文是「**配方评审**」「管理配方评审流程」（`i18n/locales/zh/rd.json:1323-1324`），按钮是「通过 / 拒绝」（k9/k10），状态列叫"待评审/已通过/已拒绝"。
- 但 `rd.builds` 是 CI 构建表，列是分支、commit hash、构建耗时、构建日志——**没有评审人、没有评审意见、没有配方 ID**。
- 前端 schema 里列了"评审人 reviewer""评论数 comment_count"（`schemas/rd/review.ts:55,114`），这两列在 `rd.builds` 里**根本不存在**，永远显示 `-` 或 0。
- 状态映射是硬凑的：前端把 `success→已通过 / failed→已拒绝 / running→评审中`（`RsReviewPage.tsx:42-47`），但数据库 `rd.builds.status` 的 CHECK 约束只允许 `active/inactive/archived`（`\d rd.builds` 实查），所以 139 行全部以原始 `active` 状态渲染——**一个待评审项都不会出现**。
- 更尴尬的是：菜单上已经有独立的「构建」页 `/rd/build`（`RsBuildPage.tsx`），那才是给 CI 构建看的正经页面。评审页等于把构建页的数据换了层皮再摆一次。
- 数据库里其实存在 `rs.formulas` 表，自带 `approval_status / approved_by / approved_at` 三个字段（`\d rs.formulas` 实查）——这才是"配方评审"语义的天然落点。

| 表关键列 | `deploy_no, project_id, build_id, env, deploy_type, environment, app_name, version, status, deploy_time, deployer, operator, target_url, logs` |

**为什么说"轻度错配 / 边界模糊"：**
- 页面标题 i18n 原文是「**配方发布**」「管理配方发布和版本部署」（`rd.json:1278-1279`）。
- `rd.deploys` 的列（环境、版本、执行人、目标 URL、部署类型 full/rolling/blue-green/canary）和"发布到哪个环境"的语义**部分贴合**——"发布一个版本到生产环境"在 DevOps 语境里本来就等于一次 deploy。
- 但和评审页同样的问题：菜单上已经有独立的「部署」页 `/rd/deploy`（`RsDeployPage.tsx`），发布页和它读同一张表，只是把状态文案从"成功/失败"换成了"已发布/已回滚/规划中"（`RsReleasePage.tsx:53-57`）。
- 真正缺的是**配方关联**：`rd.deploys` 里没有 `formula_id` 列，无法回答"这次发布发的是哪个配方的哪个版本"。
- `rs.formulas` 表自带 `version / effective_date / expiration_date` 字段，更像"配方版本生命周期"而不是"部署动作记录"。

**为什么说这是最严重的错配：**
- 页面标题 i18n 原文是「**代码库**」（`rd.json:982`），列表列是仓库名、语言、**分支数**、**提交数**、最近提交、仓库 URL。
- 但 `rs.projects` 是**研发项目立项档案表**——列是项目名、编号、负责人、预算、进度、风险等级。**没有任何一列和代码仓库有关**。
- 前端把项目名硬塞给"仓库名"字段（`RsCodePage.tsx:42` `repo_name: p.project_name`），但 `rs.projects` 实际列名是 `name` 不是 `project_name`——这一列在运行时也是空的。
- **`branch_count` 和 `commit_count` 是前端 `Math.random()` 现算的假数据**（`RsCodePage.tsx:45-46`：`Math.floor(Math.random()*10)+1` 和 `Math.floor(Math.random()*100)+10`）——每次刷新页面数字都变。
- `repo_url` 和 `tech_stack` 这两列在 `rs.projects` 里**不存在**，前端 fallback 成空字符串和"JavaScript"（`RsCodePage.tsx:44,48`）。
- 整个数据库里**没有任何代码仓库表**（已实查 `rs` schema 全部 23 张表，无 `code_repos`/`repositories` 表；`rd` schema 也只有 `bugs/builds/deploys/test_cases` 四张表）。
- 迁移注释 `database/migrations/20261107000011_resource_crud_codes_batch24.sql:12-15` 已经白纸黑字记录了这是临时方案："rd:review / rd:release / rd:code —— 无 reviews/releases/code_repos 实体……复用既有 rd:build / rd:deploy / rd:project 三码接入……三个历史 read 码登记为待清理"。

## 三、每个页面的候选改法（含成本估量）

> 成本口径：**低** ≈ 只改前端、不发版后端；**中** ≈ 后端加一个查询端点；**高** ≈ 需要新建表 + 数据迁移 + 前后端联动。

### 页面 1：配方评审

| 方案 | 做法 | 成本 | 优劣 |
|---|---|---|---|
| **A. 改读 `rs.formulas` 按 `approval_status` 过滤** | 后端加一个 `GET /api/rd/formulas?approval_status=pending` 端点（formula 模块已存在，只是没暴露"待评审列表"视图）；前端评审页换 API | **中**（后端加 1 个查询 + 前端改 adapter） | 语义最正：配方表自带 approval_status/approved_by/approved_at，按钮"通过/拒绝"直接更新这三列。推荐。 |
| B. 新建 `rd.reviews` 独立评审表 | 建表（评审单号、配方 ID、评审人、结论、意见、时间），后端加 CRUD，前端重写 | **高**（新表 + 迁移 + 全套接口 + 前端表单） | 适合"评审需要多人会签、留意见、走流程"的场景；如果产品只需要"一键通过/拒绝"，过重。 |
| C. 保持现状，把菜单名改成"构建审批" | 承认这页就是 CI 构建审批，不叫"配方评审" | **低**（只改 i18n 文案） | 最小改动，但和已有"构建"页 `/rd/build` 重复，且丢失了"配方评审"这个业务意图。 |

**研发推荐：方案 A**。`rs.formulas` 表已经有评审字段，只是没暴露成列表视图，改动量最小且语义自洽。

### 页面 2：配方发布

| 方案 | 做法 | 成本 | 优劣 |
|---|---|---|---|
| **A. 改读 `rs.formulas` 按 `status` + `effective_date` 过滤** | 后端加 `GET /api/rd/formulas?status=released`，前端发布页换 API；"回滚"动作改成把配方 status 改回 `draft` | **中** | 如果"配方发布"= 配方版本生效/失效管理，这个最对。 |
| B. 保留读 `rd.deploys`，但在 `rd.deploys` 上加 `formula_id` 列 | 迁移加列 + 部署时绑定配方版本 + 前端展示配方名 | **中高**（迁移 + 部署表单加配方选择） | 适合"配方发布 = 把配方部署到生产环境"的 DevOps 语义。但需要先想清楚和 `/rd/deploy` 页的分工。 |
| C. 保持现状，把菜单名改成"部署记录" | 承认这页就是部署列表，不叫"配方发布" | **低**（只改 i18n 文案） | 和已有"部署"页 `/rd/deploy` 重复，基本等于删一个页面。 |

**研发推荐：先看产品对"配方发布"的定义**——如果是"配方版本生效"走 A；如果是"把配方发到生产环境"走 B。两个方向都成立，不能替产品拍。

### 页面 3：代码库

| 方案 | 做法 | 成本 | 优劣 |
|---|---|---|---|
| A. 新建 `rd.code_repos` 表 | 建表（仓库名、URL、所属项目、主语言），后端加 CRUD，前端列表/创建表单对齐 | **高**（新表 + 迁移 + 接口 + 前端去随机数） | 如果产品真的要做"代码仓库台账"，这是唯一正路。但注意：分支数/提交数这种动态指标，要么接 Git 平台 API（GitHub/GitLab），要么干脆不展示。 |
| B. 砍掉这个菜单 | 代码库不是 R&D 域的核心诉求，删掉 `/rd/code` 路由和菜单项 | **低** | 如果现阶段没有代码仓库管理需求，最快止血。随机数假数据留在页面上是误导用户。 |
| C. 保持现状，但把假数字抹掉 | 前端去掉 `Math.random()`，只展示项目名 + repo_url（即使为空），明确标注"代码仓库集成待接入" | **低**（前端删几行） | 过渡方案，至少不展示假数据；但页面依然名不副实。 |

**研发推荐：方案 B（砍菜单）或 C（去假数据过渡）**。在没有真实代码仓库集成（Git 平台对接）之前，这个页面给用户看的是假数据，风险最高。

## 五、若确认不改，风险是什么

即使产品决定"这三页先这样、不动"，以下风险需要明确接受：

1. **代码库页展示假数据**：`branch_count` / `commit_count` 是 `Math.random()` 生成，每次刷新都变（`RsCodePage.tsx:45-46`）。这是**对用户的直接误导**，属于 UI 诚信问题，不是技术债。一旦有真实用户点进这个页面，会认为这些数字是系统统计的真实仓库指标。

2. **评审页永远没有"待评审"数据**：`rd.builds.status` 数据库 CHECK 约束只允许 `active/inactive/archived`，前端期望的 `pending` 状态写不进去（`\d rd.builds` 实查）。也就是说这一页上线后会一直显示 139 条"active"记录、状态列是无意义的原文 `active`，**通过/拒绝按钮永远不会出现**（按钮 `show` 条件是 `transformStatus(...)==='pending'`，`RsReviewPage.tsx:110,121`）。用户看到的是一个空壳功能。

3. **发布页同理**：`rd.deploys.status` 也是 `active/inactive/archived` 三值，前端期望的 `planning/released/rolled_back` 永远不会出现，"回滚"按钮 `show` 条件是 `transformStatus(...)==='released'`（`RsReleasePage.tsx:121`），同样永远不显示。

4. **权限码语义误导**：`rd:review:read` / `rd:release:read` / `rd:code:read` 三个权限码（`modules/rd/config.ts:317,369,395`）名字暗示"能看评审/发布/代码库"，但实际后端权限校验落在 `rd:build:read` / `rd:deploy:read` / `rd:project:read` 上（`schemas/rd/review.ts:32`、`release.ts:42`、`code.ts:30` 的 `permissionResource`）。权限管理员按名字配权限时会困惑。批 24 迁移已经把这三个码标记为"待清理"，但未实际回收。

5. **数据为空不代表功能正确**：当前三张表都是种子数据（139+139+5 行，关键字段全空），页面看起来"没报错"，但这不代表语义对。一旦将来 `rd.builds` / `rd.deploys` 接入真实 CI/CD 流水线，评审页和发布页就会**开始展示真实的 CI/CD 数据，但顶着"配方评审/配方发布"的标题**——那时候才是真正的业务事故。
