# P3-20 架构级缺陷取证与收敛（批 30）执行记录

日期：2026-11-07
原则：**无把握不动**——纯字典表可归并；涉及业务数据双写的必须先取证再决定；不可安全执行则只出方案登记，严禁为推进硬改。

## 一、供应商主数据多源问题

### 取证范围（比预想复杂：实为 6 张表）

| 表 | 行数 | 定位 |
|---|---|---|
| `scm.suppliers` | **196** | 采购供应商主数据（`supplier_no` 唯一 + `code` 冗余无唯一） |
| `srm.suppliers` | **92** | 供应商关系主数据（`supplier_no` 唯一） |
| `erp.suppliers` | 0 | CRUD 端点存活（`svc/erp/src/modules/supplier.rs:265/339/411`） |
| `erp.core_erp_suppliers` | 0 | **死表**：全仓 0 writer，唯一 reader 是 `svc/erp/src/modules/search.rs:160`（永远搜不到） |
| `scm.srm_supplier_snapshots` | 0 | srm 事件 → scm 写快照 |
| `srm.scm_supplier_snapshots` | 0 | scm 事件 → srm 写快照 |

### 判定：架构上设计为双向双写，但数据上是两份独立数据集

- **零重叠**：按 `supplier_no` / `name` / `tax_id` 三种键 JOIN scm↔srm，**全部 0 命中**（scm_only 196 / srm_only 92）
- **同步管道从未真正跑过**：`scm.suppliers` 中 `sync_from_srm=true` 行数 = 0，`srm.suppliers` 中 `sync_from_scm=true` 行数 = 0，两张快照表均 0 行
- 管道设计本身是双向的（scm CRUD → 发 `scm_to_srm` 事件 → srm upsert；srm CRUD → 发 `SrmSupplierCreated/Updated` → scm 写快照，需再调 `/scm/sync/supplier-from-srm` 才物化主表），**但生产库零事件**
- **mdm 无供应商能力**：`master_data` schema 下 92 张表，`grep %supplier%` / `%vendor%` 命中 0；mdm 只对 `master_data.materials` 有完整 CRUD，supplier 零路由、零迁移

### 结论：`safe_to_merge_now = false`，只出方案

**理论上 mdm 应为权威源，但当前不具备承载能力**；scm 与 srm 各自有完整 CRUD、平级，不存在单一权威源。

**登记的五道分裂风险**：
1. 双写管道悬空——代码设计了同步但生产 0 行走同步，业务误以为已同步
2. `erp.core_erp_suppliers` 死表被 `search.rs:160` 误读，全局搜索供应商恒空
3. 软删语义分裂——scm 用 `deleted_at`，srm 用 `status='deleted'`
4. category 枚举分裂——scm 存英文 `raw_material`，srm 存中文「原材料」
5. 编号体系分裂——scm 有 `supplier_no` + `code` 两套，srm 只有 `supplier_no`，erp 用 `code`

**归一方案（待产品拍板，本批不动数据）**：
1. mdm 建 `master_data.suppliers` 表 + 迁移
2. 一次性 UNION 导入 196 + 92 行（当前 0 重叠，直接两段 INSERT，无需去重；需 `CASE WHEN` 做 category 中英文映射）
3. scm / srm 表改只读视图指向 mdm
4. 废弃两张快照表与 erp 两张死表
5. 调用方改造：`svc/scm/src/modules/supplier.rs` 3 个 CRUD 函数、`svc/srm/src/modules/supplier.rs` 6 个、`svc/erp/src/modules/supplier.rs` 3 个、`svc/erp/src/modules/search.rs:160`、scm/srm 的 `data_sync.rs` 共 8 个 sync 端点、下游 12 处 JOIN

## 二、客户主数据多源问题

### 取证范围

| 表 | 行数 | 活跃 | 定位 |
|---|---|---|---|
| `crm.customers` | **295** | 272 | CRM 销售/营销域客户主数据（唯一真实业务表，权威源） |
| `erp.customers` | 6 | 1 | **全是测试残留**：1 行 MCP 端到端测试 + 5 行 B1 验收测试（K1B1*），5 行已软删；手机号 `138****01~05` 连续、邮箱 `b***@test.cn` |
| `crm.core_crm_customers` | 0 | 0 | 空壳表（20260725 建表时仅 id 列，后续补列）；仅被 `svc/erp/src/modules/search.rs:134` 引用，恒返回空 |

### 判定：`SEPARATE_SEMANTICS`，权威源 = **crm**，不可合并

- **零重叠**：活跃行按 name/code 比对，crm 271 行与 erp 1 行无任何命中
- **零双写**：两表各由自己服务的 CRUD 端点写，无跨表 INSERT/UPDATE/DELETE
- **事件管道是死代码**：`svc/crm/src/services/mdm_event_service.rs:19` 定义了 `publish_customer_event`，全 svc **零调用**；ERP 侧订阅（`erp/event_handlers/mod.rs:266`）收到后写的是 `erp.erp_master_data_refs` 投影表（5 行 customer 全是集成测试数据），不回写 `erp.customers`
- **备份表**：`crm.customers_tenant_null_backup_20260919`（177 行，tenant_id 全 NULL）是 2026-09-19 修 tenant_id NULL 事故的一次性备份，**代码零引用**
- **mdm 无客户能力**：`svc/master-data/src/modules/master_data.rs:1` 注释明确只承接「物料目录/UOM/样品」，全 master-data 目录对 `crm.customers`/`erp.customers` 零引用

### 执行项：读取路径收敛到权威源（唯一实际改动）

**问题**：`svc/erp/src/modules/search.rs:134` 的全局搜索查的是空壳表 `crm.core_crm_customers`（0 行），导致 ERP 全局搜索的「客户」类别**恒返回空**，而权威源 `crm.customers` 有 272 条活跃数据。

**改动**（`svc/erp/src/modules/search.rs:129-139`）：

| 项 | 改前 | 改后 |
|---|---|---|
| 表 | `crm.core_crm_customers`（0 行） | `crm.customers`（权威源） |
| description | `contact_person as description` | `COALESCE(NULLIF(email,''), NULLIF(phone,''), name)`（权威表无 `contact_person` 列） |
| 匹配列 | `name / contact_person / phone` | `name / email / phone`（均 COALESCE 兜底 NULL） |
| 软删过滤 | 无 | 新增 `AND deleted_at IS NULL` |

**安全论证（执行前逐项验证，不是假设）**：
1. **RLS 已 FORCE**：`crm.customers` `relrowsecurity = t` / `relforcerowsecurity = t`，1 条策略 `tenant_isolation_customers`
2. **策略的 NULL 放行分支不构成泄露**：`crm.customers` 中 `tenant_id IS NULL` = **0 行**（实测），故不存在「改成读真表后跨租户可见」的风险
3. **schema 边界宏不破**：`only_own_schema_query!("erp", sql, "crm")` 只校验 schema 引用（`lib/shared-boundary/src/lib.rs:288-325`），改表名不改 schema，`crm` 已在显式授权列表内
4. **列全部存在**：`name` / `email` / `phone` / `deleted_at` 均在 `crm.customers` 实际列清单内

**验证**：`cargo check`（svc/erp）exit 0；等价 SQL 在真实库执行返回 3 行真实客户，`description` 三级回退（email → phone → name）生效。

**未改**：供应商侧 `search.rs:160` 仍读死表——因供应商无单一权威源（scm/srm 平级），收敛目标不存在，只登记。

## 三、资产分类表「双份」问题

### 判定：**不是重复，是同名不同语义**，不可归并

| 维度 | `erp.asset_categories`（0 行） | `master_data.mdm_asset_categories`（4 行） |
|---|---|---|
| 语义 | 固定资产/设备分类治理表 | knowledge_v53 知识图谱的**数据资产本体** |
| PK | `uuid` | `text`（`cat-001`…） |
| 治理字段 | `code` UNIQUE、`status`、`deleted_at`、`name_en`、`parent_id` 自引用树 | 仅 `asset_count`、`tenant_id` |
| 路由 | 挂载中 `/erp/asset-categories` 全 CRUD（`svc/erp/src/modules/mod.rs:145`） | 只读 `GET /kg-v53/categories`（`svc/master-data/src/modules/mod.rs:164`） |
| 那 4 行 | — | 实体/属性/关系/数据集，全 ROOT，从 `mdm_collections` JSONB 一次性 backfill（迁移 `20261015000062:210`） |
| RLS | OFF | ON（迁移强制开启） |

**结论**：两者是不同东西，只是名字撞了。`verdict.mode = SEPARATE_SEMANTICS`，`executable_plan.class = NOT_SAFE`——**不 DROP、不归并、不动数据**。

### 顺带查出 erp 侧 0 行的真因（不是「死表」）

`erp.asset_categories` 0 行不是没人用，而是被一个 **latent bug** 卡住：

- **从未灌种子**：`grep "INSERT INTO erp.asset_categories"` 全 migrations 无命中
- **POST 端点必然报错**：`svc/erp/src/modules/asset_category.rs:235` 的 INSERT 列清单里写了 `tenant_id`，但 `information_schema.columns` 确认该表**没有 `tenant_id` 列** → 运行时 POST 必失败，数据写不进去
- 路由是活的、前端 `CategoryManagementPage` 也是活的（`apps/web/src/api/asset/assetCategory.ts:46-66` 走 `apiClient.erp`）
- **反证**：`erp.fixed_assets.asset_category` 是自由文本 `String`（`svc/erp/src/modules/fixed_asset.rs:25/45/58`），**没有 FK 到** `erp.asset_categories`——所以「资产折旧/资产列表依赖分类」目前不成立

**登记待修（批 31）**：① `asset_category.rs:235` 从 INSERT 列清单删掉 `tenant_id`（或补一次迁移加列并开 RLS）；② list 查询补 `AND deleted_at IS NULL`；③ 可选命名治理：`mdm_asset_categories` 改名 `mdm_data_asset_categories` 以根除混淆。

- 关键证据：`apps/web/src/config/runtime.ts:102,104`（bi 与 analytics 别名均指向 `/api/bi`）、`svc/analytics/src/main.rs:42`（`api_prefix=/api/bi`）、`svc/analytics/src/routes.rs:636`（`.merge(modules::report::create_routes())`）、`apps/web/src/modules/report/config.ts` 注释「P3 批4：报表域唯一归属 bi」
