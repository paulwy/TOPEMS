# CrudPage 写权限入口专项 执行记录（批 14）

- 批次：批 14
- 日期：2026-11-06
- 关联：批 12（`ListPageTemplate.writePermission`）

## 1. 盘点结论

`CrudPage` 是全站最大的 CRUD 模板：**284 个页面文件引用**（另有 51 个测试文件），分布
erp 31 / scm 27 / mes 20 / qms 18 / rd 14 / pdm 14 / ehs 14 / wms 13 / finance 13 / crm 13 /
srm 12 / lims 12 / integration 12 / hrm 10 / aps 10 …

改造前能力：只有 `actions?: ('create'|'edit'|'detail'|'delete')[]` 与 `readOnly?: boolean`，
**没有任何权限校验**（无 `usePermission` 引用）。也就是说：只要页面渲染出来，新增/编辑/删除
三个入口对任何登录用户都可见。

## 2. 通用能力（零回归设计）

### 2.1 新增 props

```ts
writePermission?: string;    // 写权限总闸：同时约束 create/edit/delete
createPermission?: string;   // 细粒度覆盖
editPermission?: string;
deletePermission?: string;
```

内部：`effectiveActions = f(actions, readOnly, 权限码, canDo)`，
`'detail'` 属读操作不受写权限影响；四个权限码**全部不传**时 `effectiveActions === actions`，
存量 284 个页面的按钮、行操作、`showCreate`、编辑表单模式判定行为完全不变。

### 2.2 为什么不直接用 `usePermission()`

`usePermission` 内部调用 `useAuth()`，无 `AuthProvider` 时抛 `useAuth must be used within AuthProvider`。
CrudPage 的 51 个测试文件多数不挂 Provider，直接接入会让它们全部挂掉（批 12 在
ListPageTemplate 上已踩过一次，当时靠逐文件加 `vi.mock` 解决，代价高）。

因此新增 `apps/web/src/hooks/useOptionalPermission.ts`：
- 读 `usePermission` 写入的 `permission_cache`（同 key、同 5 分钟 TTL）；
- **读不到缓存（无 Provider / 未登录 / 首屏未加载 / 缓存过期）→ 返回 `true`（放行）**，绝不误隐藏按钮；
- 命中缓存才做真实判定。

## 3. 首轮落地（页面级）

只对**权限码在 DB 真实存在**的页面接入，避免"传了不存在的码 → 恒无权 → 按钮消失"：

| 页面 | createPermission | editPermission | deletePermission |
|---|---|---|---|
| `pages/mes/EquipmentManagementPage.tsx` | `mes:equipment:create` | `mes:equipment:update` | `mes:equipment:delete` |
| `pages/scm/ScmPurchaseContractPage.tsx` | `scm:contract:create` | `scm:contract:update` | `scm:contract:delete` |

DB 校验：上述 6 个码在 `public.core_permissions` 中均存在（psql 实查）。

## 4. 重大发现：`hasPermission` 三段码恒真缺陷（已登记，本批不改）

排查时发现 `apps/web/src/config/permissions.ts:205 hasPermission` 对三段码
（`模块:资源:动作`，如 `scm:contract:delete`）走等级近似分支：

1. `parts = ['scm','contract','delete']` → 取 `action = 'contract:delete'`；
2. `ACTIONS.find(a => a.action === 'contract:delete')` 查不到 → 目标 `actionLevel = 0`；
3. `userActions` 取该模块下所有权限的**第二段**（`contract`）查等级 → 同样查不到 → `0`；
4. `0 >= 0` → **恒真**。

**后果**：只要用户在某模块拥有任一权限，该模块下所有三段码权限检查全部通过——
`checkPermission('scm:contract:delete')` 在仅有 `scm:contract:create` 时也返回 true。
这是"前端权限校验对三段码基本失效"的机制性根因，影响全站菜单与按钮可见性。

**本批处理**：`useOptionalPermission` 不复用该分支（三段码只认精确命中与
`<模块>:<资源>:admin` 通配，二段码仍按等级继承），并新增用例锁定
「同模块 create 不放行 delete」。

**未处理原因**：修正 `hasPermission` 会**同时改变全站**菜单与按钮可见性（原本被误放行的
按钮会批量消失），属影响登录/权限校验的高风险改动，按纪律"无把握的改动一律先评估后登记"，
不在本批试探性修改。登记为独立专项（建议紧随本批之后评估：先跑权限矩阵对账量化"误放行"
页面数量，再决定是否一刀切）。

## 6. 未落地 / 登记项

1. **284 个 CrudPage 页面未逐页接入权限码**：需按"页面实际操作 + DB 实际权限码"逐页盘点，
   且多数页面缺少对应写码（如 `mes:quality:write` 不存在，DB 仅有 `mes:work_order:write`），
   强行接入会造成按钮全隐藏。建议作为独立批次（按域推进，先补 DB 权限码再接入）。
2. **`hasPermission` 三段码缺陷**：见第 4 节，独立专项待评估。
3. **`X:create/update/delete` 与 `X:write` 两套写语义并存**：DB 中两者都有（mes 走三段语义、
   `mes:work_order:write` 走二段），未统一。
