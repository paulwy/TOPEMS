## 1. 事项一：`public.core_tenants` 的可见范围

### 1.1 问题

`core_tenants` 当前是「全员可读租户目录 + 仅系统通道可写」：可见范围到底是「所有登录租户都能看到租户目录」「仅超管/平台通道可见」，还是「租户只能看到自己」，需要产品定性。它决定批 4 的策略形态，也是 5 项中唯一直接涉及跨租户元数据暴露的事项。

### 1.2 已知事实（引自盘点 §3、§8、§9 批 4/批 6）

- 数据：**1 行**，`tenant_id IS NULL`，无全零哨兵行。
- 策略：`rls_global_read`（SELECT，PERMISSIVE，`rls_system='on' OR tenant_id = GUC OR tenant_id IS NULL`）+ `rls_system_only`（ALL）。`relrowsecurity=t`、`relforcerowsecurity=t`，属主 `topems_prod`。
- 代码：`svc/unified-core/src/modules/tenant/handlers.rs:30,44,267`，读写都在请求事务作用域；写走超管/平台流程。
- 迁移：**无任何迁移覆盖**（批 4 三个空白的其中一张）。
- 现状语义：任何租户上下文都能看到全部租户行（当前仅 1 行，实际暴露面很小，但形态上属跨租户元数据可见）。

### 1.3 候选方案

| 方案 | 做法 | 优点 | 代价 / 风险 |
|---|---|---|---|
| **A 保持宽松（现状）** | 不写迁移，只把「全员可读租户目录」登记为平台目录例外 | 零改动、零回归 | 保留 `tenant_id IS NULL` fail-open 形态，与「全面收严」口径不一致；任何新租户行都会默认全员可见 |
| **B 回填全零 + `rls_platform_read`** | `UPDATE ... SET tenant_id='000…000' WHERE tenant_id IS NULL`；删 `rls_global_read`，新增 `rls_platform_read`（平台行 OR 本租户行） | 策略形态统一，去掉 NULL 放行 | **可见范围与现状等价**（平台行对所有租户可见），安全收益接近于零，却要动鉴权关键表 → 收益/成本比最差 |
| **C 系统通道只读（推荐默认）** | 删除 `rls_global_read`；SELECT 改由 `rls_system_only` 覆盖，代码读取路径显式 `app.rls_system='on'`；租户上下文 0 行 | 租户彻底看不到租户目录，跨租户元数据面收敛；写路径不变 | 租户侧若有「租户名展示 / 租户切换器」会归零；需先核实登录前置（租户上下文建立前）是否已在系统通道 |
| **D 仅自己（`tenant_id = GUC`）** | 按行回填 `tenant_id = 该行租户自身 id`；SELECT 策略 `rls_system='on' OR tenant_id = GUC`；超管走系统通道 | 语义最干净：租户只见自己，平台通道见全量 | 回填需确定「行的自身 id」列（本表以 `id` 为准，须核实）；若登录前置需要读目录则仍需系统通道，等于 C+D 组合 |

### 1.4 影响与验证

- 影响面：`svc/unified-core` 租户模块的 3 个入口；租户侧菜单/顶部栏若展示租户名称可能受影响（待核实）。
- 验证（六档）：T0/T1 → 0；T2（全零）→ 1；T3/T4 → **方案 C 为 0，方案 D 为 1（仅自身）**；T5（系统通道）→ 1。
- 写断言：租户上下文 INSERT/UPDATE 应 `42501` 或 0 行；系统通道可写。
- 回滚：重建 `rls_global_read` 原表达式；若走 D，需评估是否把 `tenant_id` 改回 NULL（建议只回策略、不反回填）。

### 1.5 推荐与判定条件

- **默认推荐 C**：`core_tenants` 是平台目录而非租户数据，收为系统通道即可闭合跨租户元数据可见，且不动数据、回滚最简单。
- 若产品明确「租户侧要展示自己所属租户的名称/编码」→ 改 **D**（需系统通道兜底登录前置）。
- **不推荐 B**：可见范围不变，只有形态收益，却要动鉴权关键表，性价比最低。
- 仅当产品明确「租户目录就是给所有租户看的黄页」时，才选 A，并须同时登记为有意例外、后续新行写入必须显式绑定租户。

### 1.6 拍板前待核实

1. `tenant/handlers.rs` 三个入口分别在租户上下文建立前还是建立后（决定 C 是否需要额外系统通道改造）。
2. 租户侧前端是否展示租户目录/租户名称（决定 C 还是 D）。
3. `core_tenants.id` 是否即「租户自身 id」（D 的回填依据）。

## 2. 事项二：`core_menus` / `core_menu_groups` 是否「平台菜单全租户可见」

### 2.1 问题

两张表全部是 NULL 租户的平台语料，但租户分支查询按 `tenant_id = $1` 过滤。是否确认「平台菜单对所有租户可见」——这决定能否用「NULL→全零 + 平台读」直接收严，还是必须先做按租户复制或接受菜单为空。

### 2.2 已知事实（引自盘点 §3、§9 批 4）

- 数据：`core_menus` **452 行**、`core_menu_groups` **130 行**，全部 `tenant_id IS NULL`，零租户哨兵行为 0。
- 策略：两张均为 `rls_global_read`（SELECT）+ `rls_tenant_isolation`（ALL），已 FORCE，属主 `topems_prod`。
- 代码：`svc/unified-core/src/modules/menu/handlers.rs:39,92`、`menu/cache.rs:143`；超管分支无租户谓词，租户分支 `tenant_id = $1`。
- 迁移：**无任何迁移覆盖**。
- 关键风险：一旦只删 `rls_global_read` 而不回填，NULL 行对所有租户不可见 → **所有租户菜单与菜单缓存为空**。
- 关联：批 4 前置第 3 条要求先清理 `core_menus` 对 `flow.*` 空副本的依赖（与本文事项五同源）。

### 2.3 候选方案

| 方案 | 做法 | 优点 | 代价 / 风险 |
|---|---|---|---|
| **A 回填全零 + `rls_platform_read`（推荐）** | 582 行 `tenant_id` NULL→全零哨兵；删 `rls_global_read`；新增 `rls_platform_read`（`rls_system='on' OR tenant_id=全零 OR tenant_id=GUC`），与 `20261118110000 / 20261118123000` 既有平台语料口径一致 | 租户可见范围不变（平台菜单仍可见 + 本租户自定义行可见）；去掉 fail-open；菜单接口无需改语义 | 必须与代码同窗口；租户分支若改写成 `tenant_id=$1 OR tenant_id=全零` 需与策略二选一，避免双条件漂移；菜单缓存需在发布后失效 |
| **B 净减少（不回填、只收严）** | 直接删 `rls_global_read`，不改数据 | 迁移最小 | **全租户菜单归零**，属功能性事故，只有「菜单改为按租户开通时复制」的产品决策下才成立 |
| **C 按租户复制菜单** | 为每个租户插入一份平台菜单副本，再收严为严格 B | 语义上「租户拥有自己的菜单」 | 数据量 452×N、后续平台菜单变更需批量同步，改动远大于收益，不推荐 |
| **D 保持现状** | 不写迁移，登记为平台语料例外 | 零风险 | 保留 582 行 NULL 全放行，与收严目标冲突 |

### 2.4 影响与验证

- 前置：先完成事项五的证据核查（确认 `flow.*` 空副本无人使用），再排本项；否则旧部署 search_path 命中空副本时，菜单仍可能落空。
- 验证（按生产实际行数断言）：
  - T0/T1 → **0 / 0**；
  - T2（全零）→ **452 / 130**；
  - T3/T4 → **452 / 130**（方案 A）；B 方案为 0；
  - T5（系统通道）→ 全量；
  - **关键断言：T3 下菜单接口返回非空、菜单树层级完整、缓存命中后仍非空**。
- 写断言：租户上下文插入全零哨兵行 `42501`；租户更新平台行 0 行；租户新增自有菜单成功且仅自己可见。
- 回滚：重建 `rls_global_read` 原表达式 + 反回填（全零→NULL）；回滚前先快照两表行数与 `tenant_id` 分布，避免把新写入的全零业务行误反回填。

### 2.5 推荐与判定条件

- **推荐 A**：与已落地的平台语料批次（币种/角色模板/插件目录）保持同一套「哨兵行 + 平台读」口径，租户可见范围零变化，是唯一既能收严又不伤功能的方案。
- 若产品确认「菜单必须按租户独立配置、平台菜单只在开通时下发」→ 才考虑 C（需另开设计文档，不在本批）。
- **不推荐 B / D**：B 会造成全租户菜单为空；D 让 582 行长期维持 fail-open。

### 2.6 拍板前待核实

1. 产品是否确认「平台菜单全租户可见」（本项核心拍板点）。
2. 租户分支代码是继续依赖策略，还是显式加 `tenant_id=全零` 条件（二选一，需代码走读）。
3. 菜单缓存（`menu/cache.rs`）的失效机制是否覆盖策略切换窗口。
4. `flow.*` 空副本是否仍被任何部署的 search_path 命中（同事项五）。

## 4. 事项四：`erp.holidays` 的 `None` 租户全局统计分支

### 4.1 问题

`erp.holidays` 是跨租户共享的法定节假日日历，代码用裸池读取且 `tenant_id` 为 `Option`：`None` 时无谓词做全局统计，`Some` 时按租户过滤。需要确认 `None` 分支是否仍被使用——它决定该表能否从「裸池 + allow_all」改为系统通道读。

### 4.2 已知事实（引自盘点 §4.2、§9 批 6）

- 数据：**0 行**。
- 代码：`svc/erp/src/modules/holidays.rs:85-135`，**裸池**（非请求事务）读取；`None` → 无租户谓词做全局统计，`Some` → 按租户过滤。
- 定性：盘点将其归入「非租户 `allow_all`」类，判定为「平台语料 + 裸池」；收紧会让 `None` 分支归零并**静默回退到 L2 静态数据**。
- **口径不一致（须先解决）**：盘点 §4.2 同一行既把它列为「非租户 allow_all」，又记录代码使用 `tenant_id: Option`；两处口径需在开工前核实该列是否真实存在、是否可空。
- 违反的现有约定：项目规则要求租户业务模块使用请求事务作用域，而本表是裸池读取；这也是它需要单独定性的原因。

### 4.3 候选方案

| 方案 | 做法 | 优点 | 代价 / 风险 |
|---|---|---|---|
| **A 保持现状（allow_all + 裸池）** | 不改 | 零改动，`None` 分支继续可用 | 长期绕过 RLS/请求事务；与本轮收严口径冲突；但表为 0 行、语义只读，实际泄漏面小 |
| **B 改系统通道读（推荐）** | 读取路径改为显式 `app.rls_system='on'` 的专用事务/连接（保留全局统计语义）；表策略保持不套租户谓词或定型为系统只读 | 消除裸池，语义不变（`None` 仍能看到全量平台语料）；符合「系统通道」分类 | 需确认 `None` 分支仍被使用；若调用点在请求事务内改走系统通道，需确认不会误放开其他表 |
| **C 平台语料归一（全零 + 平台读）** | 先把表结构定为 `tenant_id` NOT NULL + 默认全零，已有行回填，再按平台语料收紧 | 与币种/菜单等平台语料表口径统一 | **当前 0 行**，做结构变更收益低；且 `tenant_id: Option` 的代码语义（None=全局）需同步改成全零，改动大于收益 |
| **D 系统只读 + 写禁** | `ENABLE RLS` + 仅 `rls_system` 一条策略；代码全走系统通道 | 最严格：租户完全不可见 | 若租户侧日历展示依赖本表，会归零（需核实前端是否有节假日展示） |

### 4.4 影响与验证

- 验证：T0/T1/T2 → 方案 B 下与系统通道一致（按实际查询语义断言）；T3/T4 → `Some` 分支仅见本租户 + 平台行；T5 → 全量；**关键断言：`None` 全局统计结果与改造前完全一致**（可用静态 L2 数据对照）。
- 写断言：租户上下文 INSERT `42501`（若表确无租户列，则无写路径）。
- 回滚：恢复裸池读取 + 原 allow_all 策略（0 行，回滚成本最低）。

### 4.5 推荐与判定条件

- **推荐 B**：`None` 分支只要还在用，就必须保留「全局统计」语义，系统通道是唯一既不改变口径又能去掉裸池的方式；表 0 行，风险最低。
- 若确认 `None` 分支已无调用方 → 转 **D**（系统只读），顺带消除租户可见性。
- **不推荐 C**：0 行表做结构变更收益不足；**不推荐 A**：与本轮治理目标背道而驰，且裸池属于已识别缺陷。

### 4.6 拍板前待核实

2. `erp.holidays` 是否真有 `tenant_id` 列、是否可空（盘点两处口径不一致）。
3. 租户侧前端是否有节假日展示（决定 B 与 D 的取舍）。

## 5. 事项五：`flow` schema 18 张影子表能否 DROP

### 5.1 问题

`flow` schema 下 18 张表全部 0 行、无服务引用，但历史上嵌入式部署用 `search_path=flow,public` 会命中同名空副本。需要确认嵌入式部署是否全部停用，再决定能否按 DROP 候选清退。

### 5.2 已知事实（引自盘点 §5.5、§9 批 5/批 6、§2.3 关联项）

- 数量与数据：**18 张**，全部 0 行；清单以盘点 §5.5 为准。
- 引用：`scripts/schema_boundary.json` 已无任何服务使用 `flow`；全仓无代码引用（以盘点核查为准）。
- 风险来源：旧部署 `search_path=flow,public` 会优先命中 `flow.*` 的空同名副本 → 读空；因此**不能靠 `ENABLE ROW LEVEL SECURITY` 来「顺手收严」**，只能确认无依赖后 DROP。
- 关联：`core_menu_groups`/`core_menus` 的批 4 前置第 3 条即「清理 `core_menus` 的 `flow.*` 空副本依赖」——本项必须先于事项二完成证据核查。
- 易混点：`svc/unified-core` 的 Rust `flow` **模块**与 `flow` **schema** 不是一回事，核查引用时不能只看模块名。

### 5.3 候选方案

| 方案 | 做法 | 优点 | 代价 / 风险 |
|---|---|---|---|
| **A 保持现状** | 不 DROP、不 ENABLE RLS | 零风险 | 18 张空表长期留存，干扰盘点口径与 schema defense 基线 |
| **B 先证据后 DROP（推荐）** | ①跑探针：`scripts/check_schema_boundary.py`、`scripts/check-schema-defense-drift.py`、`scripts/schema-drift-scan.sh`；②核对部署清单与连接串 search_path；③`pg_dump -n flow` 导出备份；④`DROP SCHEMA flow CASCADE`（或逐表 DROP） | 彻底清债；有备份可回滚 | DROP 不可逆（需确认备份可用）；若仍有旧部署在线，会从「读到空副本」变成「表不存在」报错 |
| **C 先 ENABLE RLS 再 DROP** | 先给 18 张表开 RLS，观察一段时间再 DROP | 可观测是否仍有读取 | 盘点已明确不建议：开 RLS 对 0 行表无实际防护，却增加一次 DDL 与误伤风险（旧部署命中后行为从「空结果」变「0 行」仍可能影响流程） |
| **D 只 DROP 无同名副本风险的子集** | 逐表评估与 `public` 同名表的对应关系，先删确定无副本依赖的 | 风险梯度最小 | 需逐表比对 18 张与 `public` 同名表，工作量大；且 schema 残留半清理状态 |

### 5.4 影响与验证

- 前置证据（缺一不可）：
  1. `schema_boundary.json` 中 `flow` 出现次数为 0；
  2. 全部部署/编排/连接串无 `search_path=flow`；
  3. 探针脚本与各服务启动 smoke 无 `schema_defense` 报警；
  4. 菜单接口在 DROP 前后返回一致（针对事项二提到的空副本依赖）。
- 验证：DROP 前跑上述三项探针 + 服务启动 smoke；DROP 后重跑同一组探针，并断言各服务 `schema_defense` 不报警、`flow` 不在任何 `schema_boundary.json`。
- 回滚：从 `pg_dump -n flow` 备份恢复 schema 与 0 行结构；因数据为 0 行，恢复只涉及 DDL。

### 5.5 推荐与判定条件

- **推荐 B**：先证据、再备份、后 DROP，一次清完 18 张；批 5 的 73 张影子表可按同样流程分批推进。
- 若任一前置证据不满足（尤其存在在线旧部署）→ 停留在 A，并把阻塞原因登记到盘点文档批 5。
- **不推荐 C**：对 0 行表开 RLS 无收益；若将来要恢复「同名空副本」行为，DROP 也比 RLS 更彻底。

### 5.6 拍板前待核实

1. 嵌入式部署（含客户现场）是否全部停用 `flow` schema 的 search_path。
2. 是否有 BI/ETL/报表工具直连 `flow.*`。
3. `flow` 18 张与 `public` 同名表的对应关系（决定能否整 schema DROP）。
4. DROP 与 `database/init` / `schema_boundary.json` / schema defense 基线的一致性（是否需要同步删基线条目）。
