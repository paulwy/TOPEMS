## 3. 草案 A：`20261119000001_iam_permission_identity_guard.sql`

- 对两张表的 `id` 执行 `ALTER COLUMN id ADD GENERATED BY DEFAULT AS IDENTITY (START WITH max(id)+1)`。
- 幂等：`attidentity <> ''` 直接跳过；存在非 identity 默认值则 `RAISE EXCEPTION`。
- 起点：`COALESCE(max(id),0)+1`；当前 0 行 → 起点 1，不与现有数据冲突。
- 选 `BY DEFAULT` 而非 `ALWAYS`：应用若仍显式提供 id 不会被拒。
  代价是显式 id **不会推进序列**——应用侧应保持「不传 id」；若未来混用显式 id，
  需把序列 `setval` 到 `max(id)` 以上，否则可能撞主键。
- 回滚：`DROP IDENTITY IF EXISTS`（见 rollback 文件），不回填数据。

## 4. 草案 B：`20261007000012_align_rebuild_selfheal.sql`（受控修改）

**改前事实**：该版本在生产账本 `success=t`；文件原第 20-21 行为
`DROP TABLE IF EXISTS iam.tool_permissions; DROP TABLE IF EXISTS iam.tenant_permissions;`，
两表当时被误判为「运行时 DDL 残留」。另两只 DROP 目标
（`plugin_erp.accounting_subjects`、`public.equipment`）在生产仍物理存在且均 0 行，
与「账本已成功但运行时又重建」的既有现象一致；本轮保留这两条 DROP，
并按 `check-destructive-sql.mjs` 要求补 `destructive-*` 豁免标记（rows-at-review=0）。

**为什么不能只加一条前向迁移**：原 DROP 之后，链上更晚的 `20261102220000` 会对
`iam.tenant_permissions` 执行无条件 `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`。
空库重建时表已被删，链条在该中途点失败；任何版本号更大的补偿迁移都来不及执行。
因此只能修改历史文件本体。

**修改内容**：两处 `DROP` 替换为 `CREATE TABLE IF NOT EXISTS`（含
`id bigint GENERATED BY DEFAULT AS IDENTITY`、主键、`uk_tenant_user`、`uk_tenant_tool`、
`chk_role`、`chk_max_permission`、FK `ON DELETE CASCADE`、6 条索引）。
生产两表已存在时整段 no-op；其余 `plugin_erp.accounting_subjects`、`public.equipment`
的 DROP 与 58 条 `ADD COLUMN IF NOT EXISTS` 保持原样。

**豁免登记**：`database/migration-exemptions.json` 新增
`B20261119-20261007000012-iam-tables-reauthority`（含改前事实、替代方案不可行的理由、
演练证据）；`checksums.txt` 仅更新该文件一行。

## 5. 草案 C：`20261119000002_public_file_monitor_rls_strict.sql`

- 对 `public.core_file_permissions` / `public.monitor_thresholds`：
  `ENABLE + FORCE RLS` → `DROP POLICY IF EXISTS` → 建 `rls_tenant_isolation`
  （`FOR ALL TO public`，`USING` 与 `WITH CHECK` 都是「系统通道 GUC 或租户等值」）→
  `CREATE INDEX IF NOT EXISTS`。
- 严格契约，不含 `tenant_id IS NULL`、空串、全零租户放行分支；GUC 未设/空串时
  等值比较为 NULL，fail-closed。
- 回滚文件把策略按同一定义重建（前态=后态，不降级为无策略），仅删除账本行；
  如需真正回到「无策略」状态，应使用 `20261118150000` 的 rollback。

## 7. 影响面

- **草案 A**：`ALTER TABLE ... ADD IDENTITY` 取 `ACCESS EXCLUSIVE`（瞬时，0 行表）；
  写入路径从「不带 id 必失败」变为可自增。对显式提供 id 的代码保持兼容。
- **草案 B**：生产上整段 no-op（两表已存在）；只影响空库重建/修复链。
- **草案 C**：`DROP/CREATE POLICY` 与 `ENABLE/FORCE` 均为短锁；单事务内完成，
  外部看不到「无策略」中间态。两张表当前 0 行，无数据风险。
- **代码耦合**：草案 A 生效前，任何不带 id 的 INSERT 仍会失败；草案 C 不改变
  已有严格策略的可见范围（同一表达式重建）。
