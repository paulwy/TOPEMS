# Portal 服务功能审计与 BFF 转型规划

> 版本: 1.0 | 更新日期: 2026-07-22
> 状态: 规划中

## 一、背景与目标

### 1.1 现状问题

Portal 服务当前定位模糊，存在以下问题：

1. **功能重复**：12 个模块中约 60% 的功能与其他服务重复（通知、公告、监控、用户设置等）
2. **数据冗余**：相同业务数据在 Portal 和专业服务中各存一份，存在数据一致性风险
3. **维护成本高**：相同功能需要在两处维护，bug 修复和功能迭代工作量翻倍
4. **定位不清晰**：初始定位为"对外门户/推广"，实际演变为"内部工作台"，与预期不符

### 1.2 转型目标

将 Portal 从"功能重复的内部工作台"转型为 **BFF（Backend For Frontend）聚合层**：

- **不存业务数据**：所有业务数据归位到专业服务
- **专注数据聚合**：为前端提供跨服务数据聚合 API
- **用户偏好管理**：管理用户级别的个性化配置（导航、快捷方式、主题等）
- **降低前端复杂度**：前端通过 Portal 一次调用获取多服务数据

## 二、功能审计与分类

| 模块 | 功能描述 | 数据存储 | 重复服务 | 分类 | 建议动作 | 理由 |

| **navigation** | 导航菜单、应用钉选、排序 | 用户偏好表 | core/plugin | 🟢 门户特色 | **保留** | 用户个性化导航配置，Portal 专属 |

| **todos** | 待办事项 CRUD | 待办表 | workflow/各业务 | 🟡 聚合功能 | **转型为聚合** | 从各服务拉取待办，统一展示 |

## 三、BFF 转型实施计划

### Phase 1：代理转发层（P0，0.5 天）

**目标**：将重复功能改为代理转发，不直接操作数据库，保持 API 兼容。

| 任务 | 改动点 | 验收标准 |
|------|--------|---------|
| notifications 代理 | 改为调用 core/notification API | Portal notification API 返回与 core 一致的数据 |
| announcements 代理 | 改为调用 ERP announcement API | Portal announcement API 返回与 ERP 一致的数据 |
| monitoring 代理 | 改为调用 monitor 服务 API | Portal monitoring API 代理到 monitor 服务 |
| user 代理 | 改为调用 core/iam 用户 API | Portal user API 代理到 IAM 服务 |
| settings 代理 | 改为调用 core/iam 设置 API | Portal settings API 代理到 IAM 服务 |
| services 代理 | 改为调用 plugin/monitor API | Portal services API 代理到对应服务 |

### Phase 2：聚合能力强化（P1，2 天）

**目标**：强化 Portal 的 BFF 聚合能力，为前端提供一站式数据接口。

| 任务 | 改动点 | 验收标准 |
|------|--------|---------|
| 仪表盘聚合 API | 聚合 5+ 服务的统计数据 | 单次调用获取 ERP/CRM/HRM/BI/Monitor 的关键指标 |
| 待办聚合 API | 从 workflow + 各业务服务拉取待办 | 统一待办列表，按来源分类 |
| 导航动态生成 | 从 plugin registry 动态生成导航菜单 | 导航菜单随已安装插件动态变化 |
| 全局搜索聚合 | 聚合各服务的搜索结果 | 一次搜索返回多模块结果 |

### Phase 3：数据清理与瘦身（P2，1 天）

**目标**：移除 Portal 中的业务数据表，仅保留用户偏好类数据。

| 任务 | 改动点 | 验收标准 |
|------|--------|---------|
| 通知表迁移 | 移除 portal.notifications 表 | 通知数据完全依赖 core/communication |
| 公告表迁移 | 移除 portal.announcements 表 | 公告数据完全依赖 ERP 或 OA 服务 |
| 用户表去重 | 移除 portal.users 相关表 | 用户信息完全依赖 core/iam |
| 监控数据去重 | 移除 portal.monitoring 相关表 | 监控数据完全依赖 monitor 服务 |
| 数据库迁移脚本 | 编写数据迁移脚本 | 现有用户偏好数据平滑迁移 |

## 四、BFF 架构设计

### 4.1 转型后的 Portal 架构

```
┌─────────────────────────────────────────────────────────┐
│                    Frontend (Web App)                    │
└─────────────────────────────┬───────────────────────────┘
                              │
                    ┌─────────▼─────────┐
                    │   Portal (BFF)    │
                    │  (无业务数据)     │
                    └─────────┬─────────┘
                              │
           ┌──────────────────┼──────────────────┐
           │                  │                  │
    ┌──────▼──────┐   ┌──────▼──────┐   ┌──────▼──────┐
    │  Unified    │   │  Business   │   │  BI /       │
    │  Core       │   │  Services   │   │  Monitor    │
    │  (IAM/Flow/ │   │  (ERP/CRM/  │   │  (报表/监控/ │
    │   File/...) │   │   HRM/...)  │   │   告警)     │
    └─────────────┘   └─────────────┘   └─────────────┘
```

### 4.2 Portal 核心职责（转型后）

1. **用户偏好管理**
   - 导航菜单个性化（钉选、排序）
   - 快捷方式收藏
   - 主题/语言偏好
   - 仪表盘布局配置

2. **跨服务数据聚合**
   - 首页仪表盘聚合
   - 统一待办中心
   - 全局搜索聚合
   - 通知中心聚合

3. **前端适配层**
   - BFF 模式，为前端定制数据格式
   - 减少前端 HTTP 请求次数
   - 统一错误处理和降级

## 五、风险与回滚

### 5.1 主要风险

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| API 兼容性问题 | 前端调用失败 | 中 | 保持 API 路径和响应格式不变，内部改为代理 |
| 性能下降 | 聚合接口耗时增加 | 中 | 引入缓存，并行调用后端服务 |
| 数据迁移丢失 | 用户偏好数据丢失 | 低 | 先双写验证，再迁移，保留回滚脚本 |
| 服务依赖增加 | 后端服务挂了影响 Portal | 中 | 实现降级策略，部分功能不可用时友好提示 |

### 5.2 回滚方案

1. **Phase 1 回滚**：直接恢复旧代码（数据库表还在）
2. **Phase 2 回滚**：聚合功能可以独立关闭，不影响基础功能
3. **Phase 3 回滚**：保留数据库备份，必要时恢复表结构

## 六、验收标准

### AC-1：重复功能代理化
- Portal 的 notifications/announcements/monitoring/user/settings 模块不直接操作数据库
- 所有 API 调用均转发到对应专业服务
- 前端调用方式不变，向后兼容

### AC-2：BFF 聚合能力可用
- `/api/portal/dashboard/stats` 聚合 5+ 服务的数据
- `/api/portal/todos` 从多个服务拉取待办
- 单次 API 调用返回前端所需的全部聚合数据

### AC-3：数据一致性
- Portal 不再存储业务数据
- 用户偏好类数据有明确的归属和管理机制
- 不存在数据重复存储

### AC-4：编译与测试通过
- `cargo check --workspace` 零错误
- 现有测试全部通过
- 新增 Portal 聚合接口的单元测试
