# 财务域服务迁移路线图

> 版本: 1.0 | 更新日期: 2026-07-22
> 状态: 规划中

## 一、背景与问题

### 1.1 现状分析

当前 TOPEMS 项目中财务功能存在**双轨制**问题：

| 维度 | ERP 内 finance 模块 | 独立 Finance 服务 |
|------|-------------------|------------------|
| 服务位置 | `svc/erp/src/modules/finance/` | `svc/finance/` |
| API 路径 | `/api/erp/finance/*` | `/api/finance/*` |
| 功能完整度 | 中等（基础 CRUD） | 较高（含审批流、过账、辅助核算） |
| 数据表 | `erp.` schema 下 | `finance.` schema 下（或独立库） |
| 前端调用 | `erpApi.finance.*` | `financeApi.*` |

### 1.2 核心问题

1. **数据一致性风险**：两套财务系统并存，核心数据（科目、凭证、余额）可能不一致
2. **重复建设成本**：相同功能在两处实现，bug 修复和功能迭代需要双倍工作量
3. **职责边界模糊**：新功能不知道应该在哪边开发
4. **维护复杂度高**：财务人员需要在两个系统间切换

### 1.3 企业管理视角定位

根据《企业管理视角分层拆解》，财务底层管控属于**基础必须层**，是企业生存合规的底线，应作为独立的核心服务存在，不应依附于 ERP。

## 二、目标与原则

### 2.1 迁移目标

1. **明确单一真理来源**：Finance 服务为财务核心唯一真理来源
2. **功能完整迁移**：ERP 内财务相关功能逐步迁移到 Finance 服务
3. **平滑过渡**：双轨运行 → 逐步切换 → 最终单轨
4. **向后兼容**：现有 API 保持兼容，通过代理/转发实现无感迁移

### 2.2 迁移原则

- **业务不中断**：迁移过程中财务功能持续可用
- **数据不丢失**：迁移前后数据一致，有完整的校验和回滚方案
- **渐进式迁移**：分模块、分阶段迁移，降低风险
- **双轨验证**：迁移后双轨运行一段时间，验证数据一致性

### 3.2 迁移范围总结

- **P0 必须迁移**：科目、凭证、账务、期间、付款、审批流（财务核心底座）
- **P1 应该迁移**：应收应付、预算费用、财务报表、期初余额（财务业务闭环）
- **P2 评估迁移**：固定资产、银行账户、合并报表、对账（高级财务功能）
- **保留在 ERP**：客户/供应商主数据（业务视图，主数据归 MDM）、采购/销售订单（业务单据）

## 四、分阶段迁移计划

### Phase 0：准备阶段（1 周）

**目标**：完成迁移前的准备工作，建立双轨运行基础设施

| 任务 | 说明 | 交付物 |
|------|------|--------|
| 数据模型对齐 | ERP finance 表结构与 Finance 服务表结构对比 | 数据映射文档 |
| API 契约对齐 | 对比两边 API 的请求/响应格式 | API 契约文档 |
| 数据同步机制 | 建立双向或单向数据同步机制 | 同步服务/脚本 |
| 监控与告警 | 建立迁移过程中的数据一致性监控 | 监控看板 + 告警规则 |
| 回滚方案 | 制定各阶段的回滚预案 | 回滚操作手册 |

### Phase 1：底座迁移 — 科目 + 期间 + 凭证（2 周）

**目标**：财务核心底座迁移到 Finance 服务，ERP 改为代理调用

| 任务 | 说明 | 验收标准 |
|------|------|---------|
| 科目管理迁移 | ERP 科目管理改为调用 Finance 服务 API | 科目 CRUD 走 Finance 服务，数据一致 |
| 期间管理迁移 | ERP 期间管理改为调用 Finance 服务 API | 期间开闭走 Finance 服务，数据一致 |
| 凭证管理迁移 | ERP 凭证功能改为调用 Finance 服务 API | 凭证 CRUD + 审批 + 过账走 Finance 服务 |
| 账务查询迁移 | 总账、余额表等查询走 Finance 服务 | 查询结果一致，性能可接受 |
| 双轨验证 | 两边数据实时同步，对账一致 | 连续 7 天数据一致性 ≥ 99.9% |
| ERP 模块下线 | ERP 内相关模块代码标记为 deprecated | 新功能统一在 Finance 服务开发 |

### Phase 2：业务迁移 — 应收应付 + 预算费用（2 周）

**目标**：财务业务功能迁移到 Finance 服务

| 任务 | 说明 | 验收标准 |
|------|------|---------|
| 应收管理迁移 | 应收账款、收款、账龄分析迁移 | 应收功能完整可用，数据一致 |
| 应付管理迁移 | 应付账款、付款核销迁移 | 应付功能完整可用，数据一致 |
| 预算管理迁移 | 预算编制、控制、分析迁移 | 预算功能完整可用 |
| 费用管理迁移 | 费用报销、费用分析迁移 | 费用功能完整可用 |
| 双轨验证 | 业务数据双轨对账 | 连续 7 天数据一致性 ≥ 99.9% |

### Phase 3：报表迁移 — 财务报表拆分（2 周）

**目标**：财务报表明确边界，专业报表归 Finance，分析报表归 BI

| 任务 | 说明 | 验收标准 |
|------|------|---------|
| 专业财务报表迁移 | 资产负债表、利润表、现金流量表等法定报表迁移到 Finance 服务 | 报表数据准确，符合财务规范 |
| 财务分析报表迁移 | 趋势分析、结构分析等迁移到 BI 服务 | 在 BI 中可查看财务分析报表 |
| ERP finance_reports 下线 | ERP 内财务报表模块标记为 deprecated | 前端统一从 Finance/BI 获取报表 |
| 报表权限对齐 | 财务报表权限与 Finance 服务权限对齐 | 权限控制正确，数据不越权 |

### Phase 4：高级功能迁移（可选，P2，2 周）

**目标**：高级财务功能迁移，完成财务域全面整合

| 任务 | 说明 | 验收标准 |
|------|------|---------|
| 固定资产迁移 | 评估后决定是否划归 Finance 服务 | 固定资产管理完整可用 |
| 银行账户迁移 | 银行账户、流水管理迁移 | 银行账户功能完整可用 |
| 合并报表迁移 | 集团合并报表功能迁移 | 合并报表功能完整可用 |
| 对账中心强化 | 统一对账引擎，服务各业务模块 | 对账功能覆盖主要业务场景 |

### Phase 5：清理收尾（1 周）

**目标**：移除 ERP 内冗余代码，完成单轨运行

| 任务 | 说明 | 验收标准 |
|------|------|---------|
| ERP 财务代码清理 | 删除 ERP 内 finance、finance_reports 等模块代码 | 代码删除干净，无残留引用 |
| 数据库表清理 | 归档或删除 ERP schema 下的财务表 | 数据完整归档，空间释放 |
| 文档更新 | 更新 API 文档、架构文档、用户手册 | 文档与实际一致 |
| 最终验收 | 全流程回归测试，数据一致性验证 | 所有财务功能正常，性能达标 |

## 五、技术方案

### 5.1 数据同步方案

```
┌─────────────┐     双写/CDC      ┌─────────────┐
│  ERP 数据库  │ ◀──────────────▶ │ Finance 数据库│
│  (erp.*)     │   数据同步       │  (finance.*) │
└─────────────┘                  └─────────────┘
       │                                │
       │                                │
       ▼                                ▼
┌─────────────┐                  ┌─────────────┐
│  ERP 服务    │                  │ Finance 服务 │
└─────────────┘                  └─────────────┘
```

**方案选择**：
- **短期**：应用层双写（两边同时写入，失败则告警）
- **中期**：基于数据库 CDC（Debezium/Wal2json）实现单向同步
- **长期**：Finance 服务为单一真理来源，ERP 只读不写

### 5.2 API 兼容方案

- ERP 原有财务 API 路径保留，但内部改为代理调用 Finance 服务
- 添加 `Deprecation` 响应头，提示调用方迁移到新路径
- 前端逐步替换 API 调用，从 `erpApi.finance.*` 改为 `financeApi.*`

### 5.3 前端迁移方案

- 后端代理确保前端无感迁移
- 分阶段替换前端 API 引用：
  1. Phase 1 后：凭证、科目等页面改用 financeApi
  2. Phase 2 后：应收应付、预算费用等页面改用 financeApi
  3. Phase 3 后：财务报表页面根据类型改用 financeApi 或 biApi

## 六、风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| 数据不一致 | 财务数据错误，影响经营决策 | 中 | 双轨对账 + 监控告警 + 快速回滚 |
| 业务中断 | 财务功能不可用，影响结账 | 低 | 灰度发布 + 回滚预案 + 双轨运行 |
| 性能下降 | 查询变慢，影响用户体验 | 中 | 缓存优化 + 数据库索引 + 压力测试 |
| 权限泄露 | 财务数据越权访问 | 低 | 权限对齐审计 + 数据权限测试 |
| 用户习惯改变 | 用户需要适应新界面/新流程 | 高 | 培训文档 + 过渡期双入口 + 用户引导 |

## 七、验收标准

### AC-1：功能完整性
- Finance 服务覆盖 100% 的 P0/P1 财务功能
- ERP 内财务功能均可正常使用（代理模式）
- 所有财务报表数据准确

### AC-2：数据一致性
- 双轨运行期间，关键数据一致性 ≥ 99.9%
- 迁移完成后，无数据丢失
- 财务账表平衡（资产=负债+权益）

### AC-3：性能达标
- 核心查询响应时间 < 2s
- 凭证过账时间 < 5s
- 月结时间 < 30min

### AC-4：向后兼容
- 原有 API 路径保持可用（代理模式）
- 前端可以逐步迁移，不强制一次性切换
- 数据格式兼容，不出现破坏性变更

### AC-5：可运维性
- 有完整的监控和告警
- 有明确的回滚预案
- 有详细的操作手册和运维文档
