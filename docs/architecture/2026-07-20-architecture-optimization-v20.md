## 1. 跨层架构优化

### 1.1 现状诊断

| 维度 | 现状 | 问题 |
|------|------|------|
| **缓存体系** | L1内存缓存(InMemoryCache) + L2 Redis + MultiLevelCacheManager | L1各实例独立，无失效广播；缓存键命名不统一；缺少缓存预热策略 |
| **事件驱动** | 44种事件类型，18服务订阅，RabbitMQ + EventPublisher/Subscriber | 缺少Saga编排；无事件版本管理；死信队列处理不完善 |
| **权限体系** | ModuleCode枚举 + 各服务独立permission.rs + RLS行级安全 | 权限定义分散；缺少统一权限中心；细粒度权限不足 |
| **多租户** | x-tenant-id header + PostgreSQL RLS + tenant_id字段 | 每次请求set_config性能损耗；连接池复用率低；跨租户数据迁移困难 |
| **工作流** | WorkflowClient + 8服务接入 + graceful fallback | 工作流定义不统一；缺少流程可视化；与业务逻辑耦合深 |

### 1.2 优化方案

#### 1.2.1 缓存一致性增强（P0）

**目标**：解决多实例部署下L1缓存不一致问题，缓存命中率提升至85%+

```
┌─────────────────────────────────────────────────────────┐
│                    缓存分层架构 V2                       │
├─────────────────────────────────────────────────────────┤
│  L0 - 本地热点缓存 (mini-lru, 100条, 无锁)               │
│  L1 - 进程内内存缓存 (InMemoryCache, dashmap, TTL)       │
│  L2 - 分布式缓存 (Redis Cluster, 持久化可选)              │
│  L3 - 数据库 (PostgreSQL, 最终一致性)                    │
└─────────────────────────────────────────────────────────┘
```

**核心改动**：
- 新增 `CacheInvalidationEvent` 事件，通过 RabbitMQ Fanout Exchange 广播缓存失效
- 引入缓存键命名规范：`{tenant}:{module}:{entity}:{id}`
- 新增 `CacheWarmer` 组件，支持启动预热和定时刷新
- 新增缓存统计指标暴露（Prometheus）：hit_rate, miss_count, eviction_count

**涉及文件**：
- `lib/src/event/event_types.rs` - 新增缓存失效事件
- `lib/src/cache.rs` - MultiLevelCacheManager 增加失效订阅
- 各服务 `shared/cache.rs` - 接入缓存失效广播

#### 1.2.2 Saga 分布式事务编排（P0）

**目标**：从"事件通知"升级为"事件驱动+Saga编排"，支持跨服务事务一致性

```
订单创建 Saga 示例:
┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐
│  SCM │──▶│ ERP  │──▶│ WMS  │──▶│ PM   │
│ 创建 │   │ 生成 │   │ 预留 │   │ 项目 │
│ 订单 │   │ 凭证 │   │ 库存 │   │ 同步 │
└──┬───┘   └──┬───┘   └──┬───┘   └──┬───┘
   │          │          │          │
   └──────────┴──────────┴──────────┘
               补偿链（反向回滚）
```

**核心改动**：
- 新增 `SagaOrchestrator` 组件，支持集中式编排
- 定义 `SagaStep` 结构：forward_action + compensate_action
- 新增 Saga 状态持久化：saga_instances, saga_steps
- 3个样板Saga：
  - `SalesOrderFulfillmentSaga`（销售订单履约）
  - `PurchaseOrderProcessingSaga`（采购订单处理）
  - `EmployeeOnboardingSaga`（员工入职流程）

**涉及文件**：
- 新建 `lib/src/saga/` - Saga编排器核心
- `lib/src/event/mod.rs` - 扩展事件元数据（saga_id, step_id）

#### 1.2.3 统一权限中心（P1）

**目标**：收敛分散的权限定义，建立RBAC + ABAC混合权限模型

权限模型 V2:
┌─────────────────────────────────────────┐

#### 1.2.4 多租户架构优化（P1）

**目标**：RLS性能优化，支持租户数据隔离等级可配置

| 隔离等级 | 方案 | 适用场景 |
|---------|------|---------|
| L1 - 共享表 + RLS | 当前方案 | 大多数中小企业租户 |
| L2 - Schema隔离 | 每租户独立Schema | 对数据隔离有要求的客户 |
| L3 - 数据库隔离 | 每租户独立数据库 | 大型企业/合规要求 |

**核心改动**：
- 引入连接池按租户分组，减少set_config调用
- 新增 `TenantConnectionPool` 支持L2/L3隔离模式
- 优化RLS策略：将 `current_setting` 改为从连接上下文读取
- 新增租户元数据缓存，减少数据库查询

#### 1.2.5 事件驱动架构升级（P2）

**目标**：事件治理体系完善，从能用→好用→可观测

**核心改动**：
- 事件版本管理：`event_type.v1` → `event_type.v2`，支持灰度迁移
- 死信队列Web控制台：查看、重试、归档死信消息

## 2. 基础设施架构优化

### 2.1 现状诊断

| 维度 | 现状 | 问题 |
|------|------|------|
| **CI/CD** | GitHub Actions，全量构建测试，质量门禁 | 构建慢（Rust全量编译）；缺少增量构建；部署自动化不足 |
| **服务发现** | Consul + 各服务SDK集成 | 缺少服务网格能力；熔断/限流分散实现；配置多份 |
| **配置管理** | services.yaml + 环境变量 + Consul KV | 配置分散；缺少版本管理；变更审计不完善 |
| **部署发布** | Docker Compose + K8s manifests | 无灰度发布；缺少滚动升级策略；回滚操作复杂 |
| **可观测性** | Prometheus + Grafana + Jaeger（docker-compose有） | 日志不统一；告警规则少；缺少SLO管理 |

### 2.2 优化方案

#### 2.2.1 CI/CD 效率革命（P0）

**目标**：CI总耗时从当前估计的20-30分钟降至8分钟内

```
CI流水线 V2:
┌──────────────────────────────────────────────────────┐
│  触发 │  变更路径检测  │  增量构建矩阵  │  质量门禁     │
├──────┼──────────────┼──────────────┼──────────────┤
│  PR  │ Rust/前端/文档 │ 并行: lint   │ 增量覆盖率    │
│      │              │       test   │ 受影响模块检查 │
│      │              │       build  │ Bundle分析    │
├──────┼──────────────┼──────────────┼──────────────┤
│  合并 │ 全量但分级    │ 1级: 核心库   │ 全量质量门禁   │
│ main │              │ 2级: 业务服务 │ 性能基线对比   │
│      │              │ 3级: 端到端   │ 发布清单生成   │
└──────┴──────────────┴──────────────┴──────────────┘
```

**核心改动**：
- **Rust增量构建**：使用 `sccache` + `swatinem/rust-cache` 深度缓存
- **变更路径过滤**：paths-filter action，只构建受影响的crate
- **并发矩阵优化**：按服务组并行测试（core/erp/manufacturing/supply-chain...）
- **前端构建优化**：Turbo 增量缓存 + pnpm 依赖级缓存
- **Docker镜像优化**：多阶段构建 + 层缓存 + 仅构建变更服务

## 3. 后端架构优化

### 3.1 现状诊断

| 维度 | 现状 | 问题 |
|------|------|------|
| **共享库** | lib/ 下 38 个独立 .rs 模块 | 职责边界模糊；依赖关系复杂；编译慢 |
| **服务结构** | 27个服务，每服务 models/modules/shared/main.rs | 重复代码多；脚手架成本高；升级扩散大 |
| **API网关** | 无统一网关，预留8080 | 认证分散；限流不统一；缺少聚合层 |
| **数据库** | 每服务独立PgPool，单库多schema | 连接数膨胀；缺少慢查询治理；读写未分离 |
| **模块边界** | ERP等大服务内部模块多 | 模块耦合深；依赖不清晰；难以独立部署 |

### 3.2 优化方案

#### 3.2.1 共享库分层重构（P0）

**目标**：从38个扁平模块重组为清晰的分层架构，编译速度提升40%

```
lib/ 分层架构 V2:
┌─────────────────────────────────────────────────┐
│  topems-web (原 axum 相关宏/middleware)         │
│  (HTTP层: 路由宏、中间件、响应格式)               │
├─────────────────────────────────────────────────┤
│  topems-domain (领域层)                          │
│  (实体、值对象、领域事件、仓储接口)               │
├─────────────────────────────────────────────────┤
│  topems-infra (基础设施层)                       │
│  (数据库、缓存、消息、配置、监控)                 │
├─────────────────────────────────────────────────┤
│  topems-core (核心原语)                          │
│  (错误类型、结果类型、工具函数、常量)             │
└─────────────────────────────────────────────────┘
```

**分层原则**：
- 依赖方向：web → domain → infra → core
- 每层独立 crate，可单独编译和测试
- core 无任何外部框架依赖，最稳定
- infra 封装所有第三方中间件

**涉及文件重组**：
```
lib/
├── topems-core/         # 核心原语（原 error/response/validation 等）
├── topems-domain/       # 领域层（原 permission/tenant/auth/audit 等）
├── topems-infra/        # 基础设施（原 database/cache/redis/event 等）
└── topems-web/          # Web框架层（原 middleware/cors/rate_limit 等）
```

#### 3.2.2 服务模板标准化（P1）

**目标**：新服务开发时间从2天降至2小时，服务结构100%一致

```
服务标准结构 V2:
{service}/
├── src/
│   ├── main.rs          # 启动入口（模板生成）
│   ├── lib.rs           # 库导出

**核心改动**：

- 宏驱动开发：`#[crud_module]` 自动生成 CRUD 全套代码

#### 3.2.4 数据库架构优化（P1）

**目标**：连接数降低60%，慢查询减少80%，支持读写分离

```
数据库架构 V2:
┌─────────────────────────────────────────────────┐
│               PgBouncer (连接池代理)             │

- 分区表策略：大表（如日志、审计、事件）按时间分区

#### 3.2.5 模块化边界治理（P2）

- 模块热插拔（可选）：支持运行时启用/禁用模块

## 4. 前端架构优化

### 4.1 现状诊断

| 维度 | 现状 | 问题 |
|------|------|------|
| **Hooks** | 50+ 个自定义 hooks，扁平存放 | 命名不统一；职责重叠；查找困难 |
| **状态管理** | 12个 Zustand store + React Query | store职责模糊；数据重复；难以追踪变更 |
| **模板体系** | 21个页面模板 + 声明式CRUD | 学习曲线陡；模板间关系复杂；定制成本高 |
| **微前端** | Module Federation + 动态路由 | 集成度低；只有核心模块用了；调试困难 |
| **构建性能** | Vite + 全量 typecheck + build | 冷启动慢；typecheck耗时；大bundle |

### 4.2 优化方案

#### 4.2.1 Hooks 分层治理（P0）

**目标**：从50+扁平hooks收敛为清晰的三层体系，复用率+50%

```
Hooks 分层架构 V2:
┌─────────────────────────────────────────────────┐
│  /hooks/features/    业务特征层（按领域组织）    │
│  useErp, useHrm, useCrm, useWms, ...            │
├─────────────────────────────────────────────────┤
│  /hooks/domain/      领域能力层（通用业务抽象）   │
│  useCrudOperations, useApproval, useImport...   │
├─────────────────────────────────────────────────┤
│  /hooks/ui/          UI交互层（纯前端，无业务）   │
│  useUrlState, useColumnConfig, useDialog...     │
├─────────────────────────────────────────────────┤
│  /hooks/foundation/  基础原语层（最底层工具）     │
│  useLocalStorage, useDebounce, useInterval...   │
└─────────────────────────────────────────────────┘
```

**依赖规则**：
- 上层可调用下层，禁止反向依赖
- 同层之间禁止相互调用（保证正交）
- feature层按模块命名空间隔离，避免污染

**清理动作**：
- 合并重复hooks：useCrudQueries + useCrudMutations → useCrudOperations
- 下沉通用逻辑：useImportExport → domain层
- 删除废弃hooks：useListPageState（已被useUrlListState替代）
- 命名规范：`use{Domain}{Action}` 统一命名

---

#### 4.2.2 状态管理架构重组（P1）

**目标**：从12个分散store收敛为领域驱动的状态分层

```
状态管理 V2:
┌─────────────────────────────────────────────────┐
│  Server State (React Query)                      │
│  ┌───────────────────────────────────────────┐  │
│  │  所有服务端数据：列表、详情、字典、配置     │  │
│  │  缓存、失效、重试、乐观更新由 RQ 管理      │  │
│  └───────────────────────────────────────────┘  │
├─────────────────────────────────────────────────┤
│  Domain Store (Zustand - 业务状态)              │
│  ┌──────────┬──────────┬──────────┐             │
│  │ auth     │ workflow │ tenant   │             │
│  │ (用户/   │ (流程/   │ (租户/   │             │
│  │  权限)   │  审批)   │  组织)   │             │
│  └──────────┴──────────┴──────────┘             │
├─────────────────────────────────────────────────┤
│  UI Store (Zustand - 界面状态)                  │
│  ┌──────────┬──────────┬──────────┐             │
│  │ theme    │ ui       │ shortcuts│             │
│  │ (主题/   │ (加载/   │ (快捷键/ │             │
│  │  语言)   │  通知)   │  窗口)   │             │
│  └──────────┴──────────┴──────────┘             │
└─────────────────────────────────────────────────┘
```

**核心改动**：
- **强边界**：Server State 与 Client State 严格分离，禁止在store中存服务端数据
- **领域store**：auth, workflow, tenant 三个核心领域store，其他全部下沉为 RQ 查询
- **UI store瘦身**：uiStore 拆分为 themeStore + notificationStore + shortcutStore
- **持久化策略**：领域store用localStorage，UI store用sessionStorage，RQ用内存+IndexedDB

## 6. 风险与应对
