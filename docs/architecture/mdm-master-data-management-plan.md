# MDM 主数据管理系统规划

> 版本: 1.0 | 更新日期: 2026-07-22
> 状态: 规划中

## 一、背景与问题

### 1.1 现状分析

当前 TOPEMS 项目中主数据存在**分散管理**的问题：

| 主数据类型 | ERP 服务 | CRM 服务 | Finance 服务 | SCM 服务 | 其他服务 |
|-----------|---------|---------|-------------|---------|---------|
| 客户主数据 | ✅ customer | ✅ customer | ⚠️ 部分 | ⚠️ 部分 | ❌ |
| 供应商主数据 | ✅ supplier | ❌ | ✅ supplier | ✅ supplier | ❌ |
| 物料主数据 | ✅ material/product | ❌ | ⚠️ 会计科目关联 | ✅ inventory | ❌ |
| 组织架构 | ✅ department | ✅ department | ⚠️ 成本中心 | ⚠️ 仓库 | ❌ |
| 员工主数据 | ⚠️ 基础信息 | ✅ employee | ❌ | ❌ | HRM ✅ |
| 科目主数据 | ⚠️ 业务视图 | ❌ | ✅ chart of accounts | ❌ | ❌ |
| 仓库/库位 | ✅ warehouse | ❌ | ❌ | ✅ warehouse | ❌ |

### 1.2 核心问题

1. **数据不一致**：同一客户/供应商在不同系统中信息不一致（名称、编码、联系人等）
2. **重复录入**：客户信息需要在 ERP、CRM、Finance 中分别录入
3. **质量难保障**：缺少统一的数据校验和审批流程
4. **集成成本高**：各服务间需要双向同步，集成复杂度高
5. **分析困难**：跨系统报表分析时，主数据口径不一致导致分析结果不可信

### 1.3 企业管理视角定位

根据《企业管理视角分层拆解》，统一主数据管理属于**基础必须层 + 共有核心层**的交叉领域：

- **基础必须**：主数据是所有业务系统的基础，没有统一主数据就无法实现业务协同
- **共有核心**：主数据为所有业务服务提供共享的数据底座，是共有核心的重要组成部分

## 二、目标与原则

### 2.1 建设目标

1. **单一真理来源**：建立统一的主数据管理平台，所有业务系统从 MDM 获取权威主数据
2. **数据质量保障**：建立数据标准、校验规则、审批流程，确保主数据质量
3. **灵活分发同步**：支持多种同步模式（实时/批量、推/拉），满足不同服务的需求
4. **全生命周期管理**：从创建、变更、审核到停用/归档的全生命周期管理
5. **可追溯可审计**：所有主数据变更有记录、可追溯、可审计

### 2.2 建设原则

- **统一标准**：统一编码规则、命名规范、数据模型
- **集中管理**：主数据的创建、变更、审核在 MDM 集中处理
- **分布使用**：各业务服务通过 API 或同步机制使用主数据
- **渐进式建设**：从最核心的主数据开始，逐步扩展覆盖范围
- **业务驱动**：以业务价值为导向，优先建设需求最迫切的主数据

### 3.2 P0 核心主数据说明

#### 3.2.1 组织域

```
组织架构树：
└── 集团/公司
    ├── 部门/事业部
    │   ├── 科室/班组
    │   └── 岗位
    ├── 成本中心
    └── 利润中心
```

- 所有业务系统共用一套组织架构
- 支持多组织、多公司架构
- 组织变更有生效日期，支持历史版本查询

#### 3.2.2 人员域

- 员工基础信息（姓名、工号、部门、岗位）
- 员工与组织的任职关系
- 支持兼岗、挂职、调岗等复杂场景
- 与 IAM 系统联动，账号-员工关联

#### 3.2.3 财务域

- 会计科目表（Chart of Accounts）
- 会计期间（年度、期间、结账状态）
- 币种与汇率
- 辅助核算项（部门、项目、客户、供应商等）

### 4.2 与现有服务的关系

#### 4.2.1 与 unified-core/master 的关系

- **现状**：unified-core 中已有 master 模块，主要提供基础数据查询
- **规划**：master 模块逐步演进为 MDM 服务，或独立为专门的 MDM 服务
- **过渡方案**：短期在 unified-core 中增强 master 模块的能力，长期考虑独立部署

#### 4.2.2 与 IAM 的关系

- IAM 管理**账号和权限**，MDM 管理**人员和组织**
- 两者通过员工 ID 关联，双向同步
- 人员入职/离职流程：MDM 维护人员信息 → 同步到 IAM 创建/停用账号

#### 4.2.3 与各业务服务的关系

- 业务服务**消费**主数据，不直接修改主数据
- 主数据的创建/变更在 MDM 中完成，通过 API 或同步机制分发到各业务服务
- 业务服务可以缓存主数据，但权威来源始终是 MDM

### 4.3 数据同步模式

| 同步模式 | 适用场景 | 技术方案 | 延迟 |
|---------|---------|---------|------|
| **实时 API 查询** | 对数据一致性要求高、查询频率不高 | REST API / gRPC | < 1s |
| **实时推送** | 重要主数据变更需要及时通知 | Webhook / 消息队列 | < 5s |
| **增量同步** | 业务系统缓存主数据，定期拉取变更 | CDC + 定时任务 | 分钟级 |
| **全量同步** | 初始化、数据修复、批量导入 | 批量任务 + 文件交换 | 小时级 |

## 六、关键技术点

### 6.1 数据模型设计

- **多版本管理**：主数据支持历史版本，可查询任意时间点的数据
- **多维度属性**：支持扩展属性，满足不同业务的差异化需求
- **关系模型**：清晰定义主数据之间的关系（组织-人员、客户-联系人等）
- **分类体系**：支持多级分类、多分类体系

### 6.2 数据质量保障

- **校验规则引擎**：可配置的数据校验规则（格式、范围、唯一性等）
- **重复数据检测**：基于相似度算法的重复数据发现和合并
- **数据质量评分**：量化评估主数据质量，持续改进
- **审批工作流**：重要变更走审批流程，确保数据准确性

### 6.3 数据同步机制

- **CDC（Change Data Capture）**：基于数据库日志的变更捕获
- **事件驱动**：主数据变更触发事件，通知下游系统
- **幂等设计**：同步接口支持幂等，防止重复处理
- **失败重试**：同步失败自动重试，有死信队列处理机制

### 6.4 性能与可扩展性

- **缓存策略**：热点主数据多级缓存，提升查询性能
- **读写分离**：主数据写入走主库，查询走从库
- **水平扩展**：服务无状态，支持水平扩展
- **分库分表**：大数据量主数据考虑分库分表

## 七、风险与缓解

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| 业务部门不配合 | 主数据标准无法落地 | 高 | 高层推动，明确主数据管理的组织和职责 |
| 数据迁移难度大 | 历史数据质量差，迁移困难 | 中 | 先清洗后迁移，分批次迁移，验证后切换 |
| 系统改造工作量大 | 各业务系统改造需要大量开发 | 中 | 提供兼容层，渐进式迁移，先读后写 |
| 性能问题 | 所有服务都查 MDM，成为性能瓶颈 | 中 | 多级缓存、读写分离、各服务本地缓存 |
| 数据安全风险 | 主数据集中后安全风险集中 | 中 | 严格的权限控制、数据脱敏、审计日志 |

## 八、验收标准

### AC-1：功能完整性
- P0 主数据（组织、人员、财务）100% 覆盖
- P1 主数据（客户、供应商、物料）100% 覆盖
- 支持 CRUD、查询、版本、审批等核心功能

### AC-2：数据一致性
- 各业务系统的主数据与 MDM 一致性 ≥ 99.9%
- 主数据变更在 5 分钟内同步到所有下游系统
- 无重复主数据（或重复率 < 0.1%）

### AC-3：性能达标
- 主数据查询响应时间 < 500ms（P95）
- 主数据写入响应时间 < 1s（P95）
- 支持 1000+ QPS 的查询压力

### AC-4：可运维性
- 有完整的监控和告警
- 数据同步状态可视化
- 有数据质量看板和治理工具
- 有详细的操作手册和运维文档

### AC-5：业务价值
- 主数据录入效率提升 50%（减少重复录入）
- 主数据质量问题率下降 80%
- 跨系统报表分析的数据一致性问题减少 90%
- 新业务系统接入主数据的时间缩短 70%
