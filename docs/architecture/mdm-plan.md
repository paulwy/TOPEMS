# TOPEMS 主数据管理（MDM）规划

> 版本: 1.0 | 更新日期: 2026-07-22
> 状态: 规划中（V14.1 Phase 3 交付物）
>
> 本规划基于《企业管理视角分层拆解》中"基础必须层"的定位，明确主数据范围、同步机制与服务边界，为 V15.0 主数据治理专项提供路线图。

---

## 一、背景与问题

### 1.1 现状分析

当前 TOPEMS 采用微服务架构，各业务服务自治管理其所需的主数据实体。通过代码库扫描（截至 2026-07-22），主数据分布如下：

| 主数据实体 | 当前归属服务 | 表名 | 重复定义服务 | 租户隔离 |
|-----------|------------|------|------------|---------|
| **客户** | ERP | `erp.customers` | SCM, SRM（功能视角不同） | ✅ tenant_id |
| **供应商** | SCM, SRM | `scm.suppliers`, `srm.suppliers` | ERP（采购模块） | ✅ tenant_id |
| **物料/产品** | ERP | `erp.materials` | — | ✅ tenant_id |
| **组织/部门** | HRM | `hrm.departments`, `hrm.companies` | — | ✅ tenant_id |
| **员工** | HRM | `hrm.employees` | — | ✅ tenant_id |
| **会计科目** | ERP | `erp.accounting_subjects` | Finance（凭证模块引用） | ✅ tenant_id |

### 1.2 核心问题

1. **客户/供应商重复定义**：ERP、SCM、SRM 各自维护客户或供应商数据，导致同一实体在不同服务中编码、名称、状态可能不一致。
2. **无统一主数据标识**：缺乏全局唯一的 `master_data_id`，跨服务关联依赖业务编码（如 `customer_code`），编码变更时联动困难。
3. **同步机制缺失**：主数据变更（如客户更名、供应商状态变更）无法自动同步到依赖该数据的其他服务。
4. **服务边界模糊**：新功能开发时，不确定应该在哪个服务中创建/修改主数据。

## 二、MDM 目标与原则

### 2.1 目标

1. **单一真理来源**：每个主数据实体有且只有一个"主所有权"服务负责创建和核心属性维护。
2. **全局唯一标识**：为所有主数据实体分配全局唯一 ID（GUID），跨服务引用时使用该 ID。
3. **实时同步**：主数据变更后，依赖服务在秒级内收到同步通知。
4. **向后兼容**：现有 API 和数据库结构保持不变，通过新增 MDM 层逐步治理。

### 2.2 原则

| 原则 | 说明 |
|------|------|
| **谁创建谁主控** | 创建主数据的服务拥有该数据的"写权限"，其他服务只读引用 |
| **事件驱动同步** | 主数据变更通过消息队列（RabbitMQ）发布事件，依赖服务订阅消费 |
| **最终一致性** | 允许跨服务数据存在短暂不一致，通过补偿机制保证最终一致 |
| **渐进式治理** | 不强制迁移现有数据，新功能优先使用 MDM 规范，存量数据逐步对齐 |
| **租户隔离优先** | 所有主数据同步必须携带 `tenant_id`，禁止跨租户数据混用 |

## 三、主数据范围与所有权

### 3.1 六大主数据域

```
┌─────────────────────────────────────────────────────────────┐
│                    TOPEMS 主数据全景                         │
├─────────────┬──────────────┬──────────────┬─────────────────┤
│   主数据域   │   主所有权服务  │   核心属性    │   消费服务       │
├─────────────┼──────────────┼──────────────┼─────────────────┤
│  客户        │   CRM        │  名称/编码/分类│ ERP, SCM, SRM   │
│  供应商      │   SRM        │  名称/编码/评级│ SCM, ERP, WMS   │
│  物料/产品   │   ERP        │  编码/规格/单位│ MES, WMS, SCM   │
│  组织/部门   │   HRM        │  名称/层级/负责人│ 全部服务        │
│  员工        │   HRM        │  工号/姓名/岗位│ 全部服务        │
│  会计科目    │   Finance    │  科目代码/名称 │ ERP, BI         │
└─────────────┴──────────────┴──────────────┴─────────────────┘
```

### 3.2 所有权分配 rationale

| 主数据域 | 归属服务 | 理由 |
|---------|---------|------|
| **客户** | CRM | CRM 是客户关系的唯一入口，拥有最完整的客户画像（联系记录、商机、合同） |
| **供应商** | SRM | SRM 专注供应商全生命周期管理（准入、评估、退出），比 SCM 的物流视角更全面 |
| **物料/产品** | ERP | ERP 是物料主数据的天然归属，BOM、库存、成本均围绕物料展开 |
| **组织/部门** | HRM | HRM 已拥有完整的组织架构和部门管理体系 |
| **员工** | HRM | HRM 是员工信息的权威来源（入职、岗位、薪酬） |
| **会计科目** | Finance | Finance 服务是财务核算的单一真理来源，科目体系应独立维护 |

## 四、同步机制

### 4.1 事件驱动同步架构

```
┌──────────────┐    变更事件     ┌──────────────┐    订阅消费     ┌──────────────┐
│  主所有权服务  │ ─────────────→ │  RabbitMQ    │ ─────────────→ │  依赖服务     │
│ (CRM/SRM/...)│   (domain evt) │  Exchange    │   (topic sub)  │ (ERP/MES/...)│
└──────────────┘                └──────────────┘                └──────────────┘
       │                              │                              │
       │  写操作                       │  路由规则                     │  本地缓存/副本
       ▼                              ▼                              ▼
  ┌─────────┐                   ┌─────────┐                    ┌─────────┐
  │ 主数据表 │                   │ tenant_id│                   │ 引用表   │
  │ (master)│                   │ + entity │                   │ (slave)  │
  └─────────┘                   │ + action │                   └─────────┘
                                └─────────┘
```

### 4.2 事件规范

所有主数据变更事件遵循统一格式：

```json
{
  "event_type": "master_data.changed",
  "entity_type": "customer",
  "action": "created|updated|deleted|activated|deactivated",
  "tenant_id": "uuid",
  "master_data_id": "uuid",
  "source_service": "crm",
  "timestamp": "2026-07-22T12:00:00Z",
  "payload": {
    "id": "uuid",
    "code": "CUST001",
    "name": "示例客户",
    "category": "vip",
    "status": "active"
  },
  "version": 1
}
```

### 4.3 同步策略矩阵

| 主数据域 | 同步模式 | 延迟要求 | 冲突解决 | 补偿机制 |
|---------|---------|---------|---------|---------|
| 客户 | 异步事件 | < 5s | 时间戳优先 | 对账任务每日执行 |
| 供应商 | 异步事件 | < 5s | 时间戳优先 | 对账任务每日执行 |
| 物料 | 异步事件 | < 10s | 版本号优先 | 库存冻结校验 |
| 组织/部门 | 异步事件 | < 5s | 层级校验 | 级联更新通知 |
| 员工 | 异步事件 | < 5s | HRM 为准 | 权限回收任务 |
| 会计科目 | 同步调用 | 实时 | Finance 为准 | 关账期禁止变更 |

> **会计科目特殊处理**：会计科目在月结/年结期间不允许变更，采用同步调用 + 分布式锁确保强一致性。

### 4.4 消息队列 Topic 设计

```
exchange: topems.master-data
├── routing_key: master.customer.{tenant_id}.{action}
├── routing_key: master.supplier.{tenant_id}.{action}
├── routing_key: master.material.{tenant_id}.{action}
├── routing_key: master.organization.{tenant_id}.{action}
├── routing_key: master.employee.{tenant_id}.{action}
└── routing_key: master.account_subject.{tenant_id}.{action}
```

## 五、服务边界

### 5.1 主数据服务职责边界

```
┌─────────────────────────────────────────────────────────────────────┐
│                        MDM 服务边界                                  │
├─────────────────────────────────────────────────────────────────────┤
│  CRM          │  客户创建/更新/删除/查询、客户分类、客户画像         │
│  SRM          │  供应商创建/更新/删除/查询、供应商评估、准入管理    │
│  ERP          │  物料创建/更新/删除/查询、BOM、物料分类             │
│  HRM          │  组织/部门/员工创建/更新/删除/查询、组织架构        │
│  Finance      │  会计科目创建/更新/删除/查询、科目体系、辅助核算    │
├─────────────────────────────────────────────────────────────────────┤
│  其他业务服务  │  只读引用（通过本地副本缓存或实时查询），禁止写操作  │
└─────────────────────────────────────────────────────────────────────┘
```

### 5.2 API 契约规范

主所有权服务必须暴露以下标准接口供其他服务查询：

```
GET /api/{service}/master/{entity}/{master_data_id}   # 按 ID 查询
GET /api/{service}/master/{entity}?code={code}         # 按编码查询
GET /api/{service}/master/{entity}/batch               # 批量查询（POST）
GET /api/{service}/master/{entity}/changes?since={ts}  # 增量变更查询
```

响应格式：
```json
{
  "master_data_id": "uuid",
  "code": "CUST001",
  "name": "示例客户",
  "tenant_id": "uuid",
  "version": 3,
  "created_at": "2026-01-01T00:00:00Z",
  "updated_at": "2026-07-22T12:00:00Z",
  "attributes": { /* 扩展属性 */ }
}
```

### 5.3 禁止行为清单

| 禁止行为 | 说明 | 违规示例 |
|---------|------|---------|
| 跨服务写主数据 | 只有主所有权服务可以执行 CREATE/UPDATE/DELETE | SCM 直接创建客户 |
| 绕过 MDM ID 关联 | 业务表之间的关联必须使用 `master_data_id` | 订单表用 `customer_code` 外键 |
| 跨租户引用 | 禁止在业务逻辑中引用其他租户的主数据 | A 租户订单关联 B 租户客户 |
| 静默缓存不一致 | 依赖服务必须监听变更事件更新本地副本 | WMS 缓存物料 7 天未更新 |

## 六、数据治理

### 6.1 主数据质量规则

| 规则 | 说明 | 校验时机 |
|------|------|---------|
| 编码唯一性 | 同一租户内主数据编码必须唯一 | 创建/更新时 |
| 名称非空 | 主数据名称不能为空 | 创建/更新时 |
| 状态有效性 | 状态只能是预定义枚举值 | 创建/更新时 |
| 层级完整性 | 组织架构必须形成完整树，不能有孤儿节点 | 更新时 |
| 科目平衡 | 会计科目变更需校验借贷平衡 | 月结前 |

### 6.2 数据清理策略

- **软删除优先**：主数据删除采用软删除（`deleted_at`），保留历史引用完整性。
- **归档机制**：超过 2 年未变更的主数据自动归档到历史表。
- **编码回收**：删除后主数据编码保留 180 天锁定期，防止误复用。

## 八、风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 存量数据编码冲突 | 高 | 实施前全局扫描编码重复，制定重编码方案 |
| 同步延迟导致业务错误 | 中 | 关键路径采用同步查询 + 本地缓存双保险 |
| 消息队列故障 | 高 | 消费端记录同步偏移量，恢复后重放；关键数据定期对账 |
| 服务拆分后查询性能下降 | 中 | 依赖服务维护本地副本表，读操作走本地查询 |
| 开发人员不习惯 MDM 规范 | 低 | Code Review 强制检查 + 自动化测试覆盖 |

## 九、验收标准

| 验收项 | 标准 |
|--------|------|
| AC-1 | 6 大主数据域均有明确的主所有权服务 |
| AC-2 | 主数据变更事件格式统一，通过 RabbitMQ 发布 |
| AC-3 | 依赖服务能在 10 秒内收到主数据变更通知 |
| AC-4 | 主数据编码在租户范围内全局唯一 |
| AC-5 | 跨服务关联使用 `master_data_id` 而非业务编码 |
| AC-6 | 存在主数据质量监控看板和对账机制 |
