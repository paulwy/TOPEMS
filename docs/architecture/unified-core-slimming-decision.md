# unified-core 继续瘦身决策（P0-2）

> 状态：✅ 决策已出（2026-09-17）· 关联：[架构演进与待办清单](./architecture-evolution-and-todo.md)、[物理库拆分预案](./database-split-plan.md)、[模块化单体设计](./modular-monolith-design.md)

## 1. 背景与决策问题

架构已演进为**模块化单体**（`svc/server` :8099 统一入口，31+ 模块嵌入，unified-core 以 `build_router_embedded` 嵌入）。P0-2 的决策问题是：**doc / flow / file 是否外迁为独立服务，给出明确决策与排期**。

## 2. 现状盘点（2026-09-17 实测）

| 模块 | 代码规模（行） | 引用表（仅本域 + 共享层） | 跨域直读 | 外部调用方 |
|---|---|---|---|---|
| iam | 7,828 | core_* 认证/用户/角色 | 无 | 全部服务（认证核心） |
| flow | 5,313 | core_workflow_* ×4 + approvals/approval_records | 无 | **14 个跨库调用方**（最大依赖面） |
| audit | 3,104 | core_audit_* | 无 | 观测型，被动 |
| file | 2,442 | core_files / core_file_permissions | 无 | 多服务上传/下载 |
| tenant | 2,372 | core_tenant_* | 无 | 平台核心 |
| master | 1,974 | core_master_* | 无 | 多服务引用主数据 |
| doc | 1,543 | core_doc_* ×4 | 无 | 文档管理域 |
| automation | 1,285 | core_automation_* | 无 | 编排域 |
| 其余 | ~6,800 | 各域自身表 | 无 | — |

**关键事实**：
1. doc / file **表层完全自包含**（仅 core_* 共享层 + 自身域表），crate 边界独立——技术外迁成本最低。
2. flow **表层自包含，但 API 依赖面广**（14 个调用方，此前 workflow 拆分专项已确认"流程引擎是拆分最大成本"）。
3. 物理拆分预案 6 项阈值**全未触发**（DB 0.1GB / portal 116 表 / 连接 1 / 跨 schema 直读清零 / 备份秒级 / 拓扑无缺口）——单库维持中。
4. core_* 留 public 作为**平台共享层**是既定设计（SaaS/本地/DSH 三模式共用），unified-core 各模块表均遵循该分层。

## 3. 决策

**维持模块化单体嵌入，不独立拆进程**（与物理拆分预案联动，阈值未达成）。同时做边界固化与拆分候选标记：

| 模块 | 结论 | 依据 |
|---|---|---|
| doc | **阶段 2 首选拆分候选**（低耦合） | 仅 4 张 core_doc_* 表、零外部业务表依赖、crate 边界独立；外迁仅需搬 crate + 路由前缀 |
| file | **阶段 2 首选拆分候选**（低耦合） | 仅 2 张 core_file_* 表，同为低耦合基础设施模块 |
| flow | **拆分后置项**（需 API 收敛前置） | 表层自包含，但 14 个调用方需全部改走 API/事件（integration 直写改 API 编排已完成，服务间认证已统一）；前置条件满足后再评估 |
| iam / tenant / master | **永不外迁** | 认证与租户边界是平台核心，外迁无收益且破坏 RLS/审计一致性 |

## 4. 触发条件与排期

- **立即（已落地）**：边界固化——doc/file 标记为可拆分候选；flow 持续收敛调用方（服务间认证统一、集成事件化已完成，剩余依赖面收敛随 P1/P2 治理推进）。
- **阶段 2 联动**：物理拆分阈值达成（任一指标：DB >10GB / portal 表数超阈值 / 活跃连接 >400 持续 10min / 跨 schema 查询 >30% / 备份 >15min）时，**先拆 doc/file**（低耦合快速见效），flow 在调用方接线收敛后作为第二批。
- **独立排期**：无（完全随物理拆分阶段 2 联动，避免重复建设独立进程运维）。

## 5. 风险与回退

- **风险**：提前外迁 flow 将付出 14 调用方适配成本且无规模收益；doc/file 外迁若在单库阶段完成，收益有限（仍是同一 PostgreSQL），仅在拆分触发时执行才有意义。
- **回退**：doc/file 均为 crate 级边界，外迁后如需回退可直接改回嵌入，无数据迁移（同库）。
