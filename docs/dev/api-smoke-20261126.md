# 接口层冒烟（OpenAPI 驱动）

页面巡检只能覆盖"用户点到过的那条链路"，前端兜底还会把接口异常吃成空表。这份冒烟直接按
`GET /api/openapi.json` 的清单逐条发 GET，回答一个更基础的问题：**声明过的接口，现在有几条真的能打通。**

脚本：`scripts/ci/api-smoke.mjs`（Node 18+，无第三方依赖）。

## 用法

```bash
node scripts/ci/api-smoke.mjs                                  # 全量（916 条，无路径参数的 GET）
node scripts/ci/api-smoke.mjs --module wms,mes --json /tmp/x.json
node scripts/ci/api-smoke.mjs --limit 100 --concurrency 3 --retry 1
```

参数：`--base`（默认 `http://127.0.0.1:8099`）、`--module`、`--limit`、`--concurrency`（默认 3）、
`--retry`（默认 2）、`--timeout`（秒，默认 20）、`--json`。退出码 0 无 FAIL / 1 有 FAIL / 2 脚本级错误。

判定口径：

| 判定 | 条件 | 含义 |
| --- | --- | --- |
| FAIL | 5xx（501 除外） | 后端真异常 |
| FAIL | 404 且文案含「接口不存在 / 路径」 | OpenAPI 声明了但路由没挂上 |
| SOFT | 400 / 403 / 409 / 422 / 501 | 业务校验、权限、显式未实现，不算缺陷 |
| SKIP | 401 | 鉴权失败，通常是测试环境缺租户头 |
| DEGRADED | 5xx 且文案是 `pool timed out` / `事务开启失败` / `开启租户作用域失败` | 连接池打满，容量信号，不算接口逻辑坏了，不进退出码 |

## 为什么要降并发 + 重试

首轮用并发 8，跑出 24 条 FAIL，其中 13 条是假红：日志里成片
`pool timed out while waiting for an open connection` / `事务开启失败`。
8099 的物理池只有 18 个连接（`[db-budget] … 物理池 18`），8 并发 × 每条请求都开 RLS 事务，
跨模块聚合查询一叠加就把池打穿。

所以默认改成**并发 3 + 5xx/超时重试 2 次（退避 1.5s、3s）**。确定性 500 三次都挂，照样判 FAIL；
只有瞬时抖动会被重试吸收。重试仍撞上池超时的 5xx 归到 DEGRADED，单列一行提示，不污染判负结果
（WMS 的 `abc-analysis`/`age-pareto` 在全量跑里偶发这一条，单跑 38/38 OK，属典型容量抖动）。

## spec 路径别名表

`docs/api/openapi.json` 是生成的基线文件（`registry.rs` 用 `include_str!` 内嵌），并行会话会重新生成它。
因此**不直接改 spec**，而是维护 `scripts/ci/openapi-path-aliases.json`：冒烟按别名打到真实路由，
结果里标 `[别名→…]`。新增漂移就往表里加一条，同时把 `#[utoipa::path]` 注解改对，
下次生成就不会再写回旧路径。

## 首轮结果与修复

首轮（并发 8）：`916 条 OK=833 SOFT=59 FAIL=24`。逐条复测定性后，24 条拆成三段：

**13 条假红**——连接池打爆，降并发后自动消失。

**6 条真 500**，全部修好（提交见文末）：

| 接口 | 根因 | 修法 |
| --- | --- | --- |
| `/api/crm/dashboard` | `AVG(EXTRACT(EPOCH …))` 返回 NUMERIC，Rust 侧按 f64 解 | 聚合外层 `::float8` |
| `/api/finance/aging/detail` | 不传 `direction` 时落到 `erp_receivables`，但 SQL 按 payable 列名取 `payable_no` | 表名补 `finance.` 前缀 + 只取两表共有的 `amount/due_date`，姓名列按方向取 `customer_name`/`supplier_name` 再统一别名 `party_name` |
| `/api/mobile/patrol-records` | `checked_by` 列是 `character varying`，绑定参数是 UUID → `operator does not exist: character varying = uuid` | 模型字段与绑定统一按文本（列本身就是文本） |
| `/api/portal/notifications` | BFF 复用了挂着 `x-system-channel: service_token` 的 client，只换了 Authorization，下游判定"用户身份声明系统通道"→403；换新 client 后又漏传 `x-tenant-id` →400 | 用用户 token 时新建 client，并把 `x-tenant-id` 透传 |
| `/api/rd/formulas` | `rs.formulas.created_by` 是 UUID，结构体按 TEXT 解 | SELECT/RETURNING 统一 `created_by::text AS created_by`；写入参数 `$17::uuid` |
| `/api/rd/reports/projects/performance` | 空集上 `SUM(...)` 返回 NULL，`Row::get` 直接 panic（`UnexpectedNullError`） | `COALESCE(SUM(...), 0)` |

顺带修了日志里暴露的 `/api/erp/customers`：`customer_type` 列可为 NULL，读取模型改成 `Option<String>`
（创建请求仍保持必填）。

**5 条 spec 漂移**——不是代码缺失，是 `docs/api/openapi.json` 里的路径过期，实际路由换个名字就在：

| spec 里写的 | 实际路由 |
| --- | --- |
| `/api/communication/notification/channels` | `/api/communication/notification/push-config/channels` |
| `/api/communication/notify/list` | `/api/communication/notification/notify/list` |
| `/api/core/users` | `/api/core/iam/users` |
| `/api/ehs/occupational-health/exam-plans` | `…/check-plans` |
| `/api/ehs/occupational-health/exam-records` | `…/check-records` |

处理：`#[utoipa::path]` 注解改成真实路径，并在
`scripts/ci/openapi-path-aliases.json` 里登记别名（改 spec 文件会被并行会话重新生成覆盖，别名表不会）。

## 修复后复跑

`916 条  OK=857  SOFT=59  FAIL=0  DEGRADED=0`，判定 OK（退出码 0）。
6 条真 500 全部 200，5 条 spec 漂移由别名表兜住，WMS 全模块 38/38 OK。

另修 WMS `discrepancy` 汇总：`SUM(...)` 空集为 NULL 且 `discrepancy_quantity` 是 NUMERIC，
补 `COALESCE(...,0)::float8`，不再在日志里刷「获取差异汇总失败」。

## 已知缺口（未在本轮修）

- **前端通知模块与后端契约错位**：`apps/web/src/api/notification/*.ts` 里有 100 处
  `apiClient.notification.xxx('/notification/...')`。这个子客户端的 baseURL 已经是
  `/api/communication/notification`，再加一层 `/notification` 变成
  `/api/communication/notification/notification/...`；把前缀剥掉后只有 2 条能在当前 spec 里找到。
  也就是说这批调用（channels / deliveries / digests / webhooks / topics / providers …）
  对应的后端接口**根本没实现**，页面靠兜底显示空表。要么补后端端点，要么把这批前端模块标记为未启用——
  属于功能缺口，不是本轮能靠改路径解决的。
- **WMS 聚合接口对连接池敏感**：`abc-analysis`、`inventory-turnover`、`location-utilization`
  在并发压测下会拖垮池子。冒烟已用低并发+重试规避，但生产侧并发上来仍有风险，值得单独压测。

## 与其他检查的关系

- 列表一致性（`check-list-page-consistency.mjs`）：页面「总数 > 0 但 0 行」。
- 页面健康（`check-page-health.mjs`）：5xx / console error / 白屏，走浏览器。
- 接口冒烟（本脚本）：只看接口本身，不依赖页面，能抓到"页面没入口、接口已经坏了"的那批。
- 总闸 `pnpm verify:frontend` 暂未并入本脚本（需要后端在跑，跑一轮约 3 分钟）。
