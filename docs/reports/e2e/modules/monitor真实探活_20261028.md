# monitor 真实探活改造（2026-10-28）

> 状态：✅ 已闭环并实测
> 范围：`svc/monitor` 的 `/api/monitor/health`（服务健康）从 16 服务静态 mock 改造为真实探活。
> 背景：TODO 📋「pm response_time degraded 监控项」——根因 = /health 为静态 mock（16 服务硬编码数据，150.3ms 系占位非真实探活）。

## 一、改造前现状

| 项 | 改造前 | 改造后 |
|---|---|---|
| 服务清单 | 16 个硬编码（topems-iam/crm/.../ai） | 实时读取 BFF 模块注册表（当前 31 模块） |
| status | 硬编码（如 pm=degraded 150.3ms） | 注册 = healthy；BFF 不可达 = down/degraded（如实标记） |
| response_time | 假数据（12.5~150.3ms 占位） | 实测 HTTP 探活耗时 |
| uptime | 假字符串（"2d 5h 30m"） | 真实进程运行时长（state.start_time） |
| id | `Uuid::new_v4()`（每请求随机） | 稳定 UUID（确定性 hash(服务名)，跨请求/跨进程一致） |

## 二、设计

**模块化单体下 16 服务 = 进程内模块（无独立端口）**，网关级探活是唯一真实度量面：

1. `AppState` 新增 `bff_url: String`（探活目标；env `MONITOR_BFF_URL` 或默认 `http://localhost:8099`）；embedded（server `monitor_real_module.rs`）与 standalone（`svc/monitor/src/main.rs`）两构造点同步。
2. `get_service_health` 真实探活流程：HTTP GET `{bff_url}/api/server/health`（5s 超时）→ 解析 `module_list`（真实模块注册三元组 name/group/version）→ 每模块生成一条 `ServiceHealth`（status=healthy、response_time=实测延迟、uptime=真实进程时长、id=稳定 UUID）。
3. **失败语义**：BFF 不可达（连接错误）→ 返回 `bff-gateway` down 条目；HTTP 非 2xx / 模块清单为空 → degraded 条目；均保留 envelope 结构，不做空壳。
4. 纯函数（`determine_health` / `classify_response_time` / `format_uptime`）与单测保持不变。

## 五、边界

- **粒度**：monolith 单进程下为「网关级探活」（BFF + 模块注册 + DB 探活——DB 在 `/api/monitor/infrastructure` 已真实 SELECT 1）。各模块无独立端口/独立 health 端点，无法做进程内逐模块延迟；若未来拆分独立服务，可扩展为按端口探活。
- **down 场景**：嵌入式（monitor 与 BFF 同进程）时 BFF 挂则 monitor 同时挂，down 分支主要在 standalone（8095 独立端口 + MONITOR_BFF_URL 指向他处）时触发；代码已覆盖。
