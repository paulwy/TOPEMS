### 2.3 D3 · 层级 invalidateQueries（合规率 0%）

**样本分布**：409 个 mutation 中 289 个（70.7%）调用了 `invalidateQueries`，但 **289/289 全为 exact：清精确 key 未清层级**。

**现状样例（exact only，抽样 6 条，共 289 处）**

| 文件                                   | 行              | 当前写法（反模式）                                       | 问题                                                                                                                                |
| -------------------------------------- | --------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `components/feedback/FeedbackList.tsx` | 108             | `invalidateQueries({ queryKey: ['feedbacks'] })`         | exact 清 `['feedbacks']`，但列表页实际 key 是 `['feedbacks', filters]` → **不会失效！** 新建反馈后列表不刷新（缓存泄漏 bug 已潜在） |
| `components/templates/CrudPage.tsx`    | 433 / 453 / 473 | 三处 `invalidateQueries({ queryKey: [schema.entity] })`  | 同上，CRUD 模板实际 key 是 `[schema.entity, page, pageSize, sort, filters]` → 保存后第一页刷新、其他分页陈旧                        |
| `hooks/useCode.ts`                     | 241 / 255       | `invalidateQueries({ queryKey: ['code-reservations'] })` | 预约号列表带 search 参数 → exact 匹配失败，保存后不刷新                                                                             |

**`_def` 前缀现状检查**：

```
grep '_def\s*:' apps/web/src/lib/reactQuery.ts  →  0 条命中
```

Code Wiki §4.4 参考写法 `invalidateQueries({ queryKey: QUERY_KEYS.hrm.employees._def })` 目前尚未在 QUERY_KEYS 中落地。**下午修复采用兼容方案（不新增字段）**：把所有精确匹配改为 `exact: false` 层级匹配：

```ts
// 修复后规范写法
queryClient.invalidateQueries({
  queryKey: QUERY_KEYS.SYSTEM.FEEDBACK._BASE, // 或 QUERY_KEYS.FINANCIAL_REPORTS.BALANCE_SHEET._BASE
  exact: false,
  refetchType: 'active',
});
```

等价的 `exact: false` 对 289 处的收益更大（**不等待 QUERY_KEYS 扩容即可修复**）。

**附带风险**：120 个 useMutation **完全未调用 invalidateQueries**（409-289=29.3%）—— 典型：`pages/admin/PermissionAuditPage.tsx` 的 `deletePermission`、`pages/bi/BIComparisonPage.tsx` 的 `saveComparison` 提交后无清缓存动作，用户看到旧数据。下午 PR 中一并要求每个 mutation **至少有一次 invalidateQueries 或明确 `queryClient.setQueryData` 乐观更新**。

### 2.4 D4 · isPending 装载态（严格合规率 0.6%；宽松 19.5%）

**现状拆解（基于 grep + 人工抽样）**

| 类别                                                    | 计数                                                                  | 抽样代表                                                                                                                                                  |
| ------------------------------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 🟢 `isPending`（标准）来自 useQuery                     | **2**（仅在 snippet 模板中出现！真实 useQuery 解构 **为 0**）         | `utils/ai/code-completion.ts:179` AI Copilot snippet `{ data, isPending, error } = useQuery`                                                              |
| 🟡 `isLoading`（兼容别名）来自 useQuery                 | **63**                                                                | `components/templates/CrudPage.tsx:416`、`FeedbackList.tsx:99`、`FinancialReports.tsx:1270` 等；另外模板/DashboardTemplate/各模块 Page 的解构形态基本一致 |
| 🟠 自定义 `useState<boolean>(false) loading` / `loaded` | **52**                                                                | 散落 `components/ReportViewer.tsx`、`pages/finance/*` 等 — 通常配合 `useEffect(() => { setLoading(true); fetch().finally(() => setLoading(false)) })`     |
| 🔴 `data === undefined / null` 判空推断加载             | **4**（全部在 `common/types/normalize_response.stub.ts`，非业务页面） | 可忽略                                                                                                                                                    |

**严格合规率结论**：**0/334 = 0.0%** 真实业务页面按 Code Wiki 使用 `isPending`。宽松把 isLoading 计"半合规"则 63/334 = 18.9%。

**isLoading → isPending 语义差距说明**：

- v5 `isLoading = isPending && isFetching` 是「首次加载」子集
- Code Wiki 统一 `isPending` 的原因：Skeleton 应该在 **首次 + 筛选 refetch（URL 参数变 → staleTime 到 → 后台在取）** 都显示轻微 loading 指示器；若仅用 `isLoading`，用户改筛选条件时 UI 会"数据不变但没提示"，造成静默假象

**样例修复前后**（63 处统一批量正则替换模式）：

```diff
- const { data, isLoading } = useQuery({ … })
+ const { data, isPending } = useQuery({ … })
- {isLoading && <Skeleton />}
+ {isPending && <Skeleton />}
```
