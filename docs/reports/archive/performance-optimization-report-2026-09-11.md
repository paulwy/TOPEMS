## 二、发现的性能优化点

### 2.1 高优先级（立即优化）

#### P-01: SELECT * 查询返回过多数据

**位置**:
- `svc/analytics/src/modules/bi/row_level_permission.rs:610`
- `svc/erp/src/modules/master_data_lifecycle.rs` (多处)

**问题**:
```rust
// row_level_permission.rs:610
let query = format!("SELECT * FROM {} LIMIT $1 OFFSET $2", req.table_name);

// master_data_lifecycle.rs (多处)
r#"SELECT * FROM erp.erp_master_data_refs WHERE master_data_id = $1"#
```

**影响**:
- 返回不需要的列，增加网络传输和内存使用
- 表结构变更时可能导致应用错误
- 无法有效利用覆盖索引

**优化建议**:
1. 明确指定需要的列名，避免使用 SELECT *
2. 对于动态表名查询，考虑使用列名白名单
3. 对于大表，考虑使用分页和延迟加载

**优先级**: 高

---

#### P-02: 缺少慢查询日志监控

**位置**: PostgreSQL 配置

**问题**:
- `log_min_duration_statement = -1`，慢查询日志未启用
- 无法及时发现生产环境的慢查询
- 缺少性能问题的早期预警机制

**影响**:
- 生产环境出现性能问题时难以定位
- 无法量化查询性能的变化趋势
- 缺少优化效果的验证手段

**优化建议**:
1. 启用慢查询日志：`log_min_duration_statement = 1000`（1秒）
2. 配置日志轮转，避免日志文件过大
3. 定期分析慢查询日志，识别性能瓶颈
4. 考虑使用 pg_stat_statements 扩展监控查询性能

**优先级**: 高

---

### 2.2 中优先级（近期优化）

#### P-03: 索引维护和优化

**发现**:
- 开发环境中部分索引未被使用（统计信息未充分收集）
- 缺少索引使用情况的定期监控
- 可能存在冗余索引或缺失索引

**优化建议**:
1. 定期分析索引使用情况：
   ```sql
   SELECT schemaname, relname, indexrelname, idx_scan, idx_tup_read, idx_tup_fetch
   FROM pg_stat_user_indexes
   WHERE idx_scan = 0
   ORDER BY pg_relation_size(indexrelid) DESC;
   ```
2. 删除长期未使用的冗余索引（需谨慎，先确认）
3. 为常用查询条件添加合适的索引
4. 定期运行 `ANALYZE` 更新统计信息
5. 考虑使用部分索引和表达式索引优化特定查询

**优先级**: 中

---

#### P-04: 数据库连接池配置

**发现**:
- 未检查后端服务的数据库连接池配置
- 高并发场景下可能出现连接耗尽
- 缺少连接池监控和调优

**优化建议**:
1. 检查并优化 sqlx 的连接池配置：
   - `max_connections`: 根据数据库最大连接数设置
   - `min_connections`: 保持一定数量的空闲连接
   - `acquire_timeout`: 连接获取超时时间
   - `idle_timeout`: 空闲连接超时时间
2. 监控连接池使用情况，及时调整配置
3. 考虑使用 PgBouncer 作为外部连接池（生产环境）
4. 避免在事务中执行耗时操作，减少连接占用时间

**优先级**: 中

---

#### P-05: API 响应时间优化

**发现**:
- 未进行系统性的 API 响应时间监控
- 部分聚合查询可能响应较慢
- 缺少缓存机制

**优化建议**:
1. 添加 API 响应时间监控中间件
2. 对常用查询结果添加缓存（Redis 或内存缓存）
3. 优化聚合查询，避免全表扫描
4. 考虑使用异步处理耗时操作
5. 实现查询结果分页，避免返回大量数据

**优先级**: 中

---

### 2.3 低优先级（长期优化）

#### P-06: 查询性能优化

**优化建议**:
1. 定期分析慢查询执行计划：
   ```sql
   EXPLAIN ANALYZE SELECT ...;
   ```
2. 优化复杂查询，避免子查询嵌套过深
3. 使用 CTE（WITH 子句）提高查询可读性和性能
4. 考虑使用物化视图加速复杂聚合查询
5. 对大表考虑分区表（按时间或租户分区）

**优先级**: 低

---

#### P-07: 数据库维护

**优化建议**:
1. 定期运行 `VACUUM ANALYZE` 清理死元组并更新统计信息
2. 定期重建索引，减少索引碎片
3. 监控数据库增长趋势，提前规划存储
4. 配置自动备份和恢复测试
5. 考虑使用 PostgreSQL 性能扩展：
   - `pg_stat_statements`: 查询性能统计
   - `pg_buffercache`: 缓冲区缓存分析
   - `pgstattuple`: 表和索引的详细统计

**优先级**: 低

---

#### P-08: 应用层性能优化

**优化建议**:
1. 避免 N+1 查询问题，使用批量查询或 JOIN
2. 使用数据库连接池，避免频繁创建连接
3. 合理使用事务，避免长事务
4. 对热点数据使用缓存
5. 实现请求限流，防止突发流量压垮数据库
6. 使用异步处理非关键路径操作

**优先级**: 低

## 四、性能监控建议

### 4.1 关键监控指标

| 类别 | 指标 | 告警阈值 |
|------|------|----------|
| 数据库 | 慢查询数量 | > 10/分钟 |
| 数据库 | 连接池使用率 | > 80% |
| 数据库 | 缓存命中率 | < 95% |
| 数据库 | 锁等待时间 | > 1 秒 |
| API | P95 响应时间 | > 2 秒 |
| API | P99 响应时间 | > 5 秒 |
| API | 错误率 | > 1% |
| 系统 | CPU 使用率 | > 80% |
| 系统 | 内存使用率 | > 85% |
| 系统 | 磁盘 I/O 等待 | > 100ms |

### 4.2 监控工具建议

1. **数据库监控**:
   - pg_stat_statements: 查询性能统计
   - pgBadger: 日志分析工具
   - Prometheus + Grafana: 指标监控和可视化

2. **应用性能监控 (APM)**:
   - OpenTelemetry: 分布式追踪
   - Jaeger / Zipkin: 链路追踪
   - Sentry: 错误监控

3. **日志管理**:
   - ELK Stack (Elasticsearch + Logstash + Kibana)
   - Loki + Grafana
