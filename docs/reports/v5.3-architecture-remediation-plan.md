## 二、Phase 1：后端路由前缀标准化（P0）

### 2.1 问题描述

各服务的路由路径缺乏统一规范：
- **finance** 服务使用 `/accounts`, `/vouchers` 无前缀
- **pm** 服务使用 `/api/plugin_pm.*` 点号分隔格式
- **erp** 服务越权提供 `/api/finance/*` 路由

### 2.2 目标

所有服务统一使用 `/api/{service_name}/` 前缀格式

### 2.3 实施步骤

#### 步骤 1：Finance 服务路由前缀修复

**影响文件**:
- `svc/finance/src/main.rs`
- `svc/finance/src/api/*.rs`

**实施**:
1. 修改 `main.rs` 中的路由注册，添加 `/api/finance` 前缀
2. 更新所有 handler 路径
3. 更新 `moduleMapping.ts` 中的映射

**验收标准**:
- `cargo build` 编译通过
- 所有路由访问 `/api/finance/accounts` 可正常响应
- 前端 API 调用路径更新后功能正常

**回滚策略**:
- 恢复 `main.rs` 路由注册
- 恢复 `moduleMapping.ts` 映射

---

#### 步骤 2：PM 服务路由前缀修复

**影响文件**:
- `svc/pm/src/main.rs`
- `svc/pm/src/api/*.rs`

**实施**:
1. 将 `/api/plugin_pm.budgets/*` 改为 `/api/pm/budgets/*`
2. 更新所有子模块路径
3. 更新 `moduleMapping.ts`

**验收标准**:
- `cargo build` 编译通过
- 所有路由访问 `/api/pm/*` 可正常响应
- 前端 PM 模块功能正常

**回滚策略**:
- 恢复 `main.rs` 路由注册
- 恢复 `moduleMapping.ts` 映射

---

#### 步骤 3：ERP 服务路由清理

**影响文件**:
- `svc/erp/src/main.rs`
- `svc/erp/src/api/finance.rs`

**实施**:
1. 将 ERP 中的 finance 路由迁移到 finance 服务
2. 删除 ERP 中重复的 `/api/finance/*` 路由
3. 更新 `moduleMapping.ts`

**验收标准**:
- `cargo build` 编译通过
- 财务相关 API 仅由 finance 服务提供
- 无重复路由冲突

**回滚策略**:
- 恢复 ERP 中的 finance 路由
- 恢复 `moduleMapping.ts` 映射

---

## 五、Phase 4：前端 API 层统一（P1）

### 5.1 问题描述

`apps/web/src/api/` 同时存在扁平文件和嵌套目录：
- `api/hrm.ts` — 旧版 API 封装
- `api/hrm/` — 新版分文件 API

### 5.2 目标

统一 API 定义方式，消除混淆

### 5.3 实施步骤

#### 步骤 1：API 定义方式决策

**决策**: 采用嵌套目录结构作为标准，扁平文件作为兼容层

**实施**:
1. 确认每个模块的 API 定义方式
2. 选择嵌套目录作为标准格式
3. 扁平文件保留为 re-export 层

---

#### 步骤 2：API 文件统一

**影响文件**:
- `apps/web/src/api/*.ts`（扁平文件）
- `apps/web/src/api/*/`（嵌套目录）

**实施**:
1. 对于同时存在扁平文件和嵌套目录的模块：
   - 以嵌套目录为准
   - 修改扁平文件为 re-export，从嵌套目录导入
2. 对于只有扁平文件的模块：
   - 按功能拆分到嵌套目录
   - 修改扁平文件为 re-export
3. 删除纯重复的扁平文件

**验收标准**:
- 每个模块仅有一套 API 定义（嵌套目录）
- 扁平文件仅作为 re-export 层
- `npx tsc --noEmit` 编译通过
- 所有 API 调用功能正常

**回滚策略**:
- 恢复扁平文件的原始内容
- 删除嵌套目录（如适用）

## 六、Phase 5：Module Federation 架构决策（P1）

### 6.1 问题描述

项目设计了完整的 Module Federation 架构，但实际上所有远程模块都指向 `empty-remote.ts` 占位文件，`apps/*` 子项目都是空壳。

### 6.2 目标

做出明确决策：要么启用，要么移除

### 6.3 实施步骤

#### 步骤 1：决策评估

**评估标准**:
- 团队资源是否支持独立部署和维护
- 当前架构是否需要微前端分离
- 性能和可维护性权衡

**决策选项**:
- **选项 A**: 启用 Module Federation — 开发独立部署能力
- **选项 B**: 移除空壳子项目 — 简化为单体应用

**推荐决策**: 选项 B（移除空壳子项目）

---

#### 步骤 2：移除空壳子项目

**影响文件**:
- `apps/core/`
- `apps/hrm/`
- `apps/crm/`
- `apps/finance/`
- `apps/pm/`
- `apps/mes/`
- `apps/scm/`
- `vite.config.ts` 中的 Module Federation 配置
- `apps/web/src/modules/empty-remote.ts`

**实施**:
1. 删除所有空壳子项目目录
2. 删除 `apps/web/src/modules/empty-remote.ts`
3. 修改 `vite.config.ts`，移除 Module Federation 配置
4. 修改 `REMOTE_MODULES` 相关配置

**验收标准**:
- `apps/core/`, `apps/hrm/` 等空壳目录不存在
- `cargo build` 和 `npx tsc --noEmit` 编译通过
- 前端应用正常运行，无路由加载错误

**回滚策略**:
- 从 git 历史恢复空壳子项目
- 恢复 `vite.config.ts` 配置

---

### 6.4 验收标准汇总

| 指标 | 目标值 |
|------|--------|
| 空壳子项目目录数 | 0 |
| Module Federation 残留配置 | 0 |

## 七、Phase 6：Vite 代理配置简化（P2）

### 7.1 问题描述

`vite.config.ts` 的 proxy 配置超过 1200 行，包含大量重复模式：
- SCM 模块有 20+ 个单独的路径规则
- 每个服务都有 `/api`、`/health`、`/plugin-health` 三套规则

### 7.2 目标

简化代理配置，提高可维护性

### 7.3 实施步骤

#### 步骤 1：服务级代理规则合并

**影响文件**:
- `apps/web/vite.config.ts`

**实施**:
1. 创建通用代理配置函数，支持服务名和端口参数
2. 替换每个服务的三套规则（`/api`、`/health`、`/plugin-health`）为通用函数调用
3. 合并 SCM 等模块的重复路径规则为前缀匹配

**验收标准**:
- proxy 配置行数减少 50% 以上
- 所有代理规则功能与之前一致
- 前端 API 调用正常

**回滚策略**:
- 恢复原始 proxy 配置
