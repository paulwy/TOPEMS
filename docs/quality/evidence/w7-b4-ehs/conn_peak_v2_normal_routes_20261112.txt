## 1. 采样方法（与 v1 同一口径，仅提高采样频率）

```sql
-- /tmp/ehs_conn_bench/watch_fast.sql，psql -At 从 stdin 喂入
select clock_timestamp()::text || '|' || count(*) || '|'
     || count(*) filter (where state='active') || '|'
     || count(*) filter (where state like 'idle in transaction%') || '|'
     || coalesce(string_agg(pid::text || ':' || state, ',' order by pid), '')
  from pg_stat_activity
 where datname='topems_conn_bench'
   and pid<>pg_backend_pid()
   and backend_type='client backend';
\watch 0.001
```

- `peak_inflight` 取**同一条采样行**的 `active + idle_tx`，不做分别取最大值相加。
- 只统计 `backend_type='client backend'`：排除 parallel worker（会继承 application_name 且 state=active）与采样自身。
- 每条路由：预热 2 次 → 启动采样 → 顺序发 30 次（health 系 200 次）→ 停止采样 → 解析。
- 本库未额外放大（不做 20 万行 ILIKE、不加 pg_sleep 触发器），改以“1ms 采样 + 多次重复 + 命中样本可复核”保证可观测性；命中样本行（peak_sample）随各用例给出。

驱动脚本：`/tmp/ehs_conn_bench/run_case.sh`；解析：`/tmp/ehs_conn_bench/parse2.py`。

## 3. 逐路由对照

| 路由（实际路径）        | 基线峰值 conns/active/idle_tx/inflight | 当前峰值 conns/active/idle_tx/inflight | 基线 N → 当前 M | 判定 |
|-------------------------|----------------------------------------|----------------------------------------|-----------------|------|
| GET /api/ehs/issues     | 3 / 1 / 1 / **2**                      | 3 / 1 / 2 / **2**                      | 2 → 2           | 无变化（2→2） |
| GET /api/ehs/accidents  | 3 / 1 / 1 / **2**                      | 3 / 1 / 2 / **2**                      | 2 → 2           | 无变化（2→2） |
| GET /api/ehs/training   | 3 / 1 / 1 / **2**                      | 3 / 1 / 2 / **2**                      | 2 → 2           | 无变化（2→2） |
| POST /api/ehs/issues    | 3 / 1 / 1 / **2**                      | 3 / 1 / 2 / **2**                      | 2 → 2           | 无变化（2→2） |
| GET /api/ehs/health-monitor | 不存在（公共 /health 早退）        | 3 / 1 / 2 / **2**                      | —（新增受保护路由） | 仅此路由为 2 条 |
| GET /health（公共）     | 3 / 1 / 0 / **1**                      | 3 / 1 / 0 / **1**                      | 1 → 1           | 无变化 |

要点：

- 四条普通业务路由基线**本来就是 2 条**：`tenant_middleware` 的请求事务（`idle in transaction`）+ handler 自己的查询连接（`active`）。当前版本只是把 handler 连接从“池直连”换成“只读作用域事务”，条数不变。
- 当前版本采样到 `peak_idle_tx=2`（如 `cur_get_training`、`cur_post_issues` 的峰值样本为 `0 active + 2 idle in transaction`）：`ScopedTxn` 未自定义 Drop，drop 后由 sqlx 异步 rollback，上一请求的只读事务在响应返回后仍短暂占连接，与下一请求的中间件事务重叠。**顺序压测下同时持有峰值仍为 2**，未出现 3。
- `GET /health` 两边都是 1 条：该路径仍在 `public_routes`、仍命中 `is_public_path` 早退，没有被本次改动影响。真正变成 2 条的只有改名为 `/api/ehs/health-monitor` 的受保护路由。
