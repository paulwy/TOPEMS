## 0. 摘要

八个已暴露问题不是八个独立缺陷，而是三条结构性缺失在不同层面的投影：

| 共因 | 一句话 | 直接解释的簇 |
|---|---|---|
| **M1 契约缺位** | 类型统一 ≠ 语义统一：`RlsTxnCell` 收敛了"签名的名字"，没收敛"谁提交 / 失败如何传播 / 部分成功如何表达" | 簇 1、簇 3、簇 4 |
| **M2 债转股** | 基线把"阻断"置换为"通行权"，债务被冻结且可自助刷新，门禁从质量闸门退化为变更记录器 | 簇 2、簇 3、簇 4 |
| **M3 真相源缺位** | 文档、账本、统计三者的"当前事实"都没有可执行来源，全部依赖一次性人工普查 | 簇 5、簇 6、簇 7、簇 8 |

先做的 4 件事（详见 §6）：**T-3 离线可编译 → T-1 单一事实源 → P-1 核销制 → M-1 事务所有权单一化**。四者有严格依赖顺序，不能并行抢跑。

对"同类问题为何在多个服务反复出现"的直接回答（§4.1）：不是人不细心，而是 **18 个服务各自手写进程引导**、**共享库只收敛类型名不收敛调用路径**、**门禁只按服务计数不检查不变量** 三件事叠加，使"每服务一份"成为合法选项。最极端的证据是同一个 `write_scope` 在 finance 是数据库事务、在 unified-core 是权限范围（§2.3）。

### 1.2 关键口径澄清：`own_txn` 不是代码标识符

后来人最容易误读的一点：仓库里 **`grep own_txn` 命中数为 0**。`own_txn` 是 [check-request-txn.mjs](../../scripts/ci/check-request-txn.mjs#L24-L32) 里的**门禁分类名**，定义是"请求路径自开事务"，统计模式为 `\.(scope|scope_read)\(\s*\)`；与之并列的 `bare_txn` 统计的是裸 `&mut **txn`。

因此：

- "own_txn 954" = 仍有 954 处 `.scope()` / `.scope_read()` 调用（会各自 `BEGIN` 一条新连接）；
- "bare_txn 1656" = 仍有 1656 处 `&mut **txn` 直接查（跳过模块 schema 域与 `SET LOCAL`）；
- 两者之和 2610 才是"事务写法债"的总量，二者不可相加后当作"文件数"或"函数数"。

同理，"`set_var` 从 16 处降到 1 处"的**统计范围是 `svc/server/src/modules/*_real_module.rs`**，不是全仓。全仓 `set_var` 仍大量存在（多数在 `#[cfg(test)]` 内），且 `SEARCH_PATH` 的 `set_var` 仍分布在 18 个 `svc/*/src/main.rs`。**统计范围不写清楚，数字就会被当成另一件事**——这本身就是簇 6 的一个实例。

### 2.1 从这张表能读出什么

1. **漂移不是单向的**：有的数字变大（180→63 类）、有的变小（1109→1021）、有的口径被换掉（590→1656）。说明不是"某次改完忘了更新"，而是**每次统计都用了一次性脚本+人工抄写**，没有稳定口径。
2. **同一概念存在多个母集**：`--changed-only`（58）与全量（63）、`*_real_module.rs`（1）与全仓、308 键与 1535 条。文档不写母集，读者只能猜。

### 2.2 一处必须自我修正的读数

本文前一版把"118 处 / 17 文件"记成"文档滞后，实际 122 处 / 18 文件"。复核后确认**文档是对的**：

```
grep -rnE "(write|read)_scope\(\)" --include="*.rs" svc lib | cut -d/ -f2 | sort | uniq -c
  118 finance
    4 shared-db
```

118 处全部在 `svc/finance`（跨 17 文件），另 4 处是 `lib/shared-db` 的通用实现。把两者相加得到 122 / 18，是把"某个服务的私有包装"与"共享库的通用实现"混进同一个母集——**我犯的正是本文批评的那个错误**。保留这段，因为它证明：口径不写在文档里时，连复核者也会得出第二个错误数字。

### 2.3 同名不同义：`write_scope` 在两个服务里是两件事

继续核对时发现一个更危险的事实：**同一个函数名在仓库里承载了两种完全不同的语义**。

| 位置 | 签名 | 语义 |
|---|---|---|
| [svc/finance/src/services/finance/mod.rs#L60-L66](../../svc/finance/src/services/finance/mod.rs#L60-L66) | `async fn write_scope(&self) -> Result<ScopedTxn<'_>, TopemsError>` | **数据库事务**（自开连接） |
| [svc/unified-core/src/modules/iam/tenant_scope.rs#L66-L79](../../svc/unified-core/src/modules/iam/tenant_scope.rs#L66-L79) | `pub fn read_scope(claims: &Claims) -> Result<IamScope, ScopeError>` | **权限范围**（IAM 判定，与数据库无关） |

后果：任何按名字做统计、检索或"统一改造"的动作（包括本文 §2 的统计、门禁脚本、以及未来的机械替换）都会把这两者混为一谈。这是"同一机制演化出多套写法"的极端形态——不是两套实现，而是**同名不同义**。

## 3. 八个问题簇

### 簇 1｜双事务模型与多套写法

**结论（【已核实】）**
事务的"所有权"没有单一裁决者。当前同一条请求链上存在三层可独立提交的事务：

1. 中间件请求事务（`Extension<Arc<Mutex<Option<Transaction>>>>`，由 `tenant_middleware` 在响应后 `commit/rollback`）；
2. `Db` 自开事务（[scope.rs](../../lib/shared-db/src/scope.rs#L66-L216) 内 8 个 `pub async fn`：`scope_read` / `scope` / `scope_read_system` / `scope_system` / `scope_read_for_tenant` / `scope_for_tenant` / `scope_with` / `scope_savepoint`）；
3. service 层包装 `write_scope()` / `read_scope()`（122 处 / 18 文件），内部再次落到第 2 层。

`RlsTxnCell` 统一的是**类型别名**（226 个文件、1845 处引用），它让 13 个服务的签名长得一样，但**没有回答三个语义问题**：谁负责 commit、失败如何向上传播、部分成功如何表达。K12/K13/K14 正是这三个问题各自的具体形态：

| 台账 | 语义冲突 | 为什么"类型统一"解决不了 |
|---|---|---|
| K12 | 明细已提交 + 聚合"最佳努力"忽略失败 | 需要业务决定"聚合失败是否回滚明细"，这是口径不是类型 |
| K13 | 提交后发事件 vs 复用请求事务后"事件早于数据可见" | 需要"提交后回调"这一新机制（已试点 `PostCommitQueue`） |
| K14 | 逐行独立事务 + 部分成功 | 需要 SAVEPOINT（已落地 `scope_savepoint`） |

**证据**
- 门禁当前值：`bare_txn=1656`（7 服务：crm 196 / erp 351 / hrm 232 / rd 163 / scm 211 / srm 211 / wms 292）、`own_txn=954`（19 个服务 > 0，ai 90、mes 203、lims 144、mobile 133、gis 92、unified-core 87、ticket 65…）。
- 三套入口并存：[scope.rs](../../lib/shared-db/src/scope.rs#L66-L216)；[known-gate-defects.md K14](../database/known-gate-defects.md#L118-L134) 记录了对 `scope_with` 生命周期的放宽以支持复用。
- 语义分歧：[K12](../database/known-gate-defects.md#L92-L101)、[K13](../database/known-gate-defects.md#L103-L116)、[K14](../database/known-gate-defects.md#L118-L134)。
- 方案侧已承认这是"口径与验收判据"问题而非机制问题：[scope-with-plan-20261116.md#L9](../database/scope-with-plan-20261116.md#L9)（"`scope_with` 已经是现成的正确抽象…要解决的是收敛口径与验收判据"）。

**影响**
- 同一 handler 内的写入可能落在两条连接、两个事务上：外层非 2xx 回滚不会回滚内层已提交的写入（[TODO §17.2](../TODO.md#L720-L731)）。
- 写请求峰值占用 2 条连接，与各服务 `max_connections=2` 叠加后，高并发先出现池等待。
- 任何"按服务逐个改"的动作都会制造第三种状态（部分 handler 走请求事务、部分自开），使判据无法一次跑全（[scope-with-plan §5](../database/scope-with-plan-20261116.md#L144)）。

**对应建议**：M-1、M-3、P-3。

### 簇 2｜382 条 RLS 策略「未设上下文即放行」

**结论（【引用】+【推断】）**
RLS 策略是按迁移时点、各服务各写的方式生长的。早期模板把"未设 `app.tenant_id` 就返回全表"当作兼容后台任务的逃生口，此后 W7 只对**新策略**和**被点名的表**收口（`pm.projects` 已是正确态），382 条历史策略从未回填。**【引用】** 策略分类取自 [K10](../database/known-gate-defects.md#L60-L77)、[scope-with-plan §7](../database/scope-with-plan-20261116.md#L151-L191) 的只读 `pg_policies` 盘点；**【推断】** "从未回填"的原因是回填成本（逐表确认业务语义）远高于登记成本，且单租户环境不产生验收压力（见簇 7）。

**证据**
- 1030 条 `SELECT/ALL` 策略中 962 条含租户谓词：**579** 有逃生口且未设即拒（正确）、**370** 无逃生口且未设即放行、**12** 双旁路叠加、**1** 安全但系统通道不可用、**68** 非租户谓词（[K10 表格](../database/known-gate-defects.md#L63-L71)）。
- 反例谓词：`rs.projects` 为 `current_setting(...) IS NULL OR tenant_id IS NULL OR tenant_id = '000…0'`，未设 GUC 直接返回全表（[scope-with-plan §7](../database/scope-with-plan-20261116.md#L178-L179)）。
- 代码侧同源风险：`tenant-context` 门禁 R2 规则统计"modules 内直接使用 `state.pool`"，基线 **104 文件 / 1094 处**（`scripts/ci/tenant-context-baseline.json`，generated_at 2026-11-12）。这些调用不走 `Db::scope*`，不会写入 `app.tenant_id`，正是 382 条策略的触发面。

**影响**
- 一旦出现"事务未带 `app.tenant_id` 却查了租户表"，这 382 条不会 fail-closed。当前请求链由 `tenant_middleware` 强制写 GUC，故线上未观测到实际泄漏；风险集中在后台任务、异常路径、事件处理器与新增的裸 `pool` 查询。
- 更隐蔽的后果：它让"RLS 是兜底"这一前提在代码审查中**不成立**——审查者以为有兜底，实际 382 张表没有。

**对应建议**：M-2、T-1（策略分类必须进事实源脚本）。

### 簇 3｜门禁长期只停留在报警层

**结论（【已核实】）**
门禁被设计成**防新增（ratchet）**，而不是**促偿还（burn-down）**：基线自证式（`--update-baseline` 可在本地自助刷新）+ 只减不增 + 存量全绿。三者叠加的必然结果是：存量债务不可见；一旦变红，最低成本动作是刷基线而不是修代码；覆盖范围还可能保留试点遗留。

**证据**
- schema-prefix 本次实跑：1535 条违规**全部"基线内"**，新增 0，`exit 0`。也就是说这个门禁"绿"只证明"今天没有人多加一条"，不证明 308 个键里有多少已该删除。
- 硬失败只覆盖两个高危级别：[check-schema-prefix.mjs#L288-L292](../../scripts/ci/check-schema-prefix.mjs#L288-L292) 的 `HARD_FAIL_LEVELS = {AMBIGUOUS, CROSS_SCHEMA}`，本次实测两者均为 0——**门禁的"有效信号"实际已归零**，因为唯一会阻断的两类已经清零，剩下 1535 条全是永不阻断的基线。
- 覆盖残缺：[lefthook.yml#L151-L156](../../lefthook.yml#L151-L156) 的 `txn-write-non2xx` 触发条件是 `^svc/scm/.*\.rs$`，scm 以外的服务改动根本不触发检查，所以 58/63 处存量长期不可见（K11 已指出"仅 scm 看起来是试点遗留"）。
- 基线可自助刷新：[check-request-txn.mjs](../../scripts/ci/check-request-txn.mjs#L1-L38) 提供 `--update-baseline`；schema-prefix 同样提供 `--update-baseline`。两者都没有"降级需审批/需工单号"的约束。
- 同类先例：K6 的 `ledger-ddl-drift` 原先在"无 `_sqlx_migrations`"时打 NOTE 后 `exit 0`，修成 fail-closed 后立刻暴露真实缺口（[K6](../database/known-gate-defects.md#L5-L37)）。这说明**门禁的价值取决于它是否可证伪**，而不取决于它有多少条规则。

**影响**
- 门禁提供的是"变更记录"而非"质量闸门"，管理层的"门禁全绿"结论不可用于发布判定。
- 一旦某次改动确实引入新债，团队学到的经验是"再刷一次基线"，形成负向激励。

**对应建议**：P-1、P-2、T-1。

### 簇 4｜迁移/基线账本无人核销

**结论（【已核实】）**
账本只有"写入"路径，没有"核销"路径。`schema-prefix-baseline.json`、`request-txn-baseline.json`、`tenant-context-baseline.json`、`txn-write-non2xx-allowlist.json`、`checksums.txt` 都是"只能加、没人删"的结构：没有 owner、没有复核日期、没有复跑证据命令，也没有"谁有权删一条键"的规则。

**证据**
- schema-prefix 基线从 326 键刷到 308 键，其中 **16 条是上游早已收敛、账本无人核销的陈旧键**。**本次补充实测**：把现有 308 键与当前 1535 条违规做差集，`stale = 0`——说明那 16 条已在 326→308 这次刷新中被人工清理。但这恰恰证明缺口存在：仓库里**没有 stale 检测脚本**，这个 0 是本次手工算出来的（见 §7 命令），而不是门禁持续保证的性质；下一次出现陈旧键，仍然只能等某个人想起来去查。
- `txn-write-non2xx-allowlist.json` 只有 **3 条** allowlist，而全量扫描命中 **63 处**——账本与真实缺口差 60 条，说明这份 allowlist 从未被当作待办清单维护。
- `tenant-context-baseline.json` 头部写"只允许下降"，但 `lefthook.yml` 注释里的 1764 与基线实际 1094 不一致（§2），说明连"基线自身的历史"都没人核对。
- K6 的修复说明给出正面样本：只有在"无账本"时 fail-closed，才能发现"目标库根本不是本仓库迁移链"这类问题。

**影响**
- 陈旧键会让后续读者误判风险面（"还有 308 个问题"里有 16 个是假的）。
- 真实缺口（60 条未登记的非 2xx）不会进入任何人的待办，因为"没有条目 = 没有问题"。

| 簇 | M1 契约缺位 | M2 债转股 | M3 真相源缺位 |

| 6 统计靠人工 | — | 辅助：基线数字被当作事实引用 | **主因**：无可复跑统计层，数字写入即脱离代码 |

**读法**：每一簇都有一条约 60%~70% 的解释力来自单一共因，另两条提供放大效应。这意味着修复不应按簇平铺（8 条并行），而应按共因切（3 条主线 + 1 条前置），否则会在不同簇里重复解决同一个问题。

### 4.1 横切问题：同类缺陷为何在多个服务反复出现

这是原问题清单里最值得单独回答的一条，因为八个簇里有六个都表现为"同一缺陷的 N 份副本"。机制上有三件事共同作用：

1. **每个服务都手写自己的进程引导**。18 处 `set_var("SEARCH_PATH", ...)` 分布在 17 个服务的 `main.rs`（unified-core 两处：`main.rs` + `embedded.rs`；analytics / crm / ehs / erp / finance / hrm / lims / master-data / mes / monitor / plugin-registry / qms / rd / scm / srm / wms），`shared-bootstrap` 虽然提供了统一入口，但**没有任何编译期约束阻止服务绕过它**。引导逻辑一旦是"每服务一份"，其中的错误也必然是 N 份。
2. **共享库只收敛了"类型与函数"，没收敛"调用路径"**。`RlsTxnCell` 让 226 个文件的签名一致，但 `.scope()` / `&mut **txn` 仍可在任意 handler 里出现；`write_scope` 甚至在不同服务里是不同语义（§2.3）。统一了类型名之后，**缺陷从"编译不过"变成了"编译通过但语义不同"**——这比编译错误更难发现，也更容易复制。
3. **门禁按"服务计数"而不按"模式检查"**。`check-request-txn` 的基线键是 `svc::kind`（如 `wms::bare_txn`），它度量的是"每个服务还剩多少处"，不是一个"请求内是否只允许一条事务"的**不变量**。按服务计数只能告诉你哪家债多，不能告诉你某种写法是否还被允许——所以同一个错误可以继续在没被点名的服务里新增，只要不越过它的计数上限。

对照证据：

| 现象 | 实测 | 含义 |
|---|---|---|
| 自建 JWT 中间件 | 仅 `plugin-registry` 1 家（其余 25 家共用共享实现） | 说明"共享有覆盖"的地方确实没复制（K9 是唯一漏网的） |
| `bare_txn` 分布 | 7 个服务 / 150 文件 / 1656 处 | 集中在"当年各自接入请求事务中间件"的那批服务，接入方式是复制 |
| `SEARCH_PATH` 引导 | 18 个 `main.rs` 各自 `set_var` | 引导层从未收敛，是复制的最底层来源 |
| 同名不同义 | `write_scope` 在 finance=事务、unified-core=权限 | 复制过程中名字被复用，但语义已分叉 |

结论：**"反复出现"不是人不细心，而是架构允许"每服务一份"存在，且门禁只数数量、不查不变量。** 修复这类问题必须靠"让错误写法无法通过编译"（M-1 的 newtype），而不是靠"再多加一条按服务计数的门禁"。

## 6. 「建议先做的 4 件」

结论：**认可 M-1、P-1、T-1、T-3 这四件**，但需修正两点——**（a）四者有严格依赖顺序，不是并行四件；（b）M-3 必须并入 M-1 同批，不得缺席。**

### 执行顺序与理由

| 顺序 | 项 | 为什么是这个位置 | 解锁什么 |
|---|---|---|---|
| 1 | **T-3 离线可编译** | 唯一"纯配置、零业务风险、当天可验证"的一条；在它之前，`svc/server` 的任何改动都无法机器校验，M-1 改到 server 侧时等于盲改 | 解锁整个聚合层的类型/契约校验；让后续所有"验证通过"结论对 server 也成立 |
| 2 | **T-1 单一事实源** | M-1 与 P-1 都需要"当前真值"作为分母。没有它，M-1 的收益无法度量（`own_txn` 从 954 降到多少算完成？），P-1 的 `evidence_cmd` 也无处可引 | 提供 §2 全部数字的可复跑来源；为 P-1/T-2 提供证据命令库 |
| 3 | **P-1 核销制** | 成本最低、见效最快：先实现 `--check-stale`，用历史 326 键快照复现出 16 条 STALE 作为回归样本，即可证明机制有效（当前 308 键 STALE 已为 0）。它也是"账本从通行证变债务清单"的第一步，直接对冲 M2 | 让 308 键 / 1656 / 954 从"数字"变成"带 owner 和期限的待办"；让陈旧键从"等人工发现"变成"自动报出" |
| 4 | **M-1 事务所有权单一化（含 M-3）** | 解锁面最大：K11（写后非 2xx）、K12（聚合事务）、K13（提交后发事件）、K14（部分成功）都以它为共同前置。但代价也最高，且必须建立在 T-3（可编译）+ T-1（可度量）+ P-1（有账本）之上 | 一次性消除"两套事务入口"这一整类问题；`own_txn` 可从 954 收敛到"后台任务/显式租户遍历"的合法剩余 |

### 为什么把 M-2（RLS 382 条）排除在首批

- 它是**策略定义**变更，不是代码变更，需要逐表确认业务语义（370 条里既有真租户表，也可能有本应 owner 谓词的表）。
- 与 M-1 的变更面不同，同批会混淆边界，且 `scope-with-plan#L219` 已明确把它划到 W7 范围。
- 它没有"低成本前置"，唯一可行的降本手段是先让 T-1 把 382 条纳入事实源，使其可追踪下降，再按表分批。

### 一条补充建议（不计入 4 件）

把 §2 这张"文档数字漂移"表作为**第一次 `facts.mjs --check` 的验收用例**：T-1 落地后的第一天就能证明它有效，而不是等到下次审计。

### 9.24 M-1 事务所有权单一化（finance，2026-11-16）

finance 是本轮最大头：**6 处直接 `scope()/scope_read()` + 服务层 118 处 helper 间接自开事务 + 116 个服务方法 + 97 个服务间调用点 + modules 侧 161 个 handler 调用点**。如果只清 6 处直接命中，开守卫后 118 处 helper 会在运行期全部报「请求上下文禁止自开事务」，所以必须一次做完。

**根因**：`FinanceService` 每个写方法内部都在 helper 里 `self.db.scope()`，方法之间还互相调用（`create_voucher` → `generate_voucher_no` / `get_account_by_code`），事务边界散落在方法内部，handler 完全不知情。

**方案（沿用仓库既有范式，settlement_center/service.rs）**：

1. **服务方法末参数追加请求事务**：`txn: &mut sqlx::Transaction<'static, sqlx::Postgres>`，helper 改为 `async fn write_scope<'a>(&'a self, txn: &'a mut Transaction<'static, Postgres>) -> Result<ScopedTxn<'a>, TopemsError>`，内部 `self.db.scope_with(txn)`；`read_scope` 同形。**没有**采用 `txn_arc: &RlsTxnCell` 参数——handler 已经持有 guard，再 lock 会自锁。
2. **借用分段**：`ScopedTxn::commit()` 对借用事务是空操作但会消费 self，只有 `commit()` 或 `drop` 才释放对 `txn` 的可变借用。因此凡「读作用域 → 再调服务方法」「写作用域 → 再取号/查科目」的位置，插入 `scope.commit().await?` 作为分段点（语义不变，同一底层事务）。
3. **handler 侧**：`modules/` 下 161 个调用点补 `, txn`，无 guard 的 handler 统一补 `Extension(txn_arc)` + `Some(txn) else → 500 请求事务缺失`；已有 `scope_with` 的 handler（模板 toggle/match、对账明细更新）在调服务前先 `commit()` 释放借用。
4. **对账明细双作用域合一**：[reconcile_orders.rs](file:///Users/xingzhai/topems/svc/finance/src/modules/reconcile_orders.rs) 的 `update_reconcile_item` 原本「明细写 + 订单聚合」各开一次事务，现合并为同一请求事务（聚合失败仍按原逻辑忽略）。
5. **共享审计 helper 例外**：`submit_approval`/`approve`/`reject` 走 `topems_shared_db::approval::*_db`，该 helper 内部自己开审计作用域（lib 层，不在本服务账本内）。为不改变其行为，这三个 handler 传 `Db::new(state.pool.clone(), "finance, public, shared")`（**不**带守卫）；仅审计/日志，业务状态变更仍在请求事务内。
6. **最后一次守卫**：[main.rs](file:///Users/xingzhai/topems/svc/finance/src/main.rs) 的 AppState Db 补 `.deny_request_own_txn()`。

**踩坑与修正（都已消解，记录以免重犯）**：

- 批量脚本给 `f(a, b)` 插参数时判断错位（前字符是 `)` 而非 `,`）→ 改为按「内层是否空 / 是否以 `,` 结尾」决定插 `txn` / ` txn` / `, txn`；

- 带尾逗号的 `json!({...})` 实参被追加成 `, , txn`（2 处）→ 手工修成 `txn,` + 收尾括号。

### 9.25 search MCP 按租户隔离（2026-11-16）

§9.19 的 MCP 三个工具当时走 `scope_read_system()`，结果是「从恒失败变为返回全租户数据」。本轮按**方案 A（调用方显式携带租户）**收敛，与 `search_logs` 缺列缺陷分开处理。

**改动面**：[mcp.rs](file:///Users/xingzhai/topems/svc/search/src/mcp.rs) 三个工具 + [ai server.rs](file:///Users/xingzhai/topems/svc/ai/src/dsh/mcp/server.rs) 租户补齐。

| 项 | 处理 |
|---|---|
| 参数 | 三个工具 `inputSchema` 增加必填 `tenant_id`（string，UUID）；`search.global`/`search.documents` 必填 `["query","tenant_id"]`，`search.suggest` 必填 `["tenant_id"]` |
| 解析 | `extract_tenant_id(params, args)`：优先 `arguments.tenant_id`，兼容 `params._meta.tenantId`（MCP 标准元数据位） |
| 校验 | 缺失 / 空串 / 非 UUID → JSON-RPC `-32602 invalid_params`（带 `reason`），不再静默放行 |
| 作用域 | 三处 `scope_read_system()` → `scope_read_for_tenant(tenant_id)` |
| AI 侧 | `ext.search.search.*` 调用前，若参数无 `tenant_id`，用 `current_request_tenant()` 补齐（系统通道 `system=true` 不补，保持 fail-closed），LLM 无需感知租户 |

**两个要点**：

1. **未知工具先拦**。`handle_tools_call` 先判工具名白名单再解析租户，避免未知工具也要求 `tenant_id` 而把 `-32601` 变成 `-32602`。
2. **AI 桥接层是唯一补齐点**。search `/mcp` 不挂租户中间件（server token 内网面），租户只能来自调用方；AI 是仓内唯一调用方，在那里注入一次即可，其他外部调用方必须自己传。

**顺带修复**：`tools_list` 单测断言键名是 `input_schema`，而 `McpTool` 序列化为 camelCase（`inputSchema`），该断言此前一直失败（历史遗留），本轮改为 `inputSchema` 并追加「三个工具都必填 tenant_id」的断言。

**行为变化**：MCP 检索从「全租户」收紧为「调用方租户」；未传 `tenant_id` 的调用方会收到 `-32602`（含 AI 真实双进程 e2e 用例，已补 `REAL_MCP_TENANT_ID`，默认 `00000000-0000-0000-0000-000000000001`）。

**未修（登记）**：`public.search_logs` 缺 `query`/`tenant_id` 列（建议词频与最近搜索落库形状不符），属数据面缺陷，本轮不动迁移。
