## 2. 总体架构与演进

### 2.1 模块化单体 vs 独立服务：当前是"双轨并存"

TOPEMS 的目标形态是**模块化单体（Modular Monolith）**，但代码实测呈现**单进程聚合 + 独立进程两套形态并存**：

- **聚合形态**：`svc/server`（默认端口 8099）以**编译期 Cargo feature 门控 + main.rs 静态 `register_boxed`** 方式，把 28 个业务服务几乎全部嵌入单进程（`svc/server/Cargo.toml:67-104` default features 已含 gis/tms/ai/analytics/mobile/integration）。这不是运行期动态插件加载。
- **独立形态**：每个业务服务又可独立起进程（`svc/erp:8010`、`svc/finance:8011`…），nginx 网关 `deploy/nginx/topems.conf:79-110` 的 23 个 upstream **指向各独立服务端口，不指向 :8099**——本地（单体 :8099）与生产（nginx→各进程）流量路径不同，形成双轨。
- **"模块组间进程内 trait 调用"目标基本未达成**：`InProcProvider` 枚举仅 1 个变体 `AccountBalance`，实际只被 dashboard→finance 一条边使用（`svc/server/src/providers.rs:39-42`、`main.rs:44`）。portal→erp 等在单体内仍是指向 :8099 的环回 HTTP，而非进程内调用。

## 3. 服务拓扑与通信

### 3.1 依赖全景（HTTP / event / db 三类边）

跨服务通信实测为三种方式，**gRPC 实际零使用**：

- **同步 HTTP REST**：`reqwest` + 强类型 `TypedServiceClient<T>`，携带 JWT service token + 最小 scope。
- **异步事件**：Redis Stream（`XREADGROUP`/`XACK`/`XGROUP`），至少一次语义 + 消费组 + DLQ。
- **跨 schema 直连 DB**：当前仍为单 PostgreSQL 实例 + schema 隔离，物理库拆分是"预案"而非现实。

ENTRY §5b 列出 54 条边，各分片 §5 补充了 erp/scm/srm/pm/pdm、wms 组、advanced/ai、crm/finance 的细化边（含 ring 标记）。完整拓扑见 HTML 报告「图2 服务依赖拓扑」。

### 3.2 两条同步 HTTP 双环（高危）

| 环 | 正向 | 反向 | 证据 |
|---|---|---|---|
| **erp ↔ hrm** | erp→hrm 查员工/部门/公司（通讯录代理） | hrm→erp 薪酬推凭证 `POST /api/erp/vouchers` | `svc/erp/src/modules/addressbook.rs:200,208,216`；`svc/hrm/src/modules/payroll.rs:990` |
| **erp ↔ mes** | erp→mes 下推生产订单 `create_from_erp` | mes→erp 报工回传 `sync_mes_progress` | `svc/erp/src/modules/production_order.rs:536`；`svc/mes/src/modules/work_report.rs:644` |

**已排除的"伪环"**：qms↔lims↔ehs 互读对方 `XXX_SERVICE_URL` 仅出现在"向前端返回配置"的 handler（`svc/ehs/src/modules/data_sync.rs:523-526`），非后端发起的 HTTP，三者间实际同步走 Redis Stream 事件，不构成同步环。未发现 3 环及以上。

### 3.3 事件总线（Redis Stream 已落地）

`lib/shared-event` 机制层实测：默认 `EVENT_BUS_MODE=stream`（`publisher.rs:47-50`），初始化失败自动降级 Pub/Sub；`XREADGROUP/XACK/XGROUP CREATE` 落地（`stream_subscriber.rs:188,237,443`）；事件带 `EventVersion{major,minor}` 版本号（`versioning.rs:24-43`）；DLQ `topems:dlq` + retry_count（`dead_letter_queue.rs:11-17,61-89`）；**Schema Registry 已实现**（`schema_registry.rs:26-129`）——而 event-driven.md:439 仍将其标为"待办"。

### 3.4 gRPC 声明未用

workspace 声明了 `tonic 0.14`，`lib/shared-core/src/grpc/connection_pool.rs` 是唯一引用（连接池工具），**无任何 `svc/*` 发起 gRPC client**。全组（CORE/ERP/WMS/FCRM）`tonic|grpc` grep 均为 0。实际同步全走 HTTP REST。

### 3.5 网关 / BFF / 统一入口现状

- **nginx 双轨**：upstream 指向各独立服务端口（80xx），不指向单体 :8099（`topems.conf:79-110` vs `server/main.rs:539`）。
- **portal GraphQL BFF**：`Schema::build(QueryRoot,MutationRoot,SubscriptionRoot)`（`graphql_schema.rs:5490`），`business_stats` resolver 用 `tokio::join!` 并行扇出 erp/crm/hrm/finance/mes/workflow 六路，每路 `.unwrap_or(默认)` 优雅降级（`:891-907`）；经 9 个强类型 `TypedServiceClient`（`shared/mod.rs:26-34`）；DataLoader 仅局部（ServiceHealthLoader/TodoLoader），未成为全局 N+1 治理手段。
- **private/saas 空 feature**：`svc/server/Cargo.toml:162-164` 的 `private-deployment=[]`、`saas-deployment=[]` **均为空 feature（无依赖、无代码门控）**，全仓 `cfg(feature=...)` 零命中，`main.rs:28` 硬编码打印"private-deployment"——文档承诺的 SaaS/私有化双形态切换不存在。

## 4. 共享库设计（lib/）

### 4.1 主 crate + 11 子 crate

根 `Cargo.toml:2-16` 声明主 crate `lib` + **11 个子 crate**：`shared-core / shared-db / shared-auth / shared-service-client / shared-event / shared-observability / shared-ai / shared-bootstrap / shared-mcp / shared-dsh / shared-boundary`。（overview.md:6 称"12 个子 crate"为口径漂移，实为 11 子 + 主 crate = 12。）

### 4.2 门面保留（229 处 `use topems_shared::`）

`lib/src/lib.rs:2` 自陈"topems_shared 门面 Crate"，:5-8 记录 P1-R3 治理（2026-08-23）：**门面作为统一入口长期保留**。实测：`use topems_shared::` = **229 处**（186 文件 / 22 个服务目录）；22 个 svc 的 Cargo.toml 仍直接依赖门面，同时也直连子 crate（core=29、bootstrap=29、auth=29、db=25、event=23、boundary=15、service-client=12…）。即"去门面化"的真实形态是"**服务可直连子 crate**"，而非"拆除门面"。

> 门面内部最大耦合异味：`lib/src/form_assistant/` 栖身 **22 个业务表单文件**（crm_forms/erp_finance_forms/wms_forms…），业务域表单配置被放进"共享门面 crate"。

### 4.3 boundary 宏（3288 处 / 15 服务）

`only_own_schema_query!` 是**编译期**过程宏（`lib/shared-boundary/src/lib.rs:288-330`）：编译期解析 SQL 中 `FROM/JOIN/UPDATE/INTO/TABLE` 后的 `schema.table`，未授权即 `compile_error!`。默认放行 `public/unified_core/information_schema`（`:192`）。实测 **3288 处调用、分布 15 个服务**（finance=620、qms=300、erp=295、wms=239、integration=205、srm=203、hrm=207、scm=190、pm=169、gis=153、mobile=144、ehs=100、ai=125、communication=79、crm=5）。

### 4.4 boundary 的结构性缺口

- **opt-in**：服务写 `sqlx::query("SELECT...")` 不包裹宏即零编译期检查；
- **子查询逃逸**：宏对 `FROM (SELECT …)` 括号形态直接跳过（`extract_schema_refs` 遇 `(` 即 continue）；
- **unified-core 不受约束**：`schema_boundary.json` 中 unified-core `schema=public`、`search_path=public`，它**不依赖 boundary crate**，是最大的跨 schema 聚合点；
- **未接 boundary 的服务**：unified-core / monitor / search / master-data / analytics / ticket / server / plugin-registry。

## 5. 数据架构

### 5.1 Schema 划分：裸名 vs plugin_* 双命名并存

`database/migrations/000_create_schemas.sql` 实际创建**两套并行 schema**：裸名（`iam doc flow unified_core erp finance hrm crm ai pm rs lims pdm mes qms ehs scm srm wms gis im bi report mail mobile core shared`）+ 插件名（`plugin_erp … plugin_ai` 等 20 个）。但代码 SEARCH_PATH 实际用**裸名**（`erp, public` / `finance, public` / `ai, public`…），`database.md` 附录 A 称"erp→plugin_erp 已迁移完成"与代码不符。scm/srm/pm 的 SEARCH_PATH 残留 `shared` 但无实际引用。

## 6. 前端架构

### 6.1 Monorepo 物理结构

`pnpm@9.15.9` workspace（`pnpm-workspace.yaml:2-4` 声明 `apps/*`、`packages/*`、`tests/integration`），Node `^22`。**3 apps + 8 packages**：

- `apps/web`（name=`topems-portal`，v5.15.0）：Vite 8 + React 19 + MUI 9，**2863 个 `.ts/.tsx`**，是主门户。
- `apps/desktop`（v5.14.0）：Tauri 2 桌面壳，仅 **40 个**源文件。
- `apps/mobile`（v5.14.0）：Expo / React Native 0.73，**React 18.2**（与 web/desktop 的 19.2.7 不一致），48 个源文件。
- `packages/` 8 个：api-client / app-shell / business-tools-sdk / shared-components / shared-hooks / shared-types / shared-utils / tokens。

### 6.2 Module Federation 是空壳（19 remote 声明 / 0 实现）

- 构建用 Vite 8 + `@module-federation/vite`（**非 Webpack**）；默认 `DEPLOYMENT_MODE='static'`（`vite.config.ts:201-202`），static 下 `buildRemotes()` 返回 `{}`、federation 插件整体跳过（`:1398`）。
- `apps/web/src/microfrontend/config.ts:96-260` 声明 **19 个** `topems_*` remote（core/erp/hrm/crm/mes/scm/wms/srm/pm/finance/pdm/qms/lims/ehs/bi/monitor/ai/gis/doc），但 `apps/` 下**只有 web/desktop/mobile，无任何对应 remote app**；编译期仅 `topems_core` 一个（且 static 不生效）。
- `RemoteLoader` 动态字符串 import 在 static 下 entry 为空串必然 reject；`MicroAppRouter` 未被 App.tsx 使用；`/core/*` 渲染"Module Federation 未启用"占位页（`appRoutes.tsx:132-165`）。实际 2863 文件全部本地打进单 bundle，36 个业务域模块本地打包。
- 决策文档 `microfrontend-architecture-decision.md:5,7` 声称 `@module-federation/vite` **"已删除"**，但它仍是 `apps/web/package.json:59-60` 的构建硬依赖，且 vite.config.ts 为兼容它写了约 **850 行 / 5 个自研 workaround 插件**（CJS→ESM / null-byte / dayjs UMD / React 19 named exports）。

### 6.3 packages 依赖（14 条边）与复用率

- packages→packages 工作区依赖 **5 条**：app-shell→shared-types；shared-components→{shared-hooks,shared-types,shared-utils}；shared-utils→shared-types（单向向下，无环）。
- apps→packages 依赖 **9 条**：web→7（缺 business-tools-sdk）；desktop→2（api-client/app-shell）；mobile→**0**（完全自建 axios + RN 栈）。
- 复用率：tokens 被 **306** 个 web 文件引用（最高）；shared-components 83；shared-types 34；shared-hooks 仅 6；shared-utils 仅 3（自身 25 源文件沉淀不足）。`business-tools-sdk` 6 源文件**零外部消费方**（死代码）。本地 `apps/web/src/components/` 586 文件 vs 共享包 38 个 named export——组件沉淀严重不对称。

### 6.4 三端分裂

- **React 版本**：web/desktop 19.2.7、mobile 18.2.0；且 `tsconfig.base.json:44` 把 `react` 类型 alias 硬指向 mobile 的 `@types/react@18`，会让 web/desktop 的 React 19 类型检查被 18 类型污染。

### 6.5 根 build 链断裂与文档漂移

- 根 `package.json:21` `build:core = pnpm --filter topems-core build`，`build` 脚本（:26）串联 `build:core`——但 **`topems-core` 包在 workspace 中不存在**，任何开发者按 README 跑 `pnpm run build` 第三步必失败（CI 实际走 `frontend-build` job 单独 `--filter topems-portal build` 绕过，掩盖了问题）。

## 9. 安全架构

### 9.1 JWT 与 AES-256-GCM 版本化密钥

- **JWT**：`lib/shared-auth/src/auth.rs` 支持 HS256（`from_secret`）与 RS256（RSA PEM）双算法（`:70-80`）；生产（`PROFILE/RUST_ENV/ENV`）强制拒绝默认密钥并要求长度≥32（`:115,131,150-171`）。
- **字段加密**：`lib/shared-auth/src/security/encryption.rs` 用 **AES-256-GCM + 版本化密钥**（`key_version`，`:38,46,58`），支持轮换；base64 32 字节主密钥来自环境变量。
- 边界防护组件：audit_logger / body_limit / encryption / mask_sensitive / rate_limiter / security_headers。

### 9.2 RBAC 权限模型

跨服务调用用 JWT service token + 最小 scope（erp→hrm 带 `hrm:admin`、erp→finance 带 `finance:read`、ai MCP 带 `erp:read/write`）。但 **crm 全量业务路由共用单一粗粒度权限 `crm:admin`**（`svc/crm/src/main.rs:348` 叠加于全部 protected_routes），客户/商机/合同/售后/计费无法按操作细分授权。

### 9.3 RLS / 多租户

见 §5.5：finance 显式关闭 RLS；unified-core 会话 GUC 在连接池上不保证生效。审计日志公共表 `public.audit_logs` 被 crm 业务服务直查。

### 9.4 插件令牌门控与边界穿透点

- **插件注册令牌**：`svc/plugin-registry/src/modules/plugin/handlers/runtime.rs:18-31` `verify_registration_token`，`PLUGIN_REGISTRATION_TOKEN` + `X-Plugin-Token` 头校验；生产（PROFILE=prod/production）未配令牌直接拒绝——比文档更严，但门控依赖 `PROFILE=="prod"/"production"` **精确串**，若部署用 staging/未设则放行。
- **IP 白名单**：仅 `svc/portal/src/modules/gateway_security.rs` 实现，且 `deployment.yaml` 默认 `ip_whitelist_enabled: false`。
- **限流**：进程内内存 `RateLimitMiddleware`，bootstrap 硬编码 200 次/60s 按 IP（`shared-bootstrap/src/lib.rs:774`），多实例不共享（实际阈值×副本数）。
- **SSRF 面**：analytics datasource 可用用户给的凭据直连 `postgres://host:port` 跑 `SELECT 1`（`datasource.rs:165-196`），具备 analytics 权限者可探测/外联内网任意 DB。
- **边界穿透点汇总**：unified-core 跨读 22 schema（不受 boundary 约束）、search 裸读 erp、integration 直写 qms/ehs、crm 直读 public.audit_logs、srm 直写 unified_core——详见第 11 章问题清单。

## 10. 性能与容量风险

- **N+1 / 扇出**：portal GraphQL `business_stats` 用 `tokio::join!` 六路扇出（`graphql_schema.rs:891-907`），DataLoader 仅局部（health/todo），dashboard 类聚合对下游形成 6×N 次 HTTP。
- **同步调用环**：erp↔hrm、erp↔mes 双向环（§3.2），任一服务超时/重启即级联；erp 通讯录代理每请求同步调 hrm，hrm 慢/挂拖垮 erp。
- **无熔断 / 超时**：高频同步调用未配置熔断器与超时（erp 客户端未设 timeout；scm 例外加了 `TimeoutLayer(30s)`）；MCP 工具还存在手写阻塞式裸 TCP HTTP 客户端（`svc/ai/src/dsh/mcp/tools/mod.rs:317-364`，`std::net::TcpStream` 阻塞在 async runtime）。
- **内存壳服务**：master-data 10 个 v51–v60 模块全部内存 Store 不落库（重启即失）；analytics 领域 KPI 硬编码/随机假数据（`get_lims_summary` 字面量 856、`main.rs:883-884` `rand::random()`），ReportScheduler 邮件投递仅 `info!` 不发信。
- **假同步**：data_sync 模块读对方 URL 不发 HTTP（§1 WMS-03），点击"同步"只在本地插"成功"记录。

## 12. 架构优点与做得好的地方（客观平衡）

问题清单之外，本报告同样记录代码中**已落地、值得保留**的良好实践，避免只报问题不记建设：

1. **编译期 boundary 宏 3288 处 / 15 服务**：`only_own_schema_query!` 在编译期用 `compile_error!` 拦截跨 schema SQL，比运行期检查更早、零运行时开销，是这套架构最硬的一道防线（`lib/shared-boundary/src/lib.rs:288-330`）。
2. **事件驱动组内解耦已实质落地**：Redis Stream + 消费组 + DLQ（`XREADGROUP/XACK/XGROUP`）、至少一次语义、事件版本号 `EventVersion{major,minor}`、DLQ `topems:dlq` retry_count、Schema Registry 已实现（`schema_registry.rs:26-129`）——机制层完整且超前于文档。
3. **TypedServiceClient 治理跨服务调用**：`lib/shared-service-client` 用强类型 `TypedServiceClient<T>` 统一 JWT service token + 最小 scope + 超时，portal 经 9 个强类型 client 扇出（`shared/mod.rs:26-34`），比裸 reqwest 可控。
4. **统一 bootstrap 三段式**：`ServiceConfig→bootstrap_service→build_application→run` 收敛 28 服务启动，双轨（独立进程/单体嵌入）共享 `build_router_inner` 防路由漂移（V66.2）。
5. **插件自动注册与运行时门控**：`plugin-registry` 维护 manifest + SHA256 + runtime token 校验；生产未配注册令牌直接拒绝（比文档更严）。
6. **财务域治理相对成熟**：finance 已较好采纳 TopemsError（245 处）、落地事件溯源 + Saga（`domain/saga.rs`）、对账改本地快照+事件（V256），是错误处理与一致性的样板域。
7. **配置四源一致性门禁**：`scripts/check-workspace-registry.py` 三向校验 + 前端 CI `check-config-sources.cjs` 强制 services.yaml↔ports.env↔ports.ts↔vite.config.ts 一致。
8. **SQLx 离线缓存 + Cargo.lock 双锚点**：`.sqlx` 309 项入库支持 CI 纯离线编译，锁文件漂移已收口。
9. **门户优雅降级**：portal GraphQL 六路扇出每路 `.unwrap_or(默认)`，下游单点失败不拖垮首页（`graphql_schema.rs:891-907`）。
10. **安全底座完整**：JWT HS256/RS256 双算法 + 生产强制拒绝默认密钥、AES-256-GCM 版本化密钥可轮换、审计/限流/敏感信息脱敏/安全 headers 中间件齐备。
