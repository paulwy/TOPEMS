## 1. RLS 迁移设计

### 1.1 目标形态（统一 fail-closed，每表一条 `FOR ALL`）

```sql
DROP POLICY IF EXISTS rls_tenant_isolation ON ehs.<t>;
ALTER TABLE ehs.<t> ENABLE ROW LEVEL SECURITY;
ALTER TABLE ehs.<t> FORCE ROW LEVEL SECURITY;
CREATE POLICY rls_tenant_isolation ON ehs.<t> FOR ALL
  USING (
    COALESCE(current_setting('app.rls_system', true), 'off') = 'on'
    OR tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid
  )
  WITH CHECK (
    COALESCE(current_setting('app.rls_system', true), 'off') = 'on'
    OR tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid
  );
```

- `USING` 与 `WITH CHECK` **同形**，`FOR ALL`。
- 无 `tenant_id IS NULL`、无 `= ''`、无 nil 分支、无 `::text`。
- 前一策略若同名先行 `DROP`；其它历史策略名在同一 DO 块内按 `pg_policies` 逐一 `DROP`。
- 覆盖 70 张租户表：31 张从 RLS 关闭→ENABLE+FORCE，5 张补 FORCE，39 张重写策略；`schema_defense_ledger` **不碰**（保持关闭、0 策略）。

## 2. 事务边界（请求事务 vs `scope_for_tenant` 第二事务）

### 2.1 现状

- `tenant_middleware` 对每个受保护请求**开启一个事务**并 `set_config('app.tenant_id')`；超管必须带 `x-tenant-id`（缺失 400），中间件把值重写进 `claims.tenant_id`；service 身份走 nil + `app.rls_system='on'` 系统通道。
- EHS 写 handler 共 97 个，SQL 触达 pool 的 handler 166 个，其中：
  - **5 个已在请求事务内**（`scope_with`）：`environment.rs` `create_record`（RlsTxnCell L173 / scope L187）、`accident.rs` `start_investigation`（L584/L597）、`create_review`（L1022/L1035）、`create_incident_action`（L1134/L1147）、`training.rs` `create_certificate`（L1563/L1575）；
  - **7 个自开第二事务**（`risk.rs`，见 §0.2 #9）；
  - **其余写 handler 走裸池自动提交**，与请求事务不在同一连接，`app.tenant_id` 为空。

### 2.2 结论与改法

1. **fail-closed 后，裸池的读也会变 0 行**，不是只影响写。因此 208 处 `&state.pool` 必须全部改为作用域查询（读用 `scope_read_for_tenant`/`scope_read_system`，写用 `scope_for_tenant`/`scope_system`）。这是本批工作量主体。
2. **同一 handler 的父行 + 子行 + 状态流转必须在同一 scope 内**，禁止“父行用请求事务、子行用裸池”或“父行提交了、子行失败只记日志”。
3. 统一选择（不新增 ApiState 字段，沿用 WMS 写法）：
   - 写 handler：`let mut scope = db.scope_for_tenant(tenant).await?;`，所有语句 `&mut *scope`，最后 `scope.commit()`；
   - 已在请求事务内的 5 个 handler：保留 `scope_with`，但**其内所有 SQL 都必须用同一个 scope**（当前已满足，逐个复核）；
   - `risk.rs` 7 个 handler：删除手写 `pool.begin()` + `set_config`，改 `scope_for_tenant`；
   - 后台事件消费者（`event_handlers/mod.rs` 3 个 handler）：**不再写 nil 集成行、不再走 `scope_system`**；租户唯一来源 `payload.tenant_id`，缺失/nil → 丢弃事件 + 计数告警（`dropped_total`），非法由反序列化拦截；生产端（HRM/QMS/LIMS payload）必须写入 `tenant_id`（已给 4 个 payload struct 加 `#[serde(default)] tenant_id`）；
   - `schema_defense` 的 DDL 不经过 RLS，保持现状；但必须以表属主身份运行（生产 `topems_prod` 即属主）。
4. **禁止在一个 handler 里先 `scope_for_tenant` 再对 pool 读回响应**；提交后用同租户只读作用域或直接用提交前 `RETURNING` 的行组装响应。
5. 事务内统一使用 `rows_affected()`/`RETURNING` 判定，见 §6。

## 6. 验收矩阵与并发压测设计

### 7.9.2 A12 判据修正（期望值写错，不是系统问题）

原判据"≤ 启动前值 +1"是从 WMS 窗口抄的，但 **WMS 那次是热更新、连接池已预热**；EHS 这次是**冷启动，全部模块池新建**，两条基线不可比。实测 35 的来源：

- `lib/shared-bootstrap/src/lib.rs:1344-1358` `embedded_pool_limits()`：嵌入模式 `max = min(config.max_db_connections, DB_MODULE_MAX_CONNECTIONS|3)`、`min = DB_MODULE_MIN_CONNECTIONS|0`
- `lib/shared-bootstrap/src/lib.rs:831-836`：`DatabaseConfig{ max, min, ..Default::default() }` → `idle_timeout`/`max_lifetime` 未显式设置
- `lib/shared-db/src/database/mod.rs:66-72`：默认 `idle_timeout=120s`、`max_lifetime=600s`、`min_connections` 默认 5（此处被显式覆盖为 0），`:91-94` 应用到池
- plist 的 `DB_MAX_CONNECTIONS=8` 并非"完全不生效"：它作为 `default_max` 进入（`lib.rs:415` → `:1352`），随后被 `DB_MODULE_MAX_CONNECTIONS` 默认值 3 封顶

结论：`min_connections=0` + `idle_timeout=120s`，冷启动建满、空闲后收缩。旧进程只剩 8 条是十小时内未被访问的池已回收。**判据改为：启动后 ≤35、`idle_tx=0`、20 分钟内不增长，随后回落。**

## 附录 B · 5 张缺 `WITH CHECK` 表的现状与越权路径

5 张表（均 `ENABLE` 但 `FORCE=false`、owner=`topems_prod`、0 行、`tenant_id` 可空）。当前策略原文（5 张完全相同）：

```
policy = rls_tenant_isolation
cmd = ALL, permissive = true
USING = (current_setting('app.tenant_id', true) IS NULL)
     OR (current_setting('app.tenant_id', true) = '')
     OR (current_setting('app.tenant_id', true) = '00000000-0000-0000-0000-000000000000')
     OR (tenant_id IS NULL)
     OR (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
WITH CHECK = <NULL>
```

涉及表：`qa_ehs_compliance_evaluations`、`qa_ehs_discharge_permits`、`qa_ehs_env_monitor_records`、`qa_ehs_environment_incidents`、`qa_ehs_environmental_regulations`。

**实际可构造的越权路径**（按可达性排序）：

1. **属主绕过（生产当前真实路径）**：应用以 `topems_prod`（表属主，`rolsuper=f/rolbypassrls=f`）连接；`FORCE=false` 时 RLS 对属主完全不生效。可直接 `INSERT INTO ehs.qa_ehs_discharge_permits(tenant_id,...) VALUES('<T2>',...)`，同时 `SELECT *` 看到全部租户。
2. **GUC 未置位放行**：任何非属主角色，只要 `app.tenant_id` 为 NULL 或 `''`，第一/第二分支为真 → 全表可读可写。
3. **nil UUID 放行**：`app.tenant_id='00000000-...'` → 第三分支为真 → 全表可读可写。
4. **NULL 租户写入**：`tenant_id IS NULL` 分支允许插入/更新 `tenant_id=NULL` 的行；这些行之后对任何租户查询都不可见，形成孤儿数据。
5. **跨租户写入不被拦截**：`WITH CHECK` 为 NULL 时，PostgreSQL 对 `FOR ALL` 策略复用 `USING` 作为检查式；而 `USING` 本身 fail-open，因此上述任一放行条件下，写入 `<T2>` 行也成功。

**迁移后**：5 张表统一 `ENABLE + FORCE`，`USING` 与 `WITH CHECK` 同为
`COALESCE(current_setting('app.rls_system',true),'off')='on' OR tenant_id = NULLIF(current_setting('app.tenant_id',true),'')::uuid`。
复验构造：属主应用无 GUC 写 `<T2>` → `new row violates row-level security policy`；`app.tenant_id<T1>` 写 `<T2>` → 同样拒绝；`app.tenant_id<T1>` 写 `<T1>` → 成功。

- **原则：先改代码、最后翻 RLS**。RLS 迁移是最后一步；在此之前生产策略仍是 fail-open，因此任意批次的代码改造在线上都是“惰性”的，不会造成 0 行读取。
- 批次：
  1. **写路径优先**：`risk.rs`(7)、`hazard.rs`(11)、`accident.rs`(12)、`safety.rs`(7)、`environmental_compliance.rs`(6)、`training.rs`(4)、`emergency_drill.rs`(3)、`environment.rs`(2)、`health.rs`(2)、`integration.rs`(2)、`data_sync.rs`(1)、`hazardous_material.rs`(1)、`occupational_disease/health.rs`(各 1) → 61 处写 + 7 处 `begin` + 3 处 `scope_with` 复核。

- **兜底**：
  - 若某模块一次改不完：**不翻该模块相关表的 RLS**，整个生产窗口顺延；禁止“部分表 fail-open 上线”。

  - CI 门禁按文件基线单调下降；每批只降低对应文件基线，不一次性清零。
  - 紧急窗口若必须先行：在迁移里显式列“暂缓表清单”并记录到期日，**不作为默认方案**，需另行批准。

### M.2 三条可选路径（v2 重测后 M=N，降级为可选项，不再是窗口前置）

> M.1 v2 实测普通路由 **2→2**，不满足“M > N”的触发条件，本节不再作为进窗口的前置决策项；保留为可选优化清单，是否随窗口带 A/B/C 由用户裁决。

**方案 A：读路径单连接化（`scope_with(request_txn)` 复用中间件事务）**

- 做法：`tenant_middleware` 已 `BEGIN` 并注入 `RlsTxnCell`；对 `GET/HEAD` 在 `BEGIN` 之后、任何业务语句之前追加 `SET TRANSACTION READ ONLY`；读 handler 从 `scope_read_for_tenant` 改为 `state.db.scope_with(request_txn)`，不再自开事务、不自行 commit。
- 效果：读请求 `inflight 2 → 1`，池 2 时读并发 `1 → 2`；写路径完全不动。
- 代价/风险：要改中间件与读 handler；`SET TRANSACTION READ ONLY` 必须早于事务内任何查询；要逐 handler 确认没有写语句、没有自行 commit；214 处作用域取数需按读/写分类回归；跨租户 404 与回滚语义需重测。
- 前置条件：先做只读 handler 清单；中间件 commit/rollback 语义已确认；压测 20/50 并发；不改隔离级别。

**方案 B：池预算重分配（不改代码路径）**

- 现状算式：`embedded_pool_limits()` → `cap = min(模块请求 10, DB_MODULE_MAX_CONNECTIONS 默认 3) = 3`；嵌入总预算 `62 = 31 池 × DEFAULT_CONNECTIONS_PER_POOL(2)`；`reserve_pool` 授予 `min(3, 每池公平份额 2) = 2`。
- 可选：`DB_MODULE_MAX_CONNECTIONS=4` 且同步抬高 `DB_TOTAL_CONNECTION_BUDGET`（每池 +2 → 62 → 124）；或给 EHS 单独配额。
- 效果：池 4 → 读/写并发 2；但单请求仍是 2 条，只是分母变大。
- 代价：每 +1/池 = 进程级 +31 条 PostgreSQL 后端（31 个池），吃 `max_connections`、内存与 FD；生产 PG 需先确认 `max_connections` 余量；预算调大影响全部模块，不是 EHS 独占；需重启。
- 若“总量不变”只做重分配：公平份额公式是均分，单方面给 EHS 加 1–2 条必须从其它模块扣，代价是那个模块并发下降；当前 31 个池都在 2 条，扣谁都要业务确认。

**方案 C：EHS 读接口并发闸门**

- 做法：对 EHS 读路由加 `ConcurrencyLimitLayer` / 信号量（建议 = 池大小 / 2），超限快速返回 `429`，不再排队到 `pool timed out` 变 `500`。
- 效果：不增加吞吐，只把“超时 500”变成“快速 429”，保护尾延迟与连接池。
- 代价：需按池容量精确设阈值；客户端要处理 429；仍无法突破 2 条/请求的限制。

**建议**：A 是正解（真正把读请求降到 1 条），B 只作为窗口内临时容量（且需 PG 余量与重启），C 作为兜底闸门。

**裁决（2026-11-12，已定）**：本轮窗口**不带 A/B/C**；A 立为下一窗口第一优先项，C 挂在 A 里作兜底，B 不动。依据是 M.1 v2 实测普通路由 2→2 无变化、M.6 生产 EHS 近 24h 仅 1 次请求。§7 已按此写定（见 §8 D6）。
