# 下一批 RLS 收紧评估清单（字典之后）

- 日期：2026-11-06
- 范围：prod `pg_policies` 中 `policyname = 'rls_tenant_isolation'` 且策略表达式仍含
  `app.tenant_id IS NULL / '' / '00000000-0000-0000-0000-000000000000'` 放行分支的全部表。
- 本轮性质：**只读评估**。不改代码、不建迁移、不对 prod 执行任何 DML/DDL。
- 数据来源：prod 只读 `SELECT`（`pg_policies`、`pg_class`、`pg_stat_user_tables`、
  `information_schema.columns`、逐表 `count(*)`）；仓库限定名引用扫描（`svc/`、`lib/`、
  `database/migrations/`、`scripts/`）。`pg_stat_user_tables.n_live_tup` 为近似值，有实际行数的
  表已用逐表 `count(*)` 覆盖。

## 1. 结论速览

| 指标 | 数值 |
| --- | --- |
| 仍含旧放行分支的策略 / 表 | 359 张（扣除本批已收紧的 `public.core_dict_types/items` 后 **357 张**） |
| 风险分级 | 高（需先回填）**7**、高 **30**、中 **271**、低 **51** |
| 有实际数据的表 | **16 张**（其余为空表） |

**核心结论**：下一批不能简单“删分支 + 重建策略”。有 **7 张表存在 `tenant_id` 为 NULL 或全零的历史行**，
直接收紧会让这些行对所有租户（含超管默认会话）不可见，等于业务侧丢数据；必须先回填租户再收紧。
其余 350 张为空表或无历史脏行，可按批次直接套用与字典相同的策略模板。

处置原则：

1. **先回填、后收紧**。回填方案逐表确认（通常 `tenant_id = '…0001'` 系统租户，或按业务归属迁移），
   回填前保持旧策略；回填后有 `NULL/0 = 0` 的断言才允许执行策略迁移。
2. `public.audit_logs` 的 27 条 NULL 行需要业务确认归属（无法从数据推断时保留在系统租户并记录）。
3. `crm.rfm_results` / `ehs` 两张表全零行占比 100%，属于历史种子/测试数据，需业务确认是“回填”还是“清理”；

   不能仅凭“代码没有写”就认为可以安全收紧。

## 3. 系统通道设计（下一批沿用本批结论）

| 通道 | 做法 | 说明 |
| --- | --- | --- |
| 普通请求 | middleware 显式 `app.tenant_id=<请求租户>` + `app.rls_system='off'` | 与字典批一致；GUC 缺失即 fail-closed |
| 超管 / service | middleware `app.rls_system='on'`，租户置 nil | 跨租户管理端唯一入口 |
| 启动期 seed | 单事务内 `set_config('app.rls_system','on',true)` + 显式租户 | 参考 `seed_dict_data` |
| 定时任务 / 后台作业 | 作业自建事务，显式开系统通道；跨租户写必须显式指定目标租户 | 每服务盘点，不能依赖连接池默认 GUC |
| 迁移 / 回填 / 清理 | SQL 文件内显式 `SET LOCAL app.rls_system='on'`；回填必须带 `tenant_id` 条件 | 迁移只做 DDL 时无需通道 |
| DBA 直连 | `SET app.rls_system='on'` 或使用 bypassrls 账号 | 文档化，不恢复 NULL/0 放行 |

**是否复用 `app.rls_system`**：是。下一批不再引入第二个开关；所有跨租户维护路径统一复用它，
避免“某个服务漏设 GUC 就全表放行”的旧问题。

## 6. 分批建议（每批独立迁移 + 独立验收）

| 批次 | 范围 | 前置条件 |
| --- | --- | --- |
| A（先回填） | 第 2 节 7 张表 | 业务确认归属 → 回填 → `NULL/0 = 0` 断言 → 再收紧 |
| B | public/iam 租户、权限、菜单、工作流、自动化、登录审计（约 22 张） | 超管/后台任务通道盘点完成 |
| C | finance/hrm/crm/mes/qms/ehs 有数据表（约 14 张） | A/B 租户双向隔离 HTTP 用例 |
| D | 其余空表（约 314 张） | 套用模板批量迁移；逐表确认无后台写入 |

每批迁移模板（与 `20261107000008` 一致）：

1. `pg_policies` 枚举删除该表全部历史策略，避免 permissive OR 叠加；
2. 建唯一 `rls_tenant_isolation`：
   `COALESCE(current_setting('app.rls_system', true), '') = 'on' OR tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid`；
3. `ENABLE` + `FORCE ROW LEVEL SECURITY`；
4. 迁移末尾断言：策略数 = 1 且表达式含 `app.rls_system`。

每批验收（最小集）：

- `app.rls_system='on'` 可见全量；租户 A 看不到 B、B 看不到 A（双向）；
- 写接口落库 `tenant_id` 正确，无全零；
- 该模块启动期 seed / 定时任务在系统通道下可写；
- `NULL/0` 租户行断言为 0；
- 门禁三项 + 受影响包测试通过。

## 7. 未决问题 / 风险

1. **回填口径需要业务拍板**：7 张表里 3 张（`crm.rfm_results`、`ehs` 两张）全零占比 100%，
   是回填还是清理必须确认；本轮不执行。
2. **后台任务清单不完整**：静态扫描只能定位显式 SQL 引用，无法证明某服务没有定时任务写表；
   每批收紧前需该服务负责人确认。
3. **`pg_stat_user_tables` 近似**：附录中空表行数为 0 的结论可靠，有数据表已用实际 `count(*)` 覆盖；
   `audit_logs` 等持续写入表在窗口期会变化。
4. **193 张表 `tenant_id` 可空**：即使当前无 NULL 行，也建议下一批在收紧前加 `NOT NULL` 约束或
   写入侧兜底，否则未来一条 NULL 写入就会“隐身”。
5. **裸名 SQL 未纳入引用统计**：附录“限定名引用”是下限；服务内 `search_path` 裸名访问未计入，
   因此“无代码引用”仅表示未发现限定名引用，不代表无调用。
