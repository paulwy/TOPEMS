## 6. `date` / `timestamptz` 漂移结论（生产只读核查 + 修法）

### 6.1 生产实测（只读事务，`default_transaction_read_only=on`）

### 6.2 读这两列的全部代码路径

- 统计 `svc/wms/src/modules/analytics.rs:295-301`：准时率比较 + 履约天数差（已按日期口径修正）。
- 导出：`svc/wms` 无 outbound 导出端点（全仓库 `export|导出` 在 outbound 模块 0 命中）。
- 前端：`apps/web/src/api/wms/types.ts` 仅声明为 `string`，无日期格式化消费点；唯一 `'2026-11-05'` 出现在 vitest mock。

### 6.3 修法（已实施，方向：补新迁移统一为 `timestamptz`）

- 新迁移 `database/migrations/20261112160000_w7_b4_wms_outbound_ship_date_timestamptz.sql`：`DO` 块逐列查 `information_schema.columns.data_type='date'` 才 `ALTER ... TYPE timestamptz USING (col::timestamp AT TIME ZONE 'Asia/Shanghai')`；已是 `timestamptz` 为 no-op；`outbound_order_items` 上两列不存在则跳过。**不动已推送的历史迁移。**
- 回滚 `database/rollback/20261112160000_...rollback.sql`：`USING ((col AT TIME ZONE 'Asia/Shanghai')::date)` 改回 `date`；截断时分秒，按应用写入口径（恒为 +08 当日 00:00）不丢业务信息。
- 写路径对齐：创建 `expected_ship_date`、更新 `expected/actual`、发货 `actual_ship_date` 均在 SQL 内用 `date_trunc('day', $n::timestamptz AT TIME ZONE 'Asia/Shanghai') AT TIME ZONE 'Asia/Shanghai'` 归一为 +08 当日 00:00，不依赖会话 `TimeZone`。
- `schema_defense.rs` 两列期望类型同步为 `TIMESTAMPTZ`；`analytics.rs` 差值改为先按 `Asia/Shanghai` 落 `date` 再相减（否则 `timestamptz - timestamptz = interval`，`interval::integer` 直接报错）。

### 6.4 业务语义判断

两列是「预计/实际发货**日期**」：只用于 `actual <= expected` 的准时判定与按天差值，无时分秒业务含义。语义上 `DATE` 更贴切；但已裁决统一为 `timestamptz`，因此以「+08 当日 00:00」作为唯一合法时刻表示，写入口径强制归一，读接口输出 RFC3339 UTC（`+08 当日 00:00` = 前一日 `16:00:00Z`），浏览器按本地 `Asia/Shanghai` 渲染回原日期。

### 6.5 生产窗口预期

- **生产是真改类型，不是 no-op**：实测两列为 `date`（此前「生产可能已是 timestamptz」的假设不成立）。因两表 0 行，`ALTER` 元数据级完成，无数据重写、无长锁。
- **重建环境**（迁移建表 → 有数据）：同样执行 `date → timestamptz`，`USING` 显式 `Asia/Shanghai`，结果与生产一致。
- 可见影响：迁移前列表/详情在有任何数据时 500；迁移后恢复 200。旧二进制模型本就是 `DateTime<Utc>`，迁移后即可正常读写，因此**迁移可先于代码部署**；新二进制把写入归一为 +08 当日 00:00。
- 门禁身份：`schema-defense-check` 必须以表属主身份连接执行——副本为 `air`，生产为 `topems_prod`（`rolsuper=f`、`rolbypassrls=f`，两表 owner 均为它）；非属主副本上的 `ADD COLUMN` 会 `must be owner ... 失败（跳过）`，那种 PASS 无效。

## 7. 连接池容量（单独立项，不进本次窗口）

**已确认事实**

- `topems-wms` 独立进程：`ServiceConfig.max_db_connections = 10` 硬编码（`svc/wms/src/main.rs:41`），非嵌入模式下 `embedded_pool_limits()` 直接返回该值；池 `acquire_timeout = connect_timeout = 10s`（`DatabaseConfig::default` 的 `connect_timeout: Some(10)`，`lib/shared-core/src/config/enhanced.rs:48`）。
- 收货路径连接占用 ≥ 2：`receive_inbound_order` 先经由租户中间件持有整请求事务（1 条连接，`RlsTxnCell`），再 `db.scope_for_tenant(tenant)` 另开写作用域（第 2 条），提交后 `scope_read_for_tenant` 再取连接做读回。
- 副本实测：池上限 10、20 并发收货 → 部分请求 `pool timed out while waiting for an open connection`（10s）→ 500；库存/明细断言仍正确（非数据错误）。按嵌入配方（池 20）重跑 20/20 通过。
- 生产单体（`topems-server`，`xingzhai@192.168.110.115`，plist `com.topems.server`）：
  - 环境变量只设了 `DB_MAX_CONNECTIONS=8`，**嵌入模式 V2 路径不读它**（`bootstrap_service_inner` 直接用模块 `ServiceConfig.max_db_connections`；只有 `legacy_bootstrap` 读 `DB_MAX_CONNECTIONS`）。未设 `DB_MODULE_MAX_CONNECTIONS` / `DB_TOTAL_CONNECTION_BUDGET` / `DB_EXPECTED_POOLS`。
  - WMS 模块 `max_db_connections = 10`；嵌入 cap = `min(10, DB_MODULE_MAX_CONNECTIONS 默认 3) = 3`（`lib/shared-bootstrap/src/lib.rs:1344-1357`）。
  - 推导池数 31（1 迁移池 + 12 模块池 + advanced 2 + 共享池权重 14 + core 2）；默认总预算 = 31 × 2 = 62；单池授予 = `min(3, 62/31=2, 剩余) = 2`（`lib/shared-db/src/database/budget.rs`）。
  - `acquire_timeout = 10s`（同上 `DatabaseConfig::default`），PG `max_connections=100`。
  - 生产 `pg_stat_activity` 旁证（只读）：`finance-module=2`、`unified_core-module=4`（core 两个池 × 2）、`analytics-module=1`、`topems-shared-runtime=1`，与「每池授予 2」一致；`wms-module` 因 `min_connections=0` 当前无常驻连接。
  - 结论：**生产 WMS 模块池 max = 2**，收货请求同时占 2 条 → 有效并发 1。
- 撞墙条件：第 2 个收货请求开始排队，排队 >10s 即 `pool timed out`。副本反证（池 10、20 并发、10s 超时即失败）意味着单请求在池内驻留约 ≥2.5s；按此推算生产有效 1 槽时，**≈5 个在途收货请求（约 0.4 次/秒持续）就可能让队尾超过 10s**。若单请求更快（0.2s），阈值抬到 ≈50 在途（约 5 次/秒）。当前低流量不暴露，但突发/批量收货会复现；同池的其它 WMS 端点也会挤占这 2 条连接。

**处置**：本窗口不改池大小；单独立项（候选：调大 wms 模块池 / 消除收货路径提交后另开作用域的二次取连接），待另行裁决。

## 9. 立项：连接池总账（`DB_MAX_CONNECTIONS` 与模块池 max=2）

**问题**：生产 plist 设了 `DB_MAX_CONNECTIONS=8`，但嵌入 V2 路径不读它；实际生效的是模块 `ServiceConfig.max_db_connections`（WMS=10）再经嵌入 cap `min(10, DB_MODULE_MAX_CONNECTIONS 默认 3)=3`、预算分摊后落为 **每池 max=2**。即"设了 8，实际 2"，配置语义与运行时不符。

**要算的账**

- 已设但无效的：`DB_MAX_CONNECTIONS=8`（嵌入路径忽略）。

**待裁决**：是"删掉无效的 `DB_MAX_CONNECTIONS`、显式声明模块池与预算"，还是"让嵌入路径读 `DB_MAX_CONNECTIONS` 并据此推导单池授予"。两者都要落成可核对的配置快照（plist + 运行时 `pg_stat_activity`），并纳入健康检查/启动日志。

## 10. 已定位并修复：`svc/unified-core/.env` 的 `DATABASE_URL` 指向无服务的 5433，导致 `sqlx::test` 建库超时

**结论**：`pre-push` 重型门禁 `cargo-test-workspace` 的 3 条 `PoolTimedOut` 是**本机环境漂移**，与 W7-B4 合并无关（基线 `origin/main` 同参数下逐字复现）。根因是 `svc/unified-core/.env`（被 `.gitignore` 忽略）的 `DATABASE_URL` 指向 `localhost:5433`——该端口无服务，且口令也是旧实例口径。已改为与根 `.env` 一致的 `127.0.0.1:5432/topems`，并在门禁侧加了防复发导出。

**已排除（不要再按这两个方向排查）**

- **测试库连接容量不足：排除。** `pg_stat_activity` 峰值：基线全量 **14**、合并树全量 14、修复后全量 **13**；PG `max_connections=100`，占用 <15%，全程无 `too many clients`、无 acquire 排队、无中途池耗尽。

### 10.4 防复发（已实施）

该文件被 gitignore，**改本机文件不构成防线**：新机器/新工作树复制模板时必然重犯。已实施"让 `sqlx::test` 不依赖 crate 级 `.env`"这一项——在 `lefthook.yml` 的 `cargo-test-workspace` 中从根 `.env` 的 `MIGRATE_URL` 派生并**显式导出 `DATABASE_URL`**（已显式提供则不覆盖）。依据：dotenvy 不覆盖已存在的环境变量，故导出后 crate 级 `.env` 再也无法劫持测试连接目标。

**`NEXTEST_TEST_THREADS=1` 为何无效**：该变量不改变执行路径（日志仍为 libtest 形态、`cargo test` 在首个失败 target 即停），串行只约束**单个测试进程内**的线程数；此处失败发生在**各 crate 的测试二进制各自建池**时，与进程内并发度无关。

### 10.5 同批修正与约束

**同批修正（2026-11-12）**：`svc/{analytics,gis,wms}/.env` 原同为 `localhost:5433` 口径，已一并改为与根 `.env` 一致的 `127.0.0.1:5432/topems`（同一口令），四份模块 `.env` 均实测 `psql … -Atc 'select 1'` 返回 `1`。`svc/wms/.env` 正是本次 WMS 收口所在模块，将来补 `#[sqlx::test]` 用例会立刻踩，现在改零成本。

> 注意：这些文件被 `.gitignore` 忽略，属本机环境；其他机器/新工作树不会自动继承，需靠 10.4 的门禁导出兜底。

**约束：crate 需要独立测试库时，必须显式传 `DATABASE_URL`**

- 门禁的导出语义是"已设置则不覆盖"，因此**门禁运行下 crate 级 `.env` 的 `DATABASE_URL` 会被静默忽略**——改它不会生效，也不会有任何提示。
- 将来某个 crate 若确实需要独立测试库，必须在**该测试进程**上显式提供，例如 `DATABASE_URL=postgres://… cargo test -p <crate>`，或在门禁/脚本里先 `export`，**不得依赖 crate 级 `.env`**。
- 违反后果是"改了没反应"：本次 3 条 × 30s ≈ 92s 的 `PoolTimedOut` 就是这类静默失效的表象，排查成本极高。
