跨切面系统性问题

1. "API 先行、后端滞后"是全局性模式：整体匹配率仅 ~35%，前端定义了 ~4,400 个 API 方法但后端仅 ~3,800 条路由（且大量为版本化/实验性）。im(93%无后端)、mobile(78%无后端)、master V61-V79(100%无后端)、notification扩展(78%无后端) 是重灾区。大量前端 API 文件属于"预埋式悬空代码"——有封装、有类型、但无后端支撑、无页面消费。

2. 命名空间 / client 调用混乱是系统性 bug 源：ticket→portal、search→portal、notification/im.ts→notification(应im)、notification/mail.ts→notification(应mail)、plugin→/api/core/plugin(应/api/plugin)、admin/system→erp(应core/master-data)、dict 三处分裂。至少 6 处命名空间错误导致 ~100 次 API 调用必然 404。

3. 路径前缀不匹配是高频缺陷：mobile (/mobile/xxx vs /xxx)、WMS/SCM sync (/sync-records vs /sync/*)、finance/reconciliation (/reconcile/{id} vs /reconciliation/sessions)、MES (/mes/v1/ 旧前缀)、plugin 三方前缀不一致。建议建立 CI 门禁：前端 API 调用的 URL 路径必须在后端路由注册表中存在。

4. 后端系统性只读：ehs 6+ 个模块几乎全 GET、crm/billing+interaction 仅有读路由、finance 多个子模块缺写操作。前端页面因此无法执行 create/update/delete，部分退化为只读展示或使用 Mock。

5. 版本化模块管理混乱：master-data 后端 V51-V60（V59/V60 仅骨架）、前端 V51-V79（V61-V79 全悬空）；finance 后端 V51-V60 共 10 个版本化模块 155 条路由无前端；finance/risk.ts+riskV54.ts+riskV59.ts 三份并存。缺乏版本化模块的生命周期管理（启用/废弃/前端对应状态）。

6. 重复实现增加维护成本：至少 6 组 API 模块存在功能重叠（consolidation 三方、voucherTemplate 双方、financialReport、risk 双份、receivablePayable 跨模块、database 双份），加上 WMS 后端 transfer 重复注册、inventory_alert 双路径。改一处漏一处的风险高。
