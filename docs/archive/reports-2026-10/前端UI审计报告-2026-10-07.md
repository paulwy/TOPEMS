## 1. 前端架构评估

### 1.1 优点（实测确认）

- **模块化单体回归**：Module Federation 已移除，业务域本地打包；`modules/*/config.ts`（38 个模块、共 18,429 行）作为插件注册层，`DynamicRoutes`/`plugin-loader` 动态挂载，路由收敛于 `routes/appRoutes.tsx`，每路由带 `PageErrorBoundary + Suspense + PageLoader`。
- **配置驱动页面**：`components/templates/` 提供 20+ 模板（CrudPage/ListPageTemplate/FormPageTemplate/DetailPageTemplate/Kanban/Dashboard…），新页面如 `CustomerManagementPage.tsx` 仅 19 行（schema + apiAdapter + 模板）。这是正确方向。
- **状态分层**：`store/` 三层架构（ui/domain/server）+ ARCHITECTURE.md 文档 + React Query 迁移路线；`hooks/` 分 foundation/domain/features，WebSocket 基础 `useWebSocket` → `webSocketService` 被 5+ 派生 hook 复用。
- **API 封装统一**：`api/client.ts` 统一 axios（CSRF、trace、错误处理、i18n、超时），`packages/shared-types` 提供跨端类型。
- **工程化基建成熟**：design-token 审计脚本、design-system-audit、unused-exports 审计、lighthouse、playwright（66 个 e2e）、storybook（75 stories）、416 个单测文件。

### 1.2 问题

1. **三端架构割裂（P0）**
   - `apps/mobile` 完全不引用任何 `@topems/*` 共享包：自带 `api/`（17 个文件）、`types/`、`store/`、`components/` 全量重复实现；且 `mobile/src/api/approval.ts` 中 `getApprovals` 与 `getTasks` 请求同一端点 `/approval/tasks`（重复定义缺陷）。
   - `apps/desktop` 仅 4 处引用 `@topems/app-shell`，自带 authStore 与整套 Layout/页面。
   - 后果：同一业务改动需在三端各改一遍；口径漂移（响应类型、错误处理、token 解析）风险高。
2. **多套 UI 体系并存（P1）**：页面 import 分布为 MUI 直接使用 530 / components/common 295 / shared-components 41 / redesign 28，另有 wms/tms/mes 模块内私有组件。设计语言无法统一。
3. **巨型模板（P0）**：ListPageTemplate 4153 行是典型的"god component"——职责过多（搜索/筛选/排序/分页/批量/列配置/卡片视图/表单弹窗），props 面巨大，改动风险集中。
4. **UIV3 redesign 双轨（P1）**：14+ 个 `*RedesignPage` 与旧页面并存（如 `CrmCustomerRedesignPage` vs `CustomerManagementPage`），`isUIV3Enabled()` 运行时切换 → 同一用户在迁移期看到两套 UI。
5. **i18n 覆盖良好但 key 质量差（P2）**：872/886 页面使用 i18n，仅 13 文件 15 处硬编码中文；但 1006 个自动生成 hash key（如 `bi.gis_page_components__entity_form_modal.text_6acaee`），语义不可读、翻译管理困难。

### 1.3 架构评分与方向

| 维度 | 评分（10） | 说明 |
|---|---|---|
| 分层清晰度 | 8 | apps/packages 边界明确，但三端复用度差异大 |
| 模块化/可扩展 | 8 | 插件注册 + 动态路由良好 |
| 组件体系收敛 | 4 | 4+ 套 UI 并存，重复实现多 |
| 状态管理 | 8 | 分层+迁移路线清晰 |
| 可测试性 | 8 | 测试/审计工具链齐全，但 lint 门禁失效 |
| 维护成本趋势 | 5 | 巨型模板 + 双轨页面 + 三端重复使增量成本上升 |

方向建议：**单 UI 封装层 + 共享包下沉 + 模板瘦身**三条主线，见 §7 路线图。

## 2. 目录与模块设置评估

### 2.1 现状

- `pages/` 921 文件、`api/` 544、`components/` 586、`schemas/` 281、`hooks/` 95 —— 按业务模块二级分组，但单目录体量过大。
- `pages/<module>/` 与 `api/<module>/`、`components/<module>/` 平行分布；`modules/<module>/config.ts` 为插件元数据层。
- 混入 src 的非业务目录：`_archive-microfrontend`、`tmp`、`debug`、`dev-tools`、`docs`、`fullstack-automation`、`intelligent-ops` 等（其中 dev-tools/dev-platform 为开发期面板，production 由 `import.meta.env.DEV` tree-shake）。
- `schema/`（7 文件）与 `schemas/`（281 文件）双目录并存，命名混乱。

### 2.2 评估

优点：模块化单体 + 插件注册是合理演进；hooks/store 分层有文档支撑。

问题：
1. **功能聚合度不足（P2）**：一个页面 = pages/ 组件 + api/ 客户端 + schemas/ 校验 + components/ 私有组件，跨 4 个根目录查找，页面级迁移/删除成本高。建议按 feature 聚合（`pages/<module>/<feature>/` 内含 api.ts、schema.ts、components/），或至少在模块内维护 index 桶。
2. **残留/死目录（P2）**：`components/ui` 实际死代码（4 文件仅 1 处引用）；`_archive-microfrontend`、`tmp` 应归档清理；`sw.ts` 与 `lib/pwa.ts` 职责重叠。
3. **eslint ignores 清单维护成本**：根 eslint.config.js 的 ignores 已有 15+ 条路径豁免，说明"非规范代码"以豁免方式存在，应改为整改。

## 3. UI 一致性评估

### 3.1 设计令牌体系（现状）

- `packages/tokens`（designTokens：品牌色阶/语义别名/间距/阴影/zIndex）+ `theme/generated-tokens.css`（自动生成，禁止手改）+ `check-design-tokens` 审计脚本。体系本身是完整的。
- 主色调 `#365ae3` 与语义别名（primary/muted/border/overlay…）齐全。

### 3.2 实测违规（`node scripts/check-design-tokens.mjs`）

**共 159 处违规**（注：2026-10-07 审计初报的 80 处为脚本默认 `--max-findings=80` 截断显示；全量实为 159 处：hardcoded-color 101 / rgb-color 48 / box-shadow 4 / fixed-px-spacing 6。其中 CSS `var(--token, fallback)` 兜底值属脚本误报，已改进脚本豁免）。主要分布：

| 区域 | 违规数 | 典型问题 |
|---|---|---|
| components/ai/business | 20+ | 状态/图表色（DocumentIntelligence、GovernanceDashboard 等；状态色已令牌化示范） |
| components/charts | 10+ | chartTheme.ts 渐变色板 rgba |
| components/redesign/layout | 12 | SideRail `#000000`×4、TopBar 阴影 `0 4px 12px rgba(0,0,0,.15)`、固定 px 间距 |
| components/gis（含 Heatmap） | 20+ | 热力色带 rgba 渐变 |
| components/redesign/primitives | 6 | Avatar 调色板 `#8b5cf6/#ec4899/#14b8a6`、Toggle 阴影 |

**关键结论：新 redesign 体系（UIV3）自身就是最大违规源之一**——它绕过了既有令牌体系，直接硬编码，将导致新 UI 与品牌令牌脱节、暗色主题适配失效。

### 3.3 其他一致性指标

- 硬编码颜色（hex/rgb/rgba）在 tsx 中 **141 处**（含上述 80 处审计命中）。
- 内联 `style={{`：**467 个文件**（部分为动态值合理，但缺规范约束）。
- z-index 魔数：`10000`×17、`9999`×4、`10001`×3、`1300`×4、`1000`×7、`10`×24、`50`×19 等 100+ 处散落，未统一走 `theme.zIndex` 语义层——浮层打架风险高（dev 面板/命令面板/通知）。
- 字体系列/间距：body 使用 token，但 redesign 内 `gap: '8px'` 等固定 px 间距违规 8 处（fixed-px-spacing）。
- i18n：覆盖率高（见 §1.2.5），但 hash key 可维护性差。

## 4. 页面缺陷（测试结果）

### 4.1 已运行验证（全绿）

- `tsc --noEmit`：**0 错误**。
- `vitest --project=crm`：**9 文件 99 用例全部通过**。
- 全库有 416 个单测文件、66 个 e2e spec、75 个 storybook stories；但 e2e 需后端与浏览器环境，本次未实跑（应纳入 CI）。

### 4.2 ESLint 门禁失效（P0）

- pages 全量：**3953 条警告，0 错误；其中 3952 条为 `import/*` 系列 `Resolve error: typescript with invalid interface loaded as resolver`**，真实代码问题仅 1 条（no-unused-vars）。
- components/hooks/api：真实警告仅 4 条（naming-convention）。
- 即：代码真实质量信号良好，但**工具链噪音使 lint 无法作为门禁**（`pnpm lint --max-warnings 100` 必失败），CI 要么已失效要么被强制豁免。根因：`eslint-import-resolver-typescript` 与当前 TypeScript 版本接口不兼容。

### 4.3 三态覆盖缺口（P1，规模统计）

| 状态 | 有处理页面数 | 731 页中占比 | 缺失 |
|---|---|---|---|
| 加载态（loading/skeleton） | 389 | 53% | 342 页（47%） |
| 空态（EmptyState/empty） | 116 | 16% | 615 页（84%） |
| 错误处理（error/ErrorBoundary） | 287 | 39% | 444 页（61%） |

> 口径：grep 关键词（isLoading/Empty/error 等）近似统计，空态数据偏乐观；实际空态覆盖率更低。路由级 `PageErrorBoundary` 是兜底，但页内加载/空态仍需模板默认注入。

### 4.4 具体缺陷实例

1. **FieldSelector.tsx 全局监听泄漏（真实 Bug）**：`onMouseDown` 内 `document.addEventListener('dragover'/'drop', ...)`，**每次点击都追加监听且永不移除** → 监听器累积 + 拖放重复触发（多行被同时 reorder）。应改为 useEffect 挂载/卸载管理，或用 pointer 事件 + cleanup。
2. **mobile `approval.ts` 重复端点**：`getApprovals` 与 `getTasks` 均请求 `/approval/tasks`，字段/分页口径两处维护。
3. **模块级监听未清理清单**（10 个文件 add > remove）：`TauriApi.ts`（28/0，需审查是否应用级单例）、`pwa.ts`（7/2）、`sw.ts`（7/0，SW 上下文可接受）、`telemetry.ts`（3/0，单例可接受）、`main.tsx`（3/0，应用级可接受）、`smart-debugger.ts`（3/0）、`FieldSelector.tsx`（2/0，**组件级真泄漏**）、`on-demand-loader.ts`（2/1）、`module-performance-metrics.ts`（2/0）、`usePerformanceMonitor.tsx`（1/0，load 一次性事件可接受）。
4. **a11y**：eslint a11y 规则集已启用且页面真实告警极少（说明基础 a11y 尚可）；仍建议对 IconButton/icon-only 按钮做 aria-label 批量核查（当前 grep 未发现明显缺漏）。

## 5. 事件处理评估与优化空间

### 5.1 现状

- 内联箭头处理器密集：pages/components 中 `onClick={() => ...}`/`onChange` 数千处；Top 文件：ListPageTemplate 49、MicroFrontendDevTools 45、AIOpsPanel 35、EntityFormModal 33、SystemSettingsPage 25。
- 但核心模板已大量使用 `useCallback`（ListPageTemplate 46 处）与 `useMemo`（34 处）——**事件引用稳定性做得较好**。
- 全局快捷键系统 `shortcuts.ts` 已存在（keydown 委托），方向正确。

### 5.2 优化空间（按收益排序）

1. **修复全局监听泄漏（P0）**：FieldSelector 等组件级 addEventListener 一律移入 `useEffect(() => { ... return cleanup }, [deps])`；审查 TauriApi 的 28 个监听是否为单例 + 是否需销毁。
2. **大列表行内事件 → 事件委托或 memo 行组件（P1）**：ListPageTemplate 等表格行/卡片行的内联 handler 每行新建闭包，千行列表渲染成本高。方案：行级 `<RowMemo>` + 稳定 handler（`useCallback` 已部分具备）；或对纯展示行做 `React.memo` + 行索引委托。
3. **DOM 高频事件治理（P1）**：scroll/resize/mousemove 监听建议统一 `passive: true` + rAF/节流封装（`useThrottle`/`useVirtualScroll` 已存在，推广使用）；拖拽改用 pointer events（统一 mouse/touch）。
4. **定时器清理审计（P2）**：全库 setTimeout/setInterval 需统一清理模式（组件卸载 clear），建议加 eslint 规则或封装 `useInterval`/`useTimeout`。
5. **React 合成事件层内不做重活（P2）**：onChange 内同步做深拷贝/重计算的地方移到 `useMemo`/`useDeferredValue`（FormPageTemplate 大表单场景）。

## 6. 公共模块评估与优化空间

### 6.1 共享包使用现状（实测）

| 包 | 被 web 直接引用文件数 | 评价 |
|---|---|---|
| `@topems/tokens` | 301 | 主力，健康 |
| `@topems/shared-components` | 83（pages 41） | 与 components/common 重复 |
| `@topems/shared-types` | 大量 | 主力，健康 |
| `@topems/shared-hooks` | 6 | 仅 useCrud/useDebounce/useIntersectionObserver，覆盖不足 |
| `@topems/shared-utils` | 3 | web 用 bridge（utils/format.ts、date.ts 转发），实际命中面小 |
| `@topems/app-shell` | 4 | 轻量，评估扩充或并入 web |
| `@topems/api-client` | 1 | 仅 web api/client.ts 使用，mobile/desktop 未用 |

### 6.2 核心问题

1. **组件重复实现（P1）**：
   - `EmptyState`：common / shared-components / templates/list / redesign/feedback 共 **4 份**
   - `StatusBadge`：common / wms / tms / mes + shared-components 共 **4+ 份**
   - `FileUpload`：common / shared-components / redesign/primitives 共 **3 份**
   - `ConfirmDialog`、`Pagination`、`LoadingSpinner`、`BackButton` 各 **2 份**
   - 合计 7 类 17 份。风险：修复/样式升级需多点同步，极易漂移。
2. **shared-components 定位不清**：与 `components/common` 功能高度重叠，页面引用 41 处 vs 295 处，说明"公共组件应放共享包"的规范未被贯彻。
3. **hooks 共享不足**：web 内 95 个 hooks 仅 3 个下沉到 shared-hooks；useCrud（shared）与 useCrudQueries/useCrudMutations（web）并存。
4. **mobile/desktop 零/低共享**（P0，见 §1.2.1）。
5. **死代码**：`components/ui`（4 文件 1 引用）、web/utils/storage.ts（自带注释声明未使用）。

### 6.3 优化方案

1. **单一真相源**：以 `@topems/shared-components` 为唯一实现层，`components/common` 改为薄 re-export（过渡期）后移除；eslint `no-restricted-imports` 禁止直接跨模块复制组件。
2. **StatusBadge 收敛**：统一到 shared-components（已有 DEFAULT_STATUS_MAP 与多业务 badge），删除 wms/tms/mes 私有实现。
3. **hooks 下沉**：把 useDataTable/useListPageState/useColumnConfig 等通用 hooks 下沉 shared-hooks，web 保留业务 hooks。
4. **mobile/desktop 接入共享**：先接 tokens/shared-types/api-client（低风险），再按需接 components（移动端可只接原子层）。
5. **清理死代码**：删除 components/ui、_archive-microfrontend、tmp 等，统一 schema 目录。

8. mobile/desktop 接入共享包，建立"端差异只在布局层"原则。
9. 清理死代码与残留目录；合并 schema/schemas。
10. i18n hash key 分批重写为语义 key；z-index 语义化。
