# TOPEMS 设计系统与页面模板治理实施规划

> 文档状态：草案 / 待评审
> 版本：V1.0
> 制定时间：2026-08-21
> 关联文档：`design-inventory-and-template-analysis.md`
> 目标：建立可持续迭代的设计系统，提升 TOPEMS 全站页面一致性、可维护性与设计-研发协同效率

---

## 1. 规划总则

### 1.1 核心目标

1. **统一页面体验**：80% 以上新增页面使用标准页面模板与共享组件。
2. **降低重复开发**：通过模板化减少同类页面的重复实现，目标减少 30% 以上页面级代码量。
3. **强化设计 Token 治理**：消除硬编码颜色/间距/字号，所有新增代码 100% 使用语义 Token。
4. **建立可持续机制**：形成「设计 → Token → 组件 → 模板 → 页面」的闭环治理流程。

### 1.2 实施原则

- **先治理入口，再治理长尾**：优先统一高频页面（Dashboard、List、Detail、Form），再处理特殊场景。
- **先增量，后存量**：新增页面必须遵循规范，存量页面按模块优先级逐步迁移。
- **数据驱动**：通过代码扫描建立基线，用量化指标（模板覆盖率、Token 使用率）衡量进展。
- **不追求一步到位**：允许过渡期存在混合实现，但必须明确迁移计划和 deadline。
- **设计-研发共建**：设计师负责 Token 与视觉规范，前端负责组件与模板，业务方负责落地。

### 1.3 关键术语

| 术语 | 说明 |
|------|------|
| 页面模板（Page Template） | `apps/web/src/components/templates` 中的 15 种高层页面模式 |
| 共享组件（Shared Component） | `packages/shared-components` 中的可复用 React 组件 |
| 设计 Token | `packages/tokens/src/tokens.ts` 中的颜色、间距、字体、阴影等设计值 |
| 语义 Token | `semanticTokens` 层，按使用场景命名，如 `space.page.horizontal` |
| 模板覆盖率 | 使用标准页面模板的页面数 / 总页面数 |
| Token 合规率 | 未使用硬编码设计值的文件数 / 被扫描文件数 |

## 3. 总体路线图

整个实施周期建议为 **16-20 周**，分为 5 个阶段：

```
阶段 0：准备与基线（2 周）
阶段 1：核心模板统一（4 周）
阶段 2：组件与 Token 深化（4 周）
阶段 3：模块级重构（6 周）
阶段 4：机制固化与持续治理（长期）
```

## 4. 阶段 0：准备与基线（第 1-2 周）

### 4.1 目标

建立可量化的现状基线，制定详细规范，搭建扫描与监控工具链。

### 4.2 任务清单

#### 任务 0.1：建立页面-模板-组件映射扫描

- **描述**：编写脚本扫描 `apps/web/src/pages/**/*.tsx`，识别每个页面实际使用的模板、组件、共享组件、硬编码颜色/间距。
- **负责人**：前端架构 / DevEx
- **输入**：537 个页面文件
- **输出**：
  - `page-template-map.csv`：页面路径 → 使用模板 → 使用共享组件 → 是否使用 PageContainer → 是否使用 DataTable
  - `hardcoded-style-report.csv`：硬编码颜色、间距、字号、shadow 的文件列表
  - `shared-component-usage.csv`：共享组件使用情况
- **验收标准**：
  - [ ] 扫描覆盖 100% 页面文件
  - [ ] 输出 CSV 可被直接打开和排序
  - [ ] 误报率低于 5%（通过人工抽样 20 个文件验证）

#### 任务 0.2：制定《页面模板选型规范》

- **描述**：明确 15 种模板的使用场景、必选子组件、禁用场景，形成团队共识文档。
- **输出**：`docs/design/page-template-selection-guide.md`
- **验收标准**：
  - [ ] 每种模板包含「适用场景」「必须使用的子组件」「不推荐场景」三个章节
  - [ ] 提供至少 1 个正例和 1 个反例
  - [ ] 通过 3 人以上前端 + 1 名设计师评审

#### 任务 0.3：制定《共享组件使用规范》

- **描述**：规范 DataTable、PageContainer、ActionButton、StatusBadge 等核心组件的使用方式。
- **输出**：`docs/design/shared-component-guidelines.md`
- **验收标准**：
  - [ ] 列出 10 个以上核心组件的 DO / DON'T
  - [ ] 明确禁止自研表格、禁止自定义按钮变体颜色
  - [ ] 明确表单控件必须优先使用共享组件

#### 任务 0.4：搭建 Token 合规扫描

- **描述**：基于 ESLint 或 AST 扫描，检测 `apps/web/src` 和 `packages/shared-components/src` 中的硬编码颜色、间距、字号。
- **输出**：
  - ESLint 规则：`no-hardcoded-design-values`
  - CI 脚本：`scripts/ci/check-design-tokens.cjs`
- **验收标准**：
  - [ ] 能识别 `#xxx`、`rgb(...)`、`rgba(...)`、`#xxxxxx` 等颜色硬编码
  - [ ] 能识别常见 MUI sx 中的硬编码 px 值（如 `16px`、`24px`）
  - [ ] CI 失败时给出文件路径和行号
  - [ ] 允许配置白名单（如 Cyber 主题特殊效果、SVG 属性）

#### 任务 0.5：建立设计系统看板

- **描述**：在项目管理工具中建立看板，跟踪各阶段任务、模块迁移进度、模板覆盖率、Token 合规率。
- **输出**：项目管理看板 + 每周自动化数据更新脚本
- **验收标准**：
  - [ ] 看板包含「待开始」「进行中」「待验收」「已完成」四列
  - [ ] 关键指标每周五自动更新

### 4.3 阶段 0 验收标准

- [ ] 页面-模板-组件映射表已生成并评审
- [ ] 2 份核心规范文档已通过评审并发布
- [ ] Token 合规扫描可在本地运行并输出报告
- [ ] 设计系统看板已建立并投入使用

### 4.4 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 扫描脚本误报率高 | 团队不信任数据 | 先小范围验证，再迭代规则；允许白名单 |
| 规范文档过于理想化 | 难以落地 | 规范必须配套示例代码和迁移指南 |
| 业务压力大，无法投入 | 阶段延期 | 阶段 0 以架构/DevEx 为主，业务方少量参与 |

## 5. 阶段 1：核心模板统一（第 3-6 周）

### 5.1 目标

让 5 种核心模板（list / detail / form / dashboard / kanban）覆盖 80% 以上新增页面，并完成 50% 高频存量页面迁移。

### 5.2 任务清单

#### 任务 1.1：统一 Dashboard 入口页

- **范围**：
  - `pages/shared/DashboardPage.tsx`
  - `pages/shared/HybridHomePage.tsx`
  - `pages/shared/ModulesOverviewPage.tsx`
- **动作**：
  - 全部接入 `DashboardTemplate`
  - 统计卡片统一使用 `dashboard/StatCardComponent`
  - 图表卡片统一使用 `dashboard/ChartCardComponent`
  - 移除自定义布局和硬编码样式
- **验收标准**：
  - [ ] 3 个入口页均使用 `DashboardTemplate`
  - [ ] 无自定义统计卡片实现
  - [ ] 暗色模式下无视觉异常
  - [ ] 移动端卡片布局正常

#### 任务 1.2：统一 List 类型页面

- **范围**：从映射表中筛选出表格/列表类页面（预计 150-200 个）
- **优先级**：先迁移 MES、WMS、ERP、CRM、SCM、SRM 中的高频列表页
- **动作**：
  - 使用 `ListPageTemplate`
  - 表格统一替换为共享 `DataTable`
  - 按钮使用 `ActionButton`
  - 空状态使用 `EmptyState` 系列
  - 分页使用共享 `Pagination`
- **验收标准**：
  - [ ] 目标列表页均使用 `ListPageTemplate`
  - [ ] 无业务自研表格（白名单除外）
  - [ ] 搜索、筛选、导出、分页功能正常
  - [ ] 移动端切换为卡片视图

#### 任务 1.3：统一 Detail 类型页面

- **范围**：从映射表中筛选详情页（预计 80-120 个）
- **动作**：
  - 使用 `DetailPageTemplate`
  - 信息展示使用 `PageContainer` + 卡片布局
  - 状态使用 `StatusBadge`
  - 时间使用 `RelativeTime`
- **验收标准**：
  - [ ] 目标详情页均使用 `DetailPageTemplate`
  - [ ] 详情页布局一致（标题区、信息区、操作区、关联区）
  - [ ] 打印/导出 PDF 样式正常

#### 任务 1.4：统一 Form 类型页面

- **范围**：新建/编辑表单页（预计 80-120 个）
- **动作**：
  - 使用 `FormPageTemplate`
  - 表单控件统一使用共享组件（FormField、FormSelect、DatePicker 等）
  - 校验与 schema 对齐
- **验收标准**：
  - [ ] 目标表单页均使用 `FormPageTemplate`
  - [ ] 表单字段使用共享组件比例 ≥ 90%
  - [ ] 表单校验错误提示样式统一

#### 任务 1.5：Kanban 看板页试点

- **范围**：选择 1-2 个任务/工单看板页（如 PM、MES、Ticket）
- **动作**：
  - 使用 `KanbanPageTemplate`
  - 定义看板列、卡片、拖拽交互规范
- **验收标准**：
  - [ ] 至少 1 个看板页完全使用 `KanbanPageTemplate`
  - [ ] 拖拽、状态变更、卡片详情交互正常

### 5.3 阶段 1 验收标准

- [ ] 新增页面 100% 使用标准核心模板
- [ ] 高频存量列表页 50% 完成迁移
- [ ] Dashboard 入口页 100% 统一
- [ ] 模板覆盖率从基线提升 ≥ 20%
- [ ] 阶段 1 迁移页面无 P0/P1 级 Bug

### 5.4 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 业务页面逻辑复杂，迁移成本高 | 进度延迟 | 拆分大页面为子组件；允许分步骤迁移 |
| 模板灵活性不足 | 业务方抵触 | 收集需求，扩展模板 props，避免一刀切 |
| 回归测试工作量大 | Bug 漏出 | 优先补充单元测试和视觉回归测试 |

## 6. 阶段 2：组件与 Token 深化（第 7-10 周）

### 6.1 目标

补齐共享组件缺口，深化设计 Token 体系，建立组件级 Token 和主题统一策略。

### 6.2 任务清单

#### 任务 2.1：新增布局组件

- **描述**：将模板中的公共布局抽象为独立共享组件。
- **新增组件**：
  - `DetailLayout`：详情页标准布局（标题区、信息网格、操作栏、关联标签页）
  - `FormLayout`：表单页标准布局（表单区、底部操作栏、分节）
  - `SettingsLayout`：设置页标准布局（左侧菜单 + 右侧内容）
  - `MasterDetailLayout`：主从布局（左侧列表 + 右侧详情）
- **验收标准**：
  - [ ] 4 个布局组件均通过单元测试
  - [ ] 每种布局提供 Storybook 示例
  - [ ] 至少 10 个存量页面接入新布局组件

#### 任务 2.2：新增/补齐表单组件

- **新增组件**：
  - `FormRadio` / `FormRadioGroup`
  - `FormSlider`
  - `FormAutocomplete`
  - `FormRating`
  - `FormTransferList`（可选）
- **验收标准**：
  - [ ] 新组件与现有表单组件 API 风格一致
  - [ ] 均支持 `size`、`disabled`、`error`、`helperText`
  - [ ] 均接入 FormField 的 label/error 体系

#### 任务 2.3：统一图表组件

- **描述**：基于 Recharts/ECharts 封装共享图表组件，供 Dashboard 和统计页使用。
- **新增组件**：
  - `LineChartCard`
  - `BarChartCard`
  - `PieChartCard`
  - `AreaChartCard`
  - `StatTrendChart`
- **验收标准**：
  - [ ] 图表颜色自动从 Token 获取
  - [ ] 支持空状态、加载态、错误态
  - [ ] 支持响应式缩放
  - [ ] 暗色模式下自动切换配色

#### 任务 2.4：组件级 Token 扩展

- **描述**：在 `semanticTokens` 下增加 `components` 层级。
- **新增 Token 示例**：
  - `semanticTokens.components.button.primary.bg`
  - `semanticTokens.components.button.primary.hoverBg`
  - `semanticTokens.components.input.border`
  - `semanticTokens.components.input.focusBorder`
  - `semanticTokens.components.card.bg`
  - `semanticTokens.components.card.hoverShadow`
  - `semanticTokens.components.table.headerBg`
  - `semanticTokens.components.table.rowHoverBg`
- **验收标准**：
  - [ ] 至少 20 个组件级 Token 被定义
  - [ ] 共享组件优先使用组件级 Token
  - [ ] Token 变更时组件自动响应

#### 任务 2.5：暗色模式与 Cyber 主题统一

- **描述**：明确 light / dark / cyberpunk 三套主题的关系和使用范围。
- **决策项**：
  - Cyber 主题是否只用于 AI/实时看板？
  - 普通暗色模式是否使用 Cyber 的玻璃态/霓虹效果？
  - 主题切换是全局还是局部？
- **输出**：`docs/design/theme-strategy.md`
- **验收标准**：
  - [ ] 三套主题的边界清晰文档化
  - [ ] 主题切换无闪烁
  - [ ] 所有共享组件在三套主题下视觉正常

#### 任务 2.6：Token 合规扫描接入 CI

- **动作**：将阶段 0 的 Token 扫描脚本接入 CI，仅对变更文件执行（避免一次性修复全部存量）。
- **验收标准**：
  - [ ] CI 对新增/修改文件执行 Token 合规检查
  - [ ] 硬编码颜色/间距导致 CI 失败
  - [ ] 白名单机制生效

### 6.3 阶段 2 验收标准

- [ ] 共享组件数量从 29 扩展至 40+
- [ ] 组件级 Token 覆盖 10 个以上核心组件
- [ ] 主题策略文档发布
- [ ] CI 对新增代码执行 Token 合规检查
- [ ] 至少 20 个页面接入新增组件/布局

### 6.4 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 新增组件 API 设计不合理 | 后期大量重构 | 先出 RFC，小范围试点 |
| 组件级 Token 过多 | 维护成本上升 | 按组件优先级分批增加，避免过度设计 |
| 主题策略争议大 | 决策延迟 | 由设计负责人拍板，允许后续微调 |

## 7. 阶段 3：模块级重构（第 11-16 周）

### 7.1 目标

按模块优先级完成存量页面重构，实现 80% 以上页面使用标准模板，90% 以上页面 Token 合规。

### 7.2 模块优先级

| 优先级 | 模块 | 页面数 | 重构理由 |
|--------|------|--------|----------|
| P0 | MES | 42 | 页面最多，制造核心 |
| P0 | WMS | 33 | 供应链核心，列表页密集 |
| P0 | ERP | 23 | 核心模块，跨多个业务域 |
| P1 | CRM | 21 | 高频使用，列表/详情/表单典型 |
| P1 | Finance | 23 | 报表/表单多，数据精度要求高 |
| P1 | HRM | 26 | 员工/考勤/薪酬，表单密集 |
| P1 | QMS | 24 | 质量核心，状态流转复杂 |
| P2 | RD / PDM / SCM / SRM / LIMS / APS | — | 按业务优先级分批 |
| P3 | 其他长尾模块 | — | 最后处理 |

### 7.3 每个模块的重构流程

#### 步骤 A：模块评估（0.5-1 天）

1. 从映射表中提取该模块所有页面
2. 识别每个页面的目标模板类型
3. 标注高风险页面（复杂交互、特殊布局、大量自定义组件）
4. 输出：`modules/<module>/design-refactor-plan.md`

#### 步骤 B：公共组件/工具提取（1-2 天）

1. 提取模块内重复的表格列配置、表单 schema、状态映射
2. 放入 `modules/<module>/components/` 或 `shared-components`
3. 输出：模块级组件清单

#### 步骤 C：页面迁移（按页面复杂度 0.5-3 天/页）

1. 按「Dashboard → List → Detail → Form → 其他」顺序迁移
2. 每迁移一个页面补充/更新单元测试
3. 标记迁移状态到看板

#### 步骤 D：模块验收（1 天）

1. 设计师走查视觉一致性
2. QA 回归核心流程
3. 输出走查报告

### 7.4 阶段 3 验收标准

- [ ] P0 模块 100% 页面完成模板迁移
- [ ] P1 模块 80% 页面完成模板迁移
- [ ] P2 模块 50% 页面完成模板迁移
- [ ] 全站模板覆盖率 ≥ 80%
- [ ] 全站 Token 合规率 ≥ 90%
- [ ] P0/P1 模块无 P0/P1 级 Bug

### 7.5 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 模块重构影响业务交付 | 业务方反对 | 与业务负责人协商，安排在业务低峰期 |
| 复杂页面迁移引入回归 Bug | 线上问题 | 增加视觉回归测试，关键流程必须人工回归 |
| 模块间依赖导致无法独立迁移 | 进度阻塞 | 优先抽象公共依赖，允许临时 shim |

## 9. 质量保障体系

### 9.1 自动化检查

| 检查项 | 工具 | 触发时机 | 失败策略 |
|--------|------|----------|----------|
| Token 合规检查 | ESLint / AST | PR / 本地 commit | 阻塞合并 |
| 模板使用检查 | AST 扫描 | PR | 警告（过渡期）→ 阻塞 |
| 组件导入检查 | ESLint | PR | 阻塞合并 |
| TypeScript 类型检查 | tsc | PR | 阻塞合并 |
| 单元测试 | vitest | PR | 阻塞合并 |
| 视觉回归测试 | Playwright / Chromatic | 关键 PR | 人工确认 |

### 9.2 代码审查清单

每个涉及页面/组件/Token 的 PR 必须检查：

- [ ] 是否使用了合适的页面模板？
- [ ] 是否使用了共享组件而非自研？
- [ ] 是否存在硬编码颜色/间距/字号？
- [ ] 是否使用了语义 Token？
- [ ] 是否处理了空状态、加载态、错误态？
- [ ] 是否在移动端正常显示？
- [ ] 是否补充了单元测试？
- [ ] 是否更新了相关文档/Storybook？

### 9.3 设计走查清单

- [ ] 页面是否符合模板规范？
- [ ] 颜色、字体、间距是否与 Token 一致？
- [ ] 按钮/链接/状态是否使用正确变体？
- [ ] 表格、表单、卡片是否风格统一？
- [ ] 暗色/Cyber 主题下是否有异常？
- [ ] 交互状态（hover/active/focus/disabled）是否完整？
