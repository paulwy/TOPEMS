## 1. 系统架构概述

### 1.1 四层架构

TOPEMS 采用四层架构设计：

```
┌─────────────────────────────────────────────────────────────┐
│                    Layer 3: 业务赋能层                        │
│  ERP │ MES │ CRM │ WMS │ HRM │ QMS │ SCM │ APS │ EHS │ OA │ BI │
│  业务 Copilot │ 智能表单 │ 文档智能 │ 数据分析                │
├─────────────────────────────────────────────────────────────┤
│                    Layer 2: 智能中枢层                        │
│  Agent 编排器 │ 多 Agent 协作 │ 知识图谱 │ RAG 引擎          │
│  缓存管理 │ 告警管理 │ 性能监控 │ 意图识别                    │
├─────────────────────────────────────────────────────────────┤
│                    Layer 1: 运行时基座层                      │
│  服务框架 │ 数据库访问 │ 缓存层 │ 消息队列 │ 认证授权         │
│  配置管理 │ 日志追踪 │ 指标监控 │ 限流熔断 │ OpenAPI          │
├─────────────────────────────────────────────────────────────┤
│                    Layer 0: MCP 适配层                        │
│  模型适配 │ 工具注册 │ 上下文管理 │ 协议转换 │ 多模型支持      │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 技术栈

- **后端**：Rust + Axum + SQLx + PostgreSQL + Redis
- **前端**：React + TypeScript + Vite + Ant Design
- **AI 服务**：自研 DSH Agent 编排器 + 多模型适配
- **部署**：Docker + Kubernetes（可选）
- **监控**：Prometheus + Grafana

### 1.3 服务端口

| 服务 | 默认端口 | 说明 |
|------|---------|------|
| AI 服务 | 8013 | AI 智能中枢服务 |
| 统一核心服务 | 8080 | 业务核心服务 |
| 前端 Web | 3000 | Web 前端服务 |
| PostgreSQL | 5432 | 数据库 |
| Redis | 6379 | 缓存 |

## 2. 系统部署

### 2.1 环境要求

#### 2.1.1 硬件要求

| 配置类型 | CPU | 内存 | 磁盘 | 说明 |
|---------|-----|------|------|------|
| 最低配置 | 4 核 | 8 GB | 100 GB | 开发测试环境 |
| 推荐配置 | 8 核 | 16 GB | 500 GB | 生产环境（中小规模） |
| 高性能配置 | 16 核 | 32 GB | 1 TB | 生产环境（大规模） |

#### 2.1.2 软件要求

- **操作系统**：Linux（Ubuntu 20.04+、CentOS 8+）、macOS 12+
- **数据库**：PostgreSQL 13+
- **缓存**：Redis 6+
- **Node.js**：18+（前端构建）
- **Rust**：1.70+（后端编译）
- **Docker**：20+（容器化部署，可选）

### 2.2 快速部署

#### 2.2.1 使用生产部署脚本

1. 克隆代码仓库：
   ```bash
   git clone https://github.com/your-org/topems.git
   cd topems
   ```

2. 复制并修改生产环境配置：
   ```bash
   cp .env.production.example .env.production
   vi .env.production
   ```

3. 运行生产部署脚本（dry-run 模式先检查环境）：
   ```bash
   bash scripts/deploy/production-deploy.sh --dry-run
   ```

4. 确认环境检查通过后，执行完整部署：
   ```bash
   bash scripts/deploy/production-deploy.sh --version v1.0.0
   ```

5. 部署完成后，访问系统验证：
   ```bash
   curl http://localhost:8080/health
   ```

#### 2.2.2 部署脚本选项

| 选项 | 说明 | 默认值 |
|------|------|--------|
| `--env <file>` | 指定环境变量文件 | `.env.production` |
| `--version <tag>` | 指定部署版本 | `latest` |
| `--skip-backup` | 跳过部署前备份 | `false` |
| `--skip-migration` | 跳过数据库迁移 | `false` |
| `--dry-run` | 仅检查环境，不执行部署 | `false` |
| `--help` | 显示帮助信息 | - |

### 2.3 Docker 部署

1. 构建 Docker 镜像：
   ```bash
   docker build -t topems:latest .
   ```

2. 使用 Docker Compose 启动服务：
   ```bash
   docker-compose up -d
   ```

3. 查看服务状态：
   ```bash
   docker-compose ps
   ```

### 2.4 Kubernetes 部署

1. 进入 Kubernetes 配置目录：
   ```bash
   cd deploy/k8s
   ```

2. 修改配置文件（命名空间、镜像版本、资源限制等）

3. 部署服务：
   ```bash
   kubectl apply -f base/
   kubectl apply -f services/
   ```

4. 查看部署状态：
   ```bash
   kubectl get pods -n topems
   ```

## 3. 用户与权限管理

### 3.1 用户管理

#### 3.1.1 创建用户

1. 进入「系统管理」模块，选择「用户管理」
2. 点击「添加用户」按钮
3. 填写用户信息：
   - 用户名（登录账号）
   - 姓名
   - 邮箱
   - 手机号
   - 所属部门
   - 职位
4. 设置初始密码
5. 分配角色和权限
6. 点击「保存」按钮

#### 3.1.2 用户状态管理

- **启用**：用户可以正常登录系统
- **禁用**：用户无法登录系统，但数据保留
- **锁定**：连续多次登录失败后自动锁定，30 分钟后自动解锁
- **删除**：删除用户账号（建议使用禁用代替删除）

### 3.2 角色管理

#### 3.2.1 预设角色

| 角色 | 权限范围 | 说明 |
|------|---------|------|
| 超级管理员 | 全部权限 | 系统最高权限，谨慎分配 |
| 系统管理员 | 系统管理权限 | 用户、角色、配置管理 |
| 业务管理员 | 业务模块管理权限 | 各业务模块的管理操作 |
| 普通用户 | 业务操作权限 | 日常业务操作 |
| 只读用户 | 只读权限 | 仅查看数据，无法修改 |

#### 3.2.2 创建自定义角色

1. 进入「系统管理」模块，选择「角色管理」
2. 点击「添加角色」按钮
3. 填写角色名称和描述
4. 勾选该角色拥有的权限
5. 点击「保存」按钮

### 3.3 权限管理

#### 3.3.1 权限类型

- **模块权限**：是否可以访问某个业务模块
- **操作权限**：在模块内可以执行的操作（查看、新增、编辑、删除、审批等）
- **数据权限**：可以查看的数据范围（全部、本部门、本人）

#### 3.3.2 权限分配原则

- **最小权限原则**：只分配用户完成工作所需的最小权限
- **职责分离原则**：关键操作需要不同角色的用户分别执行
- **定期审查原则**：定期审查用户权限，及时回收不再需要的权限

## 7. 备份与恢复

### 7.1 数据备份

#### 7.1.1 备份策略

| 备份类型 | 频率 | 保留时间 | 说明 |
|---------|------|---------|------|
| 全量备份 | 每天凌晨 2:00 | 30 天 | 完整数据库备份 |
| 增量备份 | 每小时 | 7 天 | 增量数据备份 |
| 日志备份 | 实时 | 7 天 | 数据库事务日志备份 |
| 配置备份 | 配置变更时 | 永久 | 系统配置文件备份 |

#### 7.1.2 手动备份

1. 进入「系统管理」模块，选择「备份恢复」
2. 点击「立即备份」按钮
3. 选择备份类型（全量备份、增量备份）
4. 填写备份描述
5. 点击「开始备份」按钮
6. 等待备份完成，可以下载备份文件

#### 7.1.3 命令行备份

```bash
# PostgreSQL 全量备份
pg_dump -U topems -h localhost -d topems -F c -f topems_backup_$(date +%Y%m%d).dump

# Redis 数据备份
redis-cli -h localhost -p 6379 BGSAVE

# 配置文件备份
tar -czf config_backup_$(date +%Y%m%d).tar.gz /etc/topems/
```

### 7.2 数据恢复

#### 7.2.1 恢复前准备

1. 确认备份文件完整可用
2. 通知相关用户系统即将进行维护
3. 停止应用服务
4. 对当前数据进行一次全量备份（作为回滚点）

#### 7.2.2 恢复步骤

1. 进入「系统管理」模块，选择「备份恢复」
2. 在备份列表中选择要恢复的备份文件
3. 点击「恢复」按钮
4. 确认恢复操作（此操作会覆盖当前数据）
5. 等待恢复完成
6. 启动应用服务
7. 验证系统数据完整性

#### 7.2.3 命令行恢复

```bash
# 停止应用服务
systemctl stop topems-backend

# PostgreSQL 数据恢复
pg_restore -U topems -h localhost -d topems -c topems_backup_20260828.dump

# Redis 数据恢复
# 将备份文件复制到 Redis 数据目录，然后重启 Redis
cp dump.rdb /var/lib/redis/
systemctl restart redis

# 启动应用服务
systemctl start topems-backend
```

### 7.3 备份验证

定期验证备份文件的可用性：

1. 每月在测试环境恢复一次最新备份
2. 验证数据完整性
3. 验证应用功能正常
4. 记录验证结果

## 8. 性能优化

### 8.1 数据库优化

#### 8.1.1 索引优化

- 定期检查慢查询日志，识别需要添加索引的查询
- 为常用查询条件创建索引
- 避免过度索引（会影响写入性能）
- 定期重建索引，减少索引碎片

```sql
-- 查看慢查询
SELECT * FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10;

-- 重建索引
REINDEX INDEX CONCURRENTLY idx_table_column;
```

#### 8.1.2 连接池优化

- 根据并发量调整数据库连接池大小
- 推荐连接池大小 = (核心数 * 2) + 有效磁盘数
- 监控连接池使用率，及时调整

#### 8.1.3 查询优化

- 避免 SELECT *，只查询需要的字段
- 使用分页查询，避免一次返回大量数据
- 合理使用事务，避免长事务
- 定期执行 VACUUM 和 ANALYZE

### 8.2 缓存优化

#### 8.2.1 缓存策略

- **热点数据缓存**：将频繁访问的数据缓存到 Redis
- **查询结果缓存**：缓存复杂查询的结果
- **会话缓存**：缓存用户会话信息
- **配置缓存**：缓存系统配置信息

#### 8.2.2 缓存失效策略

- **TTL 过期**：设置缓存过期时间
- **主动失效**：数据更新时主动删除相关缓存
- **LRU 淘汰**：内存不足时淘汰最近最少使用的缓存

#### 8.2.3 缓存监控

- 监控缓存命中率（目标 > 80%）
- 监控缓存内存使用率
- 监控缓存 Key 数量
- 定期清理无效缓存

### 8.3 应用优化

#### 8.3.1 代码优化

- 避免 N+1 查询，使用批量查询
- 使用异步处理非关键操作
- 合理使用并发，避免资源竞争
- 定期进行代码审查，识别性能问题

#### 8.3.2 资源限制

- 为每个服务设置合理的 CPU 和内存限制
- 使用限流机制，防止突发流量压垮系统
- 设置请求超时，避免长时间占用资源
- 使用熔断机制，故障时快速失败

### 8.4 AI 服务优化

#### 8.4.1 模型选择

- 根据任务复杂度选择合适的模型
- 简单任务使用轻量级模型（如 GPT-3.5-turbo）
- 复杂任务使用高级模型（如 GPT-4）
- 本地部署模型，降低延迟和成本

#### 8.4.2 缓存优化

- 缓存相似请求的 AI 响应
- 使用语义缓存，提高缓存命中率
- 合理设置缓存过期时间

#### 8.4.3 批量处理

- 批量处理多个 AI 请求，减少网络开销
- 使用异步队列处理非实时 AI 请求
- 合理控制并发请求数，避免触发 API 限流

## 9. 故障排查

### 9.1 常见故障

#### 9.1.1 服务无法启动

**可能原因：**
- 配置文件错误
- 端口被占用
- 数据库连接失败
- 依赖服务未启动

**排查步骤：**
1. 查看服务日志：`journalctl -u topems-backend -f`
2. 检查配置文件：确认数据库连接、端口等配置正确
3. 检查端口占用：`lsof -i :8080`
4. 检查数据库连接：`pg_isready -h localhost -p 5432`
5. 检查依赖服务：确认 PostgreSQL、Redis 已启动

#### 9.1.2 系统响应慢

**可能原因：**
- 数据库慢查询
- 缓存命中率低
- 服务器资源不足
- 网络延迟高

**排查步骤：**
1. 查看系统监控：CPU、内存、磁盘、网络使用率
2. 查看数据库慢查询日志
3. 查看缓存命中率
4. 使用 APM 工具追踪请求链路
5. 检查网络连接质量

#### 9.1.3 数据库连接失败

**可能原因：**
- 数据库服务未启动
- 数据库连接配置错误
- 网络不通
- 数据库连接数已满
- 防火墙阻止连接

**排查步骤：**
1. 检查数据库服务状态：`systemctl status postgresql`
2. 测试数据库连接：`psql -h localhost -U topems -d topems`
3. 检查连接配置：确认主机、端口、用户名、密码正确
4. 检查网络连通性：`telnet localhost 5432`
5. 检查连接数：`SELECT count(*) FROM pg_stat_activity;`
6. 检查防火墙规则

#### 9.1.4 AI 服务无响应

**可能原因：**
- AI 模型 API Key 无效
- AI 模型服务不可用
- 网络不通
- 请求超时
- 触发 API 限流

**排查步骤：**
1. 查看 AI 服务日志
2. 测试 AI 模型 API 连接
3. 检查 API Key 是否有效
4. 检查网络连通性
5. 检查 API 调用频率是否超限
6. 查看 AI 治理仪表盘的错误统计

### 9.2 日志管理

#### 9.2.1 日志位置

| 日志类型 | 位置 | 说明 |

## 10. 安全管理

### 10.1 访问安全

#### 10.1.1 网络安全

- 使用 HTTPS 加密传输
- 配置防火墙，只开放必要端口
- 使用 VPN 或堡垒机访问管理后台
- 限制数据库和缓存的访问 IP
- 定期扫描安全漏洞

#### 10.1.2 身份认证

- 强制使用强密码（长度 >= 8，包含大小写字母、数字、特殊字符）
- 启用多因素认证（MFA）
- 定期更换密码（建议每 90 天）
- 禁止共享账号
- 离职员工及时禁用账号

#### 10.1.3 会话安全

- 设置合理的会话超时时间（建议 30 分钟）
- 使用安全的 Cookie（HttpOnly、Secure、SameSite）
- 支持单点登录（SSO）和单点登出
- 记录用户登录日志（登录时间、IP、设备）
- 异常登录时发送通知

### 10.2 数据安全

#### 10.2.1 数据加密

- 传输加密：使用 HTTPS/TLS 1.2+
- 存储加密：敏感数据加密存储
- 数据库加密：启用 PostgreSQL 透明数据加密（TDE）
- 备份加密：备份文件加密存储
- 密钥管理：使用专业的密钥管理服务（KMS）

#### 10.2.2 数据脱敏

- 个人身份信息（PII）脱敏显示（如手机号、身份证号）
- AI 服务请求和响应中的敏感数据脱敏
- 日志中的敏感数据脱敏
- 测试环境使用脱敏数据

#### 10.2.3 数据访问控制

- 基于角色的访问控制（RBAC）
- 数据权限控制（全部、本部门、本人）
- 敏感操作需要二次确认
- 重要数据操作记录审计日志
- 定期审查数据访问权限

### 10.3 AI 安全

#### 10.3.1 内容安全

- 启用内容安全过滤，防止生成有害内容
- 配置敏感词过滤规则
- 记录 AI 交互内容，用于安全审计
- 定期审查 AI 生成内容
- 用户可以举报不当内容

#### 10.3.2 隐私保护

- AI 服务请求中的个人数据脱敏
- 不将用户数据用于模型训练（除非用户明确同意）
- 提供数据删除功能
- 遵守相关法律法规（如 GDPR、个人信息保护法）
- 定期进行隐私影响评估

#### 10.3.3 滥用防护

- 配置请求频率限制，防止 API 滥用
- 监控异常请求模式
- 识别和封禁恶意用户
- 设置 API 调用配额
- 定期分析 AI 使用情况

### 10.4 安全审计

#### 10.4.1 审计日志

记录以下操作的审计日志：
- 用户登录和登出
- 用户权限变更
- 重要数据的创建、修改、删除
- 系统配置变更
- AI 服务调用
- 安全相关操作

#### 10.4.2 定期审计

- 每月审查用户权限
- 每月审查审计日志
- 每季度进行安全漏洞扫描
- 每半年进行渗透测试
- 每年进行安全评估

#### 10.4.3 应急响应

- 制定安全事件应急响应预案
- 发现安全事件立即启动应急响应
- 及时通知相关人员和用户
- 记录事件处理过程
- 事后进行复盘和改进
